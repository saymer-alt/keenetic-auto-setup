## Часть A. Проверка работающей beta.2 в выходные (без обновления)

### 1. Зафиксировать исходное состояние

В SSH на **своём** NC-4210 (команды ниже только читают состояние):

```sh
date
uname -m
opkg print-architecture
opkg list-installed | grep '^kas-control-center '
/opt/bin/kas-control-center -version
sh /opt/etc/init.d/S98kas-control-center status
```

Отдельно записать фактический адрес и порт панели (8081 — типовой, но пользователь
может изменить его), режим авторизации, выбранный канал обновлений и статусы
Mihomo/MagiTrickle. Не публиковать секреты или полные конфигурации в Issue.

### 2. Контрольный список работы beta.2

- [ ] Web доступна с разрешённого клиентского устройства по штатному адресу; нет неожиданной доступности из недоверенных подсетей/WAN.
- [ ] В обзоре указано `v0.1.0-beta.2` и правильный source SHA; установленная и runtime-версии не расходятся.
- [ ] Русский и английский язык, переключение темы и сохранение выбранных настроек работают.
- [ ] `Обзор`, `Подписки`, `Конфигурация`, `Диагностика`, `Настройки` доступны.
- [ ] Список серверов подписок загружается; исключение **и снятие** `exclude-filter` работают с проверкой фактического результата (только на безопасном тестовом сценарии и с резервной копией).
- [ ] Полный YAML и работающие маршруты остаются штатными; Doctor показывает фактическое состояние без маскировки WARN/FAIL.
- [ ] Ручные проверки доступности обновлений Mihomo/MagiTrickle не изменяют сервисы сами по себе.
- [ ] Выбран канал `Бета`; `Проверить версию панели` на опубликованной beta.2 сообщает об отсутствии более новой beta, не инициирует установку.
- [ ] Порт, ограничения доступа и пароль/их отсутствие сохраняются после штатного перезапуска панели.
- [ ] Реальный доступ клиентских устройств в сеть работает; состояние одного процесса не считается доказательством успешной маршрутизации.
- [ ] При плановой перезагрузке устройства панель и рабочие службы восстановились; не перезагружать только ради формального PASS, если это помешает работе.

Перед любым изменением YAML/фильтров сделать защищённую копию соответствующих
файлов (например, `/opt/etc/mihomo/config.yaml` и доступных
`/opt/etc/kas-control-center.*`) на надёжный носитель, проверить, что копия читается;
не выгружать пользовательские секреты в GitHub.

## Часть B. Критическая проверка будущего beta.2 → beta.3

**Не выполнять до появления канонического опубликованного релиза beta.3 и
проверенного experimental index.** Draft PR #304 — не готовый IPK.

### Обязательные release gates до появления кнопки обновления

1. Merge beta.3 в подходящую ветку **только после ревью**, сборка на финальном
   immutable source SHA, проверенные ABI/ELF/BUILD_INFO, SHA256, opkg versions.
2. Для всех заявленных архитектур — соответствующие IPK и согласованный
   `SHA256SUMS`, service-lab update `beta.2 → beta.3` с запуском нового процесса,
   восстановлением настроек и отрицательными сценариями.
3. Независимо подтвердить, что release не является test alias и его метаданные
   соответствуют выбранному `experimental` каналу; перед изменением индекса
   сохранить его прежний asset для восстановления.
4. Не переключать индекс и не публиковать beta.3 без отдельного owner GO.
   Никакого обязательного SSH в штатном сценарии будущего обновления.

### Когда beta.3 будет опубликована и владелец разрешит тест

1. Сделать защищённый backup пользовательских настроек Web и YAML; записать
   исходные версии, выбранный порт, интерфейсы, состояние Mihomo/MT и доступность сети.
2. В beta.2 открыть `Настройки → Обновление панели` (или фактический раздел
   самообновления), выбрать `Бета` и **вручную** запустить проверку.
3. Проверить предлагаемые версию и источник. Подтвердить установку **один раз**.
   Не запускать параллельно импорт YAML, opkg либо другое обновление.
4. Дождаться перезапуска панели и повторного подключения браузера.
   Сверить **новую runtime-версию**, source SHA и состояние службы; только ответ
   старого HTTP-процесса не доказывает успешное обновление.
5. Проверить все ранее зафиксированные настройки и конфигурацию, подписки,
   `exclude-filter`, Doctor, Mihomo, MagiTrickle, доступ клиентов и смену темы.
6. Повторная ручная проверка должна вернуть `нет более новой версии` без
   нового opkg install. Автообновления по таймеру не должно быть.

### Негативные случаи

- Недоступный GitHub/индекс: понятная ошибка, старый бинарник продолжает работать.
- Неверный SHA256, ABI, release tag, source SHA или `Channel`: отказ **до** установки.
- Равная/более старая версия: no-op, без downgrade.
- Занятый opkg/другие операции: блокировка конфликта, без параллельных транзакций.
- Нет свободного места: безопасный отказ.
- Потеря Web-соединения при обновлении: проверить фактическую установленную и
  запущенную версию после восстановления связи, не объявлять успех преждевременно.
- Откат автоматически **не обещать**. При `PANEL_RECOVERY_REQUIRED` использовать
  документированный `/opt/bin/kas-control-center -recover-panel-update`
  через SSH **только как восстановление**, не как нормальный путь upgrade.

Не воспроизводить опасные сбои (включая обрыв питания) на основном домашнем
роутере без отдельного разрешения и плана восстановления: достаточно
соответствующих отрицательных тестов в CI/лаборатории.
