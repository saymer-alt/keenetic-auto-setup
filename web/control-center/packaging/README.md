# Optional experimental Control Center IPK

Это отдельный opt-in пакет `kas-control-center`, не часть автоматической установки
KAS. Пакет не устанавливает, не останавливает и не удаляет Mihomo, watchdog,
MagiTrickle, маршруты или конфиги ядра. Нужны уже работающий Entware и отдельно
проверенный KAS. Аппаратная приёмка нового пакета пока **не выполнена**.

Проблема: ручной lifecycle-helper владеет бинарником и init-файлом самостоятельно;
обновлять эти же пути через opkg без явного разделения владения опасно. Выбран
маленький отдельный рецепт opkg вместо изменения основного установщика. Альтернатива
— продолжать ручной helper — остаётся доступна. Польза: стандартный учёт payload и
удаление через opkg. Цена: четыре cross-build, отдельные hooks и аппаратная приёмка.
Критерии: отказ от чужих файлов, сохранение настроек, drain импортера перед
заменой/удалением, отсутствие операций над ядром. При непроверенном владельце или
незавершённом drain пакет останавливается с ошибкой; принудительного удаления нет.

## Сборка

Из корня checkout; Python 3, Go и обычный Linux build-host:

```sh
python3 web/control-center/packaging/build-ipk.py \
  --arch mipsel-3.4 --version 0.1.0-1 \
  --source-sha "$(git rev-parse HEAD)" --output /tmp/kas-ipk
(cd /tmp/kas-ipk && sha256sum ./*.ipk > SHA256SUMS)
python3 tests/test_ipk.py -v
```

Поддержаны `aarch64-3.10`, `armv7-3.2` (`GOARM=7`), `mipsel-3.4`, `mips-3.4`.
Все сборки — `CGO_ENABLED=0`, MIPS — `GOMIPS=softfloat`. В пакет включается
`/opt/share/kas-control-center/BUILD_INFO`: source SHA, архитектура, параметры Go и
SHA256 бинарника. Версия пакета задаётся явно. `--binary` предназначен только для
тестирования архива, а не для выпуска: происхождение переданного файла не проверяется.

Workflow `web-ipk.yml` собирает четыре IPK с возрастающим номером запуска CI
и SHA в версии (`0.0.1~testRUN.SHA-1`) и SHA в имени артефакта. Это устраняет
ложный downgrade при сравнении случайных хешей старых `0.0.0~gitSHA` сборок. Он
сохраняет `SHA256SUMS` и вывод `go version -m`. Он не создаёт релизов, не публикует
`latest`, не меняет `main`/`stable`. Пререлиз с правом записи требует отдельного
явного решения и привязки к конкретному source SHA.

## Ручная установка и запуск на тестовом устройстве

Выбрать IPK **точной архитектуры Entware**, проверить контрольную сумму, затем:

```sh
sha256sum -c SHA256SUMS
opkg install ./kas-control-center_VERSION_ARCH.ipk
/opt/etc/init.d/S98kas-control-center start
/opt/etc/init.d/S98kas-control-center status
```

`postinst` **никогда не запускает сервис** — также после upgrade. При upgrade
`preinst` останавливает старую панель через SIGTERM и ожидает drain до 60 секунд;
при ошибке замену следует прекратить. После успешного upgrade панель нужно запустить
вручную. Уже установленный init-файл запускает сервис при обычном Entware boot.
Не применять `--force-overwrite`/`--force-removal-of-dependent-packages` для обхода отказа.

Команда сервиса:

```sh
/opt/bin/kas-control-center -lan -listen auto \
  -settings-file /opt/etc/kas-control-center.settings.json
```

Свежая конфигурация использует Home LAN/br0 и порт **8081**. Отсутствующий settings-файл
означает defaults; файл создаёт приложение при сохранении. Импортированная ручная
настройка может сохранять **18081**. При занятом адресе старт возвращает ненулевой код и понятный `PORT_BIND_FAILED`;
другие сервисы и порты не меняются. Для первого запуска на свободном порту можно
явно создать **новый**, ещё не существующий settings-файл (не перезаписывать свои
настройки), затем запустить сервис:

```sh
umask 077
# Только если settings-файла ещё нет; 18082 — пример свободного порта.
(set -C; printf '%s\n' '{"version":1,"port":18082,"auth_mode":"none"}' > /opt/etc/kas-control-center.settings.json)
/opt/etc/init.d/S98kas-control-center start
```

Для существующей конфигурации менять порт через настройки панели либо подготовить
копию настроек отдельно, сохранив все поля и права 0600. Init выводит проверенный
адрес, полученный от запуска Go. Произвольные ошибки/секреты не сохраняются: FIFO
фильтр оставляет не более двух коротких служебных строк в tmpfs startup-файле.
Точный текущий адрес после изменения порта нужно смотреть в настройках панели;
init не утверждает, что импортированный порт равен defaults.

Совместимые необязательные пользовательские файлы:

| Файл `/opt/etc/kas-control-center.*` | Аргумент |
| --- | --- |
| `password` | `-password-file` (legacy password) |
| `proxy-origin` | `-proxy-origin` |
| `export-names` | `-provider-names-export` (явный opt-in) |
| `mihomo-api-secret` | `-provider-secret-file`, только вместе с export |

Settings и эти файлы не входят в package payload. Пакет не читает и не переписывает
секреты в hooks; init передаёт секретные файлы по пути, а не содержимое в argv.
В payload сохраняется BSD notice зависимости `github.com/GehirnInc/crypt` в
`/opt/share/kas-control-center/THIRD_PARTY_NOTICES`.

Файлы секретов должны быть обычными, принадлежать root и иметь права 0600;
проверки содержимого выполняет приложение. Симлинки отклоняются.

## Переход с ручной установки и удаление

IPK и `kas-web-manage.sh` имеют разные ownership markers. `preinst` отказывает,
если бинарник/init уже существуют без учёта этого пакета в opkg, либо остался
`kas-control-center.web.sha256`. Автоматического захвата/миграции нет.

Сначала сохранить настройки/секреты, записать текущий порт (для старой ручной установки
обычно 18081), остановить и удалить **только панель** исходным ручным helper. Проверить,
что процесс завершился, его binary/init/manifest убраны, а настройки сохранены. Затем
установить IPK и явно запустить его. Не удалять несовпадающий payload вручную ради
обхода проверки: сначала выяснить владельца.

```sh
/opt/etc/init.d/S98kas-control-center stop
opkg remove kas-control-center
```

Удаление вызывает graceful stop; SIGKILL отсутствует. При незавершённом импорте
удаление/upgrade должны завершиться ошибкой: дождаться окончания и повторить.
Файлы настроек, паролей, API secret и proxy origin сохраняются после удаления,
поскольку opkg их не устанавливал. Не использовать ручной helper для удаления IPK.

## Границы проверки

Тесты читают **реальный gzip-tar IPK** и исполняют извлечённые hooks в изолированном
`IPKG_INSTROOT`/`PKG_ROOT`; это не имитация положительного ответа opkg. Проверяются состав,
metadata, свежая установка, upgrade ownership, отказ от ручного init и сохранение
пользовательского settings. Offline hooks не запускают сервисы хоста.

Реальный Entware opkg 38eccbb1 (2024-10-16), официальный статический x64 installer,
прошёл install → upgrade → remove в offline-root с `--force-postinstall`: исполнялись
также hooks. Этот тест выявил и закрепил три требования Entware: gzip-tar внешний
контейнер вместо Debian ar; явные directory members внутри data tar; `PKG_ROOT`
для offline hooks. SHA256 installer: `08c8feb2ef3153f025ba687f8df02adf915e4252a3605cc6798f8d105162cb38`.
CI скачивает его по HTTPS и проверяет закреплённый SHA256 перед запуском.

Локально тест реального Entware `opkg --offline-root` выполняется при наличии
`KAS_TEST_OPKG=/path/to/entware/opkg`; без него явно SKIP. Ни host-архив, ни hooks
не доказывают поведение BusyBox/proc на роутере или фактический
importer drain. Перед продвижением нужны тестовый роутер каждой заявляемой архитектуры,
install/start/reboot/upgrade/remove, занятый порт, изменённый/чужой PID, рабочий импорт
во время SIGTERM и сохранность конфигов ядра. Не выполнять на production автоматически.


### Проверка реального init в CI

`tests/test_panel_ipk_service.sh` запускается только отдельным job `service-lifecycle`
на одноразовом Ubuntu x86_64 runner с явным lab guard. Он устанавливает native Go
fixture через настоящий Entware opkg в собственные предварительно пустые `/opt`
пути и создаёт синтетический bridge `br0`. Fixture имеет aarch64 metadata **только
для проверки hooks**; это не проверка ABI aarch64 или KeeneticOS.

Проверяются реальный init/PID/proc lifecycle, HTTP default8081, отдельный пароль,
живой перенос listener на8082, Entware root auth на синтетических `/opt/etc/passwd`
и `/opt/etc/shadow` (правильный/неверный/locked пароль), понятный отказ при занятом
порту без остановки чужого listener, upgrade и remove с сохранением настроек и
core sentinel. Credentials остаются в приватных fixtures и HTTP-запросах; лог
содержит только маркеры этапов и SHA256 сохранённой конфигурации. Cleanup посылает
только TERM собственному Python listener, gracefully останавливает панель, удаляет
созданный bridge и собственные fixtures. При существующем `br0`, credential-файлах
или других test-owned путях сценарий отказывается работать до изменений.

Эта проверка добавлена как отдельный обязательный CI gate; локальная среда с
несовпадающими PID namespace её не подтверждает. Crossbuild job ожидает её успеха.

### Обзор процессов и итог Doctor

GET `/api/status` сопоставляет исполняемые файлы процессов через `/proc` с
установленными Mihomo/MagiTrickle. Это наблюдение процесса, а не доказательство
исправности маршрутизации. Недоступный proc даёт неизвестный результат, найденный
файл сам по себе не означает работающий сервис. Процессы не запускаются.

Версия Mihomo читается только GET `http://127.0.0.1:9090/version`, с лимитом
4 KiB и таймаутом 1 секунда, без HTTP proxy и redirects. При включённом экспорте
может использоваться уже загруженный secret; YAML и новые секреты не читаются.
Версия MagiTrickle подписана «пакет» и берётся из защищённого opkg control,
а не объявляется версией работающего процесса. Watchdog без записи применения
показывает фактическую SHA256 вместо выдуманного номера версии.

Doctor возвращает отдельно итоговую сводку OK/WARN/FAIL и числа проверок.
Проверяется полный конечный блок сводки, его согласованность с exit code и
отсутствие обрыва/дубликата. WARN/FAIL — результаты диагностики, а не обязательно
сбой её запуска. При отсутствии распознанной сводки панель предлагает прочитать
полный отчёт. Нулевой код сам по себе не означает исправную сеть.

### Ручное обновление Mihomo

В обзоре доступны отдельные кнопки проверки и подтверждённого обновления Mihomo.
При открытии панели сетевой запрос к GitHub не выполняется. Проверка читает
фиксированный канал `saymer-alt/entware-go:latest`, не скачивая бинарник.
Для HTTPS используются системные CA плюс защищённый root-owned Entware bundle
`/opt/etc/ssl/certs/ca-certificates.crt`; проверка сертификата сохраняется.
HTTP proxy/redirects отключены, JSON ограничен 1 MiB и таймаутом 10 секунд.
Неподдержанная архитектура, неоднозначные/некорректные метаданные дают неизвестный
результат. Эта версия проверки поддерживает обычные стабильные пакеты; наличие
незавершённого starter asset может временно заблокировать проверку даже для другой
архитектуры (более строгий отказ, чем в штатном updater).

Предпросмотр доступной версии информационный: после подтверждения штатный
`update-mihomo.sh` заново проверяет канал и самостоятельно решает, нужна ли замена.
Панель раздельно показывает работающую версию из API и сведения opkg: обновление
бинарника вне пакетного менеджера может оставить старую запись opkg. При одинаковой
версии выпуск сверяется с защищённой записью штатного KAS updater: формат,
источник, имя asset, архитектура, версия и размер единственного канонического файла.
Старая запись связывает размер и версию, а не криптографический хеш. При отсутствии
записи выпуск не объявляется подтверждённым; опkg не используется вместо неё.
Совпадающий/старый выпуск не предлагается для установки, невалидная запись блокирует
обновление только выпуска. Новый выпуск при валидной записи либо новая runtime
версия предлагаются, а окончательное решение остаётся за штатным скриптом.
Более старая подтверждённая версия не предлагается. Проверка перед действием действительна
10 минут; после запуска нужно проверять заново. Нет `--force` или произвольных
URL/команд/аргументов. Встроенная копия updater генерируется из корневого скрипта;
CI сверяет байты. Система shared lifecycle lock и отката скрипта не меняется.

Обновление занимает тот же исключительный слот панели, что импорт: Doctor,
импорт, фильтры и сохранение настроек не выполняются одновременно. Закрытие
браузера не убивает worker. TERM панели ожидает его завершения; init/opkg upgrade
при незавершённом drain отказывает, а не применяет SIGKILL.

Результат показывает только ограниченный код и сравнение фактических бинарных
SHA256 до/после: изменён, не изменился или не подтверждён. Stdout/stderr updater
не передаются в HTTP/журнал. Ошибка не объявляется успешным откатом. При потере
ответа на запуск панель запрашивает статус; замена результата другой вкладкой
не оставляет вечный фиктивный RUNNING. История операций хранится только в памяти;
после перезапуска/потери статуса состояние нужно проверить Doctor.

Полный updater проходит через HTTP adapter в `updates_transaction_test.go`: новый
файл, отказ от старой версии, сбой запуска нового сервиса и восстановление.
Config остаётся идентичным, ложный второй probe запрещён. Файловые операции,
распаковка и transaction-код настоящие; сеть, process/PID и init — синтетические
seams, поэтому это не доказательство ABI/загрузки/реального kernel PID на роутере.
Self-update панели и обновление watchdog этим этапом не реализуются.

### Ручное обновление MagiTrickle

У MT отдельные кнопки и результат. Проверка выполняется только вручную:
`opkg status magitrickle`, `opkg update`, `opkg list-upgradable`. Она обновляет
индексы **подключённых репозиториев Entware**, не использует версию GitHub как
замену версии доступного Entware-пакета, не устанавливает репозитории и не запускает
сервисы. Подтверждается точное имя установленного пакета и его статус installed.
Предлагается только одна однозначная строка обновления именно `magitrickle` с
совпадающей текущей версией. Отсутствие такой строки означает «репозитории не
предлагают обновление», а не доказательство самой новой версии в мире.

POST `/api/updates/magitrickle/check` имеет таймаут 90 секунд и общий слот панели.
Пакетные команды фиксированы; вывод ограничен 256 KiB и не передаётся в HTTP.
Ни `upgrade` без имени, ни force-параметры, ни команды/URL из браузера не доступны.
POST `/api/updates/magitrickle` требует повторного подтверждения и проверки не старше
10 минут. Worker заново обновляет индексы и проверяет кандидат, выполняет только
`opkg install magitrickle` (с его штатными зависимостями), затем штатный init restart.
Если кандидат исчез, переустановка и restart не выполняются. Нет фоновых обновлений.

Установка требует подтверждённого работающего процесса и uptime больше 300 секунд:
upstream postinst обычно сам делает restart, а ранний запуск init Keenetic может
оставлять startup_loop. Остановленный/неизвестный сервис не включается автоматически.
Проверяются защищённые обычные конфиги `/opt/var/lib/magitrickle/config.yaml` и
необязательный `/opt/etc/config/magitrickle.conf`, каждый не более 4 MiB, до и после
операции. Изменение содержимого даёт ошибку; панель не перезаписывает параллельные
пользовательские правки. Успех требует новой версии в opkg, сохранённых конфигов и
процесса с установленным исполняемым файлом. Это не проверка DNS или клиентской сети.

**У MT нет автоматического транзакционного отката пакета.** Сохранение изменённых
conffiles выполняет opkg; после сбоя нужны фактическая проверка и Doctor. Закрытие
браузера/TERM панели не прерывает пакетную установку. Импорт/Doctor/настройки и другое
обновление в это время заблокированы. Обе операции используют общий GET
`/api/updates/operation` с явным компонентом; старый успешный ID не выдаётся за
результат новой операции при потере ответа.

`mt_opkg_test.go` проверяет фактический Entware opkg, локальный HTTP feed и IPK на
изолированной файловой системе: обновление, повторный no-op и оба изменённых
conffiles. В CI IPK этот тест обязателен с проверенным `KAS_TEST_OPKG`. Hooks,
процессы и uptime — явно синтетические; это не аппаратная проверка MT.
