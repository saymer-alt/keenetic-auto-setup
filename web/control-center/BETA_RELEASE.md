# KAS Control Center — первая публичная бета `v0.1.0-beta.1` (кандидат)

**Статус: подготовка, не опубликовано.** Это отдельный необязательный IPK `kas-control-center`, **не** релиз ядра KAS и **не** `stable`/GitHub `latest`. Публикация, merge и изменение рабочих маршрутизаторов — только после отдельного решения владельца.

## Состав и основание

Релизная цепочка: [#279 — WEB self-update](https://github.com/saymer-alt/keenetic-auto-setup/pull/279) → [#283 — пользовательская приёмка](https://github.com/saymer-alt/keenetic-auto-setup/pull/283) → [#285 — RU/EN правки](https://github.com/saymer-alt/keenetic-auto-setup/pull/285) → этот beta-prep PR. Все три PR пока Draft; не считать их влитыми в `main` или `stable`. Перед тегом проверить актуальные SHA, CI, соответствие дерева и права распространения.

Проверенная аппаратная база: Keenetic Giga **KN-1010**, KeeneticOS **5.1.8**, Entware **mipsel-3.4**, `/opt` на внешнем EXT4. 30.10.2026 пользователь подтвердил установку test16, работу Mihomo/MT, UI, нескольких HTTP-подписок, применение и сохранность `exclude-filter` после reboot, ручное WEB-обновление **test16 → test17** и запуск нового `0.0.1~test44.9c715283d525-1`. После обновления работали Overview/Subscriptions/Settings и отображались правильные версии, новый текст RU и «нет более новой версии». Прямой результат `opkg status` после WEB-обновления и полноценные отрицательные сценарии на физическом устройстве не утверждаются; последние проверены в CI.

Всё новое в экспериментальном канале остаётся opt-in; автообновлений без нажатия нет. Подробности и recovery: [PANEL_UPDATE.md](PANEL_UPDATE.md); установка/удаление: [packaging/README.md](packaging/README.md).

В документации не писать «ARM64 аппаратная приёмка», пока её нет. Для первой ограниченной беты не блокировать выпуск на KN-1010, однако не обещать production-готовность на остальных устройствах.

## Что делает и чего не делает панель

Панель умеет запускать штатный Doctor; импортировать полный готовый YAML через установленный KAS; просматривать провайдеров работающего Mihomo и **исключать** отмеченные узлы, не меняя подписку на сервере; вручную проверять и инициировать обновления Mihomo/MT и самой панели; переключать язык/тему. Истинность «процесс запущен» не доказывает доступ клиентов в Интернет. Отмена фильтра восстанавливает исключения, но не является откатом произвольного YAML.

Пакет не устанавливается вместе с обычным KAS и не перезаписывает настройки KeeneticOS, Mihomo или MagiTrickle. Для импорта/фильтра/Doctor нужен соответствующий существующий штатный KAS и доступный Mihomo; отсутствие `kas-core` в карточке не доказывает неисправность legacy-инсталляции.

## Безопасность перед установкой

1. Стандартный listener — **IPv4 интерфейса `br0`, TCP 8081**, а не `0.0.0.0`/WAN. Привязка к адресу **не заменяет** ограничения по источнику: если роутер маршрутизирует из другой сети к адресу `br0`, доступ может существовать. Имена сегментов не важны. Не публиковать доступ на WAN, через незащищённый KeenDNS/proxy или port forwarding.
2. По умолчанию **нет авторизации и TLS**, опция «только подсеть `br0`» выключена. В рабочей сети явно ограничить доступ firewall/ACL по источнику, либо дополнительно включить приемлемую авторизацию и защищённый транспорт. **HTTP Basic по обычному HTTP не шифрует пароль.** Не считать пароль панели, пароль Entware и пароль KeeneticOS одним и тем же.
3. Опциональный `br0`-фильтр может отрезать управляющего клиента из другой подсети, включая удалённое подключение. До включения проверить путь восстановления через LAN/SSH. Панель не создаёт VPN и не меняет firewall.
4. Использовать только подписанные/проверенные источником выпуска IPK и SHA256. Не передавать наружу YAML, подписочные URL, API secret, приватный JSON узлов, реальные пароли, журналы с приватными адресами. Проверка `SHA256SUMS` гарантирует совпадение с опубликованным релизом, но **не заменяет** доверие к учётной записи/репозиторию выпуска.
5. Нет автоматического отката собственного IPK и MagiTrickle; при прерванном self-update не запускать несколько обновлений подряд. Проверить состояние, затем при необходимости использовать документированный recovery через SSH.
6. Во время установки и импорта не выключать роутер. Не применять `opkg --force-*` для обхода ownership/PID/drain-проверок.

## Установка беты с GitHub Release — только после публикации

Перед установкой проверить `opkg print-architecture`, состояние Entware, доступность и свободное место `/opt`, наличие доступа по SSH и копии пользовательских настроек/конфигов. Скачать **один** IPK соответствующей архитектуры и `SHA256SUMS` именно из [тега `v0.1.0-beta.1`](https://github.com/saymer-alt/keenetic-auto-setup/releases/tag/v0.1.0-beta.1) (ссылка активна только после публикации).

На компьютере сверить хеши через `sha256sum -c SHA256SUMS` в каталоге с файлами (точные имена проверять по assets). Перенести проверенный файл через SCP/SFTP либо скачать с проверкой TLS и хеша на роутере. Затем явно:

```sh
opkg install /tmp/kas-control-center_*.ipk
/opt/etc/init.d/S98kas-control-center start
/opt/etc/init.d/S98kas-control-center status
```

**Важно:** `*.ipk` в примере допустимо только в каталоге, где находится **ровно один** заранее проверенный пакет нужной архитектуры; при нескольких файлах указать точное имя. `postinst` не запускает службу автоматически даже после upgrade. Открыть `http://<IPv4 br0>:8081/` либо ранее сохранённый порт. Убедиться в правильных версии/source SHA, авторизации, доступе, фильтрах и Doctor, отдельно подтвердить работу маршрутизации клиентов.

Если панель уже установлена как IPK, `opkg install` выполнит upgrade с обязательным контролируемым stop/drain. Для перехода с ручного helper требуется **другая** процедура ownership: [packaging/README.md](packaging/README.md), раздел «Переход с ручной установки». Удаление **только панели**:

```sh
/opt/etc/init.d/S98kas-control-center stop
opkg remove kas-control-center
```

Установка/удаление WEB не равны установке/удалению KAS core, Mihomo или MT; пользовательские файлы `/opt/etc/kas-control-center.*` сохраняются. Удаление IPK не снимает уже применённый `exclude-filter` в конфигурации Mihomo: при необходимости снять фильтр **до** удаления через WEB.

## Релизный протокол (для сопровождающего)

- Внутренняя версия IPK: **`0.1.0~beta.1-1`** (opkg-comparable), отображаемое имя релиза **`v0.1.0-beta.1`**. Не путать с существующим test17 `0.0.1~test44.9c715283d525-1`. Версия беты должна быть старше test17 по настоящему Entware opkg comparison, не по строковому сравнению.
- Собрать **четыре** IPK из **одного чистого source SHA**, проверить go generate, архитектуру ELF, BUILD_INFO, package control, встроенную версию, SHA256 и результаты CI. CI-кандидаты хранятся как Actions artifacts; **не публикуются автоматически**. Процесс описан в [`web-beta-build.yml`](../../.github/workflows/web-beta-build.yml).
- Внимательно проверить последние результаты CI, включая реальные service-lab и QEMU. Для release-публикации не использовать файл из чужого SHA, dirty checkout или перезапуск сборки под тем же опубликованным тегом.
- После отдельного owner GO: создать **prerelease**, `latest=false`, Git tag `v0.1.0-beta.1` на **точном проверенном source SHA**, загрузить IPK и SHA256SUMS и независимо сверить GitHub API assets/size/digest/URLs. Не менять `main`/`stable` и общую ветку `latest` этой процедурой.
- Действующий WEB experimental updater принимает только index в `kas-web-channel-experimental`, указывающий на immutable `kas-web-ipk-<SHA>`, а **не напрямую** на `v0.1.0-beta.1`. Для обновления беты из WEB потребуется отдельный такой релиз-asset-канал с **теми же** проверенными IPK и согласованный с ним index после owner GO. Пока этого нет — beta распространяется как ручной opt-in IPK. Не обновлять экспериментальный index до проверки идентичности обоих наборов assets.
- Если релизные проверки не прошли, оставить Draft, не публиковать и не затрагивать рабочие роутеры. Отложенные функции (Flow/NetFlow, Ping Check, WDTT) — вне этой беты.

## Минимальная приёмка кандидата

- [ ] Документация и release notes соответствуют реальному поведению; SHA/теги и матрица архитектур честные.
- [ ] GitHub CI на **точном beta source SHA** — green; версия беты сравнивается выше test17 в Entware opkg.
- [ ] IPK каждого ABI проверен по ELF, пакетным метаданным, контрольным суммам и `BUILD_INFO`.
- [ ] Изолированная установка, запуск, изменение порта/пароля, clean/remove/upgrade и сохранность настроек — CI, без влияния на production.
- [ ] Проверка basic security: LAN-bind, отсутствие случайного WAN-публикации, Host/Origin, auth, строгие права settings, безопасные отказы при ошибках.
- [ ] Пользовательский KN-1010 остаётся рабочим; beta устанавливается только вручную после решения владельца. Физическую ARM64 проверку не объявлять завершённой.
- [ ] Отдельное разрешение владельца на публичную публикацию и затем на тестирование рабочего роутера; без автоматического изменения `stable` или маршрутов.
