# Архитектура Keenetic Auto Setup

Этот документ — главный архитектурный документ проекта: **как система реально устроена, как проходит трафик и почему в ней одновременно существуют MagiTrickle, `mitun0`, `ProxyN`, порт `7890`, DNS interception и Mihomo**.

Он не про установку — за пошаговыми действиями идите в [docs/HOWTO.md](docs/HOWTO.md) ([RU](docs/HOWTO_RU.md)); обзор и быстрый старт — в [README](README.md).

> Документ на русском языке (как и подробные гайды `docs/00–10`). Уровни и факты, подтверждённые кодом проекта и официальной документацией MagiTrickle/Mihomo/Keenetic, помечены ссылками; то, что зависит от конкретной сети или модели роутера, помечено как требующее проверки.

---

## Почему появился проект

Изначально проект создавался исключительно для себя: хотелось один раз настроить Keenetic и больше не возвращаться к нему каждые несколько дней — не проверять, жив ли VPN, не менять конфигурации после каждой блокировки.

Но по мере развития стало ясно: проблема шире. Обычный домашний роутер жёстко связывает маршрутизацию, VPN и выход в интернет в одну цепочку:

```
Устройство → Роутер → Провайдер → Интернет
```

Одна труба, одна политика, ноль решений о том, *что* куда отправлять. Проект вырос в попытку разделить эти задачи между независимыми уровнями — так, чтобы любой уровень можно было заменить, не перестраивая систему.

---

## Основная идея: слои вместо одной трубы

Главная задача — не установить очередной VPN, а превратить домашний роутер в **автономный сетевой узел, который сам принимает решения о маршрутизации**. Каждый компонент делает одну работу и почти ничего не знает о внутренностях остальных:

| Уровень | Кто | За что отвечает | Чем не является |
| --- | --- | --- | --- |
| Платформа | **Keenetic** | интерфейсы, policy-роутинг, firewall, DNS-прокси | не «просто коробка с Wi-Fi» |
| Решение | **MagiTrickle** | смотрит на DNS-запросы, решает, куда идёт каждый домен | не VPN, не прокси, не транспорт |
| Выход-движок | **Mihomo** | принимает трафик и разруливает его по своим серверам/правилам | не «тот самый VPN на роутере» |
| Выходы | AWG, SSTP, OpenConnect, WireGuard, DIRECT | физические каналы | взаимозаменяемые детали |

Благодаря разделению внутреннюю инфраструктуру (серверы Mihomo, подписки, балансировка) можно менять, не трогая Keenetic, — и наоборот.

## Три пути трафика

Это ключевая часть. В системе существуют **три разных механизма прохождения трафика**, и их нельзя смешивать.

### Путь A — DNS-классификация через MagiTrickle (основной)

```
Client
  ↓
DNS → Keenetic DNS → MagiTrickle (классификация домена)
  ↓
решение: DIRECT / ProxyN / mitun0 / другой интерфейс
  ↓
Keenetic policy routing
  ↓
Интернет
```

Клиент спрашивает DNS, MagiTrickle видит запрос, сопоставляет домен с правилами и помечает, через какой интерфейс должен пойти этот трафик. Так работает «точечная маршрутизация»: YouTube — в туннель, локальный банк — напрямую, остальное — по правилам.

### Путь B — прямой proxy-inbound (FoxyProxy и любые SOCKS/HTTP-клиенты)

```
Client / Browser
  ↓
Keenetic :7890  (mixed-port Mihomo)
  ↓
Mihomo inbound
  ↓
Mihomo outbound / выбранный proxy
  ↓
Интернет
```

Здесь клиент сам подключается к прокси-порту Mihomo. MagiTrickle в этом пути не участвует: выбор «что проксировать» делает клиент (шаблоны расширения) плюс правила Mihomo.

### Путь C — TUN (`mitun0`)

```
Client
  ↓
MagiTrickle (классификация)
  ↓
mitun0 (TUN-интерфейс Mihomo)
  ↓
Mihomo TUN → правила Mihomo
  ↓
Linux / Keenetic routing
  ↓
default gateway / выбранный WAN
  ↓
Интернет
```

Трафик входит в Mihomo прозрачным IP-потоком через TUN-устройство. Всё, что Mihomo передаёт дальше без прокси-outbound, уходит через **обычную таблицу маршрутизации Keenetic** — то есть через default gateway.

**Не смешивайте эти пути.** Особенно частая ошибка — считать, что путь C управляется настройками Mihomo так же, как путь B. Это не так (см. [«interface в MetaCubeX ≠ выбор WAN»](#interface-в-metacubex--выбор-wan)).

## Keenetic — платформа

KeeneticOS предоставляет всё, на чём стоит система:

- **интерфейсы и сегменты** — физические WAN, бриджи (`Bridge0` = домашний сегмент), дополнительные Wi-Fi/LAN-сегменты, VPN-интерфейсы;
- **policy routing** — политики подключений (`ip policy`), которые можно назначать сегментам и отдельным зарегистрированным клиентам (web UI «Приоритеты подключений», OS 3.8+);
- **DNS-прокси** — системный резолвер с поддержкой DoT/DoH (OS 3.0+) и опцией перехвата транзитных DNS-запросов;
- **netfilter.d** — хуки, выполняющиеся при каждой пересборке firewall (на них построен VoIP-bypass).

Проект интегрируется через штатные механизмы (`ndmc`/RCI, `netfilter.d`, init-скрипты Entware), а не борется с системой. Никакого Docker в этой архитектуре нет: Mihomo управляется init-скриптом `/opt/etc/init.d/S99mihomo`, тем же, что используют watchdog и updater.

## MagiTrickle — уровень принятия решений

MagiTrickle не передаёт трафик. Он читает DNS и решает. Официальная модель конфигурации проста:

```
Group → Interface → Rule → (Type + Condition)
```

- **Group** — именованный контейнер: набор доменов, привязанный к одному выходу («VPN», «Direct», «Торренты»).
- **Interface** — настройка группы: интерфейс Keenetic, через который уйдёт трафик этой группы (ProxyN, mitun0, VPN-интерфейс).
- **Rule** — матчер домена внутри группы: **Type** определяет, *как* сверять (namespace = домен со всеми поддоменами, wildcard, точный домен, regexp), **Condition** — *что* сверять.

Что происходит, когда клиент открывает `youtube.com`:

```
клиент спрашивает DNS            → перехваченный MagiTrickle DNS отвечает и запоминает пару «IP ↔ youtube.com»
трафик к этому IP появляется     → firewall-метка по правилам группы
группа "VPN" (interface: mitun0) → трафик направлен в mitun0
```

По официальной документации MagiTrickle работает подменой DNS на выбранных интерфейсах и сопоставлением ответов с доменами; маршрутизация выполняется firewall-метками и policy-правилами (цепочки с префиксом `MT_`, ipset-таблицы `mt_*`). Сам MagiTrickle ничего не туннелирует и не проксирует.

### DNS interception: `link` и его назначение

```yaml
link:
  - br0
  - br1
```

`link` — список интерфейсов, **на которых MagiTrickle выполняет DNS-подмену** (по умолчанию `br0` и `br1` — имена мостов со стороны Entware; `br0` — домашний сегмент). Классификация работает только для клиентов тех сегментов, которые входят в этот список. Новый сегмент = новый интерфейс = его нужно добавить в конфигурацию MagiTrickle.

Две границы, которые важно держать в голове:

- DNS-классификация **не равна** IP policy routing: MagiTrickle решает по доменам через DNS, а двигает трафик уже policy-роутинг Keenetic по меткам.
- Перехват классического (порт 53) DNS **не является** блокировкой DoH/DoT: шифрованный клиентский DNS проходит мимо точки подмены (подробнее — раздел DNS ниже).

## Mihomo — маршрутизатор внутри маршрутизатора

Самая распространённая ошибка — считать Mihomo обычным VPN. В этой архитектуре Mihomo — отдельный движок маршрутизации, а для Keenetic он выглядит скромно:

- **inbound**: mixed-порт `7890` (HTTP+SOCKS5) и/или TUN-интерфейс (`mitun0`);
- **outbound**: записи в `proxies`/`proxy-groups` — серверы VLESS/Reality, WireGuard-подобные туннели, SOCKS/HTTP-релеи;
- **rules**: собственные правила Mihomo выбирают outbound для каждого соединения.

Внутри Mihomo может находиться практически любая инфраструктура — несколько подписок, десятки серверов, health-check, резервирование. Роутер не знает, как именно Mihomo доставляет трафик: он просто передаёт его следующему уровню. Поменяли `config.yaml` Mihomo — поменяли всю исходящую инфраструктуру, а Keenetic этого не заметил.

Вход и выход независимы: можно входить одним типом туннеля, а выходить в интернет совершенно другим — любой транспорт заменяется без перестройки остального.

## ProxyN и mitun0 — два входа в Mihomo, два разных механизма

Оба ведут в один и тот же Mihomo, но это **разные уровни**:

| | **ProxyN** (пример: `Proxy0`) | **mitun0** |
| --- | --- | --- |
| Что это | *прокси-интерфейс Keenetic* (SOCKS5 к `127.0.0.1:7890`) | *TUN-устройство Mihomo* (L3, прозрачный IP-вход) |
| Кто создаёт | установщик этого проекта (`ndmc`, идемпотентно) | сам Mihomo — имя задаётся в его конфиге (`tun` → `device-name`); `mitun0` — распространённое имя в Keenetic-сетапах |
| Как трафик входит | как SOCKS5-проксирование на уровне приложения | как обычный IP-трафик через сетевой интерфейс |
| Где виден | в политиках и правилах Keenetic как полноценный интерфейс | в Keenetic как обычный интерфейс, на который тоже можно навести политику |
| Сильная сторона | явная «точка назначения» для правил по клиенту/сегменту | прозрачный основной путь для IP-трафика без клиентских настроек |

О нумерации: на чистом роутере установщик создаёт `Proxy0`; если ID занят, Keenetic выдаст следующий свободный (`Proxy1`, `Proxy2`, …), а человекочитаемая подпись следует номеру — `mihomo t2s0`, `mihomo t2s1`, … (соответствие с нумерацией t2s в MagiTrickle). Поэтому в документации говорят `ProxyN`, а `Proxy0` — это пример, а не гарантированное имя.

## interface в MetaCubeX ≠ выбор WAN

Это одна из самых важных развилок понимания. Три разных понятия:

1. **интерфейс Mihomo** (`interface-name`) — Linux-интерфейс, к которому Mihomo привязывает **собственные исходящие соединения** (по официальной документации — *"mihomo's traffic outbound interface"*);
2. **inbound Mihomo** — порт `7890` или TUN `mitun0`, куда трафик *входит*;
3. **роутинг Keenetic/Linux** — default gateway и политики, решающие, откуда трафик реально уходит из роутера после попадания в таблицы маршрутизации.

Пример на роутере с двумя провайдерами:

```text
WAN1 = ISP A (default gateway)      WAN2 = ISP B
interface-name в Mihomo = WAN2

Путь B:  Client → :7890 → Mihomo → proxy → dialer привязан к WAN2  → выход через ISP B
Путь C:  Client → mitun0 → Mihomo (TUN) → kernel routing → default gateway → выход через ISP A
```

**Настройка interface в MetaCubeX/Mihomo не переключает WAN для всего трафика.** Она биндит исходящие сокеты самого Mihomo — прежде всего соединения к вашим прокси-серверам. Трафик, вошедший через `mitun0`, подчиняется правилам Mihomo как любой другой inbound, но всё, что уходит из него несвязанным потоком, следует обычным таблицам маршрутизации Keenetic. В TUN-настройках есть `auto-detect-interface` (автоопределение выходного интерфейса; документация рекомендует ручную настройку на multi-WAN) — поведение на конкретной схеме с несколькими WAN стоит проверять практически. Если нужен per-path выбор WAN для TUN-трафика — это задача policy-роутинга Keenetic, а не галочка в MetaCubeX.

Скрипт `mihomo-interface-check.sh` — диагностический помощник именно для первого пункта: он перечисляет пригодные WAN-интерфейсы роутера и выдаёт готовые строки `interface-name:` для `config.yaml` Mihomo.

## MetaCubeX UI и controller

Mihomo — самодостаточный сетевой демон. Дашборды в стиле MetaCubeX (metacubexd, yacd, zashboard) — только управление/мониторинг поверх REST API (`external-controller`, по умолчанию `127.0.0.1:9090`).

- Установка по умолчанию в этом проекте не ставит никакого web UI: на роутере работает только демон.
- Дашборд можно разместить на роутере (`external-ui` — статические файлы, раздаваемые API по пути `/ui`) или вообще на другом устройстве — публичные страницы дашбордов умеют подключаться к API удалённо.
- **Безопасность**: API контроллера меняет поведение Mihomo на лету. Не выставляйте его в WAN; держите localhost/LAN-биндинг, задайте `secret`, для удалённого управления используйте VPN или SSH-туннель.
- Влияние наличия/отсутствия локального дашборда на RAM слабых (128 МБ) устройств — вопрос, требующий отдельных измерений; утверждений на этот счёт проект не делает.

## DNS-архитектура

```
Client DNS
    ↓
Keenetic / MagiTrickle        ← контроль пути DNS
    ↓
DNS upstream                  ← выбор резолвера
    ↓
Интернет
```

Здесь три независимых решения, которые часто путают:

1. **DNS клиента** — куда клиент отправляет запросы. Классический DNS должен приходить на Keenetic: MagiTrickle классифицирует только те домены, которые видит. Для этого установщик включает перехват транзитных DNS-запросов (`dns-proxy intercept enable`) — запросы, адресованные напрямую внешним резолверам, перенаправляются в DNS-прокси роутера.
2. **DNS upstream** — куда за резолвингом ходит сам Keenetic: DNS провайдера, Yandex, Cloudflare, Quad9 и т.д., в том числе по DoT/DoH (нативно с OS 3.0, до 8 серверов, приоритет по времени отклика). В сетях с белыми списками доступность выбранного резолвера из этой сети важнее его «лучшести»: сервис может поддерживать DoH/DoT и быть недоступным. Менять Cloudflare colo — не то же самое, что менять страну выхода (см. WARP-раздел ниже).
3. **DoH/DoT клиентов** — шифрованный DNS браузеров и приложений идёт мимо порта 53 в любом случае. Контроль DNS-пути помогает сохранить DNS-контекст для MagiTrickle, но **не является** универсальным контролем всех способов разрешения имён и всех туннелей.

Связка с роутингом: DNS-классификация — входные данные для MagiTrickle, поэтому DNS-проблемы маскируются под проблемы маршрутизации. Чинить нужно уровень выше.

## Дополнительные Wi-Fi/LAN сети

KeeneticOS позволяет создавать дополнительные сегменты — гостевые Wi-Fi на каждый диапазон и проводные сегменты, каждый со своей подсетью и DHCP — и привязывать их к политикам подключений. Доступное число зависит от модели и версии OS (смотрите страницу «Сегменты» своего web UI, фиксированной цифры в документации нет).

Архитектурный сценарий (пример, не обязательная конфигурация):

```text
Network A (Home) → DIRECT (напрямую через провайдера)
Network B        → ProxyN (пример: Proxy0) → Mihomo
Network C        → mitun0 → Mihomo (TUN)
```

Сегмент привязывается к политике, политика — к нужному интерфейсу. И обязательно: **новый сегмент не попадает под MagiTrickle автоматически** — его интерфейс должен быть добавлен в `link:` конфигурации MagiTrickle (или выбран в её web UI), иначе DNS-подмена, а значит и классификация, на этот сегмент не действует.

## Браузерный режим: FoxyProxy

```
Browser
  ↓
FoxyProxy (SOCKS5)
  ↓
Keenetic :7890
  ↓
Mihomo → proxy outbound
  ↓
Интернет
```

Это путь B: расширение подключается напрямую к proxy-эндпоинту Mihomo, минуя MagiTrickle. Выбор сайтов делают шаблоны FoxyProxy плюс собственные правила Mihomo. Можно направлять через прокси только выбранные сервисы (ChatGPT, YouTube, Telegram Web, Gemini, Grok, Copilot, Threads, Instagram — что угодно), не ставя VPN-клиент на компьютер.

```yaml
allow-lan: true
```

в контексте проекта означает: порт `7890` доступен LAN-клиентам — браузеру с FoxyProxy, другим устройствам Wi-Fi/LAN, удалённой домашней/рабочей сети. Самому роутеру эта настройка **не нужна** — Keenetic общается с Mihomo по `127.0.0.1` в любом случае. Граница безопасности: `allow-lan` — не повод открывать `7890` в WAN; firewall на этот порт закрываем.

**WebRTC**: прокси покрывает обычный веб-трафик браузера, но не все его сетевые механизмы. WebRTC может устанавливать собственные UDP-пути мимо прокси, и в прокси-сценарии сайт может узнать о вашей сети информацию, отличающуюся от выхода прокси. Что именно раскрывается — зависит от браузера, версии и сети; универсальной защиты обещать нельзя. Настройки WebRTC проверяются и настраиваются по-браузерному, результат — тестовой страницей WebRTC. Это ограничение именно браузерного сценария: при маршрутизации всей сети через Keenetic UDP идёт по политикам роутера.

## Клиентский VPN и вложенные туннели

Роутер маршрутизирует трафик клиента, пока тот приходит к нему как обычный трафик:

```
без клиентского VPN:
  Client ── site A / B / C ──> Keenetic+MagiTrickle ── решение по каждому ──> DIRECT / mitun0 / Mihomo

с клиентским VPN:
  Client ══ [шифрованный туннель: A+B+C внутри] ══> Keenetic ── видит туннель, не сайты ──> выход туннеля
```

В обычной модели клиентского VPN устройство упаковывает свой трафик в единый поток к VPN-серверу. Keenetic видит этот поток, а не отдельные сайты внутри него, — доменная классификация на такой трафик не действует. Детали зависят от типа VPN и клиента, но принцип один: что не появляется на роутере как отдельные соединения, то нельзя промаршрутизировать по-отдельности.

**Продвинутый случай — наоборот**: Keenetic сам умеет строить туннели (AWG, SSTP, OpenConnect, WireGuard), и такой роутерный туннель можно направить через Mihomo-прокси. Тогда цепочка выходит с публичным IP/страной удалённого прокси. Во вложенных туннелях особенно важен MTU: правильное значение специфично для каждой цепочки (одна из наших WARP-схем работает на 1200 — это пример, а не универсальная рекомендация).

## IPv6 — выключен намеренно

В базовой конфигурации проекта IPv6 **отключён сознательно** — MagiTrickle поставляется с отключённым IPv6, конфиги от link-generators используют `ipv6: false`. Это архитектурное решение, а не недочёт:

- меньше неожиданных путей;
- проще контролировать DNS и роутинг;
- нет потенциальных обходов задуманного IPv4-маршрута.

Включение IPv6 — продвинутое изменение: после него нужно отдельно проверить IPv6-роутинг, DNS и отсутствие пути, обходящего построенную схему.

## WARP / MASQUE и colo

Для схем на базе Cloudflare WARP (конфигурации для них генерирует [link-generators](https://github.com/saymer-alt/link-generators)) важно не путать две вещи:

- **colo** (дата-центр Cloudflare, через который проходит подключение) и **страна выхода/public IP** — разные понятия; смена colo сама по себе не меняет exit IP и не «переносит» вас в другую страну;
- при этом смена colo может практически влиять на качество и доступность отдельных сервисов (например, Telegram или YouTube) даже при том же exit IP.

Поэтому colo имеет практическое значение как параметр отладки, но не как способ выбора геолокации. Для исследования доступных и выбираемых colo существует инструмент [vernette/warpscout](https://github.com/vernette/warpscout) — детали в его документации.

## MT TEST — быстрый smoke test

Практический приём быстрой проверки после установки или изменения маршрутизации: в MagiTrickle создаётся временная группа `MT TEST` с несколькими тестовыми сайтами:

```text
MT TEST
 ├── 2ip.ru
 ├── 2ip.io
 └── speedtest.net
```

Группа направляется через проверяемый выход (например, `mitun0`). Открытие этих страниц за один заход проверяет несколько уровней: правило срабатывает (клиент действительно попадает под группу), DNS-перехват и маршрутизация работают, трафик реально уходит через ожидаемый выход, видимый публичный IP — ожидаемый, speedtest подтверждает реальную передачу данных. Это **быстрый smoke test**, а не исчерпывающая диагностика всего стека — он просто быстро показывает, какой уровень сломан.

## Диагностика: дерево решений

Когда «не работает», идите по уровням сверху вниз — каждый шаг отсекает половину вариантов:

```text
DNS работает?
   ↓
MagiTrickle классифицирует домен?
   ↓
Выбрана правильная Group?
   ↓
Правильный Interface?
   ↓
Трафик попал в mitun0 или :7890?
   ↓
Mihomo получил трафик?
   ↓
Выбран правильный outbound?
   ↓
Какой gateway/WAN?
   ↓
Какой public IP?
```

Где живёт каждый тип проблемы:

| Симптом на уровне | Что смотреть |
| --- | --- |
| DNS | раздел DNS выше: interception (`dns-proxy intercept enable`), upstream, whitelist-доступность |
| MagiTrickle | покрытие интерфейсов (`link:`), правила/группы в его UI |
| Keenetic routing | политики, привязка сегментов, default gateway |
| Mihomo | статус `S99mihomo`, порт `7890`/TUN, правила, `interface-name` |
| upstream proxy | доступность сервера из `config.yaml`, счётчики в логе |
| WAN | провайдер, кабель, MTU |

Пошаговый алгоритм с командами — в [docs/HOWTO.md](docs/HOWTO.md), раздел Diagnostics.

## Watchdog в архитектуре

Любая сложная система сталкивается со сбоями, поэтому в проект встроен механизм самоконтроля. Watchdog каждые 5 минут проверяет: доступность интернета (WAN, напрямую и без Mihomo), порт прокси, сквозной туннель. Принцип решений: **локальная проблема — чиним (рестарт Mihomo), внешняя — ждём**. Отсутствие WAN не означает, что сломан Mihomo, поэтому при полном отказе сети рестартов нет; рестарт происходит только при подтверждённой сети и подтверждённой проблеме в Mihomo/туннеле, с защитой от циклов. Подробная механика — [docs/04-watchdog.md](docs/04-watchdog.md).

## Границы: чего эта архитектура не гарантирует

Технически точная модель обязана объявлять свои пределы:

- весь трафик **не** «всегда идёт через VPN» — маршрутизация выборочная, и часть трафика всегда идёт напрямую;
- SOCKS5/прокси **не** скрывает IP во всех случаях — за рамками проксируемого трафика (пример: WebRTC в браузере) действуют обычные правила сети;
- DNS interception **не** блокирует DoH/DoT и не контролирует шифрованное разрешение имён;
- настройка interface в MetaCubeX **не** определяет WAN для всего трафика роутера;
- MagiTrickle маршрутизирует то, что смог классифицировать через DNS, — **не** любой IP-трафик независимо от DNS;
- `Proxy0` **не** гарантированно существует — корректное имя `ProxyN` (`Proxy0`, `Proxy1`, …);
- смена colo **не** меняет страну выхода;
- даже корректный DNS и правильные маршруты **не** защищают от фильтрации/вмешательства на других уровнях сети (IP-блокировки, DPI) — это ограничение любой однороутерной схемы, а не дефект проекта.
