# KAS: как измерять расход токенов на реальных задачах

> **По необходимости, не стартовые инструкции для агента.** Этот лист — процедура будущего измерения к [Issue #420](https://github.com/saymer-alt/keenetic-auto-setup/issues/420). Общие правила loop guard, бюджетов, безопасного контекста и [матрица метрик](agent-token-efficiency.md#матрица-измерения-шаблон) уже определены; здесь они не дублируются. Никаких текущих результатов измерений этот файл не утверждает.

## До старта одной настоящей задачи

1. Использовать существующую пользовательскую ошибку/задачу, а не создавать дефект ради A/B. Записать Issue/PR, понятный человеку результат (DoD), категорию сложности, точный `branch/HEAD SHA`, модель/агента/режим, дату и часовой пояс. Отдельно отметить, какие правила применяются (`main`/ `stable`, обычная сессия или тестовая копия).
2. **До первой работы агента** зафиксировать доступную телеметрию: точные input/output/cache tokens по задаче, если платформа это предоставляет; иначе `NOT_AVAILABLE`. Если доступен только остаток бонусной квоты, сохранить исходный счётчик **с единицами и источником**, не конвертировать процент в точный расход. Не присылать API-ключи, дампы окружения и приватные конфиги.
3. Убедиться, что задача не выполняется другим агентом одновременно. При фоновых расходах, других чатах/моделях или неотделимых вызовах пометить измерение `CONTAMINATED` — не приписывать общий расход одному PR.

## После задачи, до следующего задания

4. Сохранить финальные показатели **того же счётчика**, время и число вызовов, повторных бесполезных операций, перезапусков CI и ручных `/compact`. Для каждого доказательства — ссылка на конкретный CI run и SHA. Замер квоты «до/после» одной сессии имеет смысл только когда нет иных потребителей квоты.
5. Оценивать **качество наравне с расходом**: DoD выполнен? Обязательные тесты и отрицательные сценарии пройдены? Сколько замечаний review и дополнительных правок? `CI PASS`/ `MERGED`/ `FIELD PASS`/ `PUBLISHED` — разные состояния.
6. Добавить **краткую обезличенную запись** в [Issue #420](https://github.com/saymer-alt/keenetic-auto-setup/issues/420) либо в оговорённый владельцем журнал. При отсутствии точных показаний не пытаться вычислить «средние токены на PR» по округлённому индикатору.

## Карточка замера — копировать только для реально выполненной задачи

```text
Task / Issue / PR:
Category / complexity:
Goal + acceptance:
Agent / exact model / mode / version:
Date / timezone:
Branch / baseline SHA -> final SHA:
Before: tokens input/output/cache = NOT_AVAILABLE
After:  tokens input/output/cache = NOT_AVAILABLE
Before / after quota (value, unit, source) = NOT_AVAILABLE
Other simultaneous quota users: NONE / UNKNOWN / YES
Tool calls / futile repeats / CI reruns = NOT_AVAILABLE
Elapsed time / manual compactions = NOT_AVAILABLE
Gates + evidence URL:
Result = IMPLEMENTED / CI PASS / MERGED / FIELD PASS / BLOCKED
Review corrections / residual risks:
Measurement reliability = EXACT / COARSE / CONTAMINATED / NOT_AVAILABLE
```

## Как корректно сравнивать

- **Наблюдательная серия:** несколько (ориентир **3–5**) реальных сопоставимых *новых* задач одного типа при близких модели, среде и объёме проверки. Это данные **после** оптимизации, не A/B и не доказательство экономии относительно прошлого.
- **Контролируемое A/B** возможно только в отдельной безопасной тестовой копии, с одинаковыми условиями модели/инструментов/настроек/задачи и изолированным учётом. Не отключать обязательные правила KAS-SAFETY-001/KAS-AGENT-001 и не повторять реальные мутации/релизы ради сравнения.
- **Округлённый процент бонусной квоты** (например, 69% → 68%) не даёт точной стоимости задачи: неизвестны точность индикатора, кеширование и параллельное использование. Это только ориентир, **не** основание утверждать «экономия X%».
- Если нет совместимых исходных замеров **до** внедрения #433–#439, писать `NO_COMPARABLE_BASELINE`; не сравнивать разные типы задач и модели так, будто это эксперимент.
- Итог **GO** только при наблюдаемом улучшении *качества-скорректированных* затрат и сохранении всех обязательных проверок; иначе `INCONCLUSIVE` или `NO-GO`. Изменение токенного бюджета не даёт новых полномочий на merge, release или роутеры.

**Текущий статус на 2026-11-07:** `PREPARED / NO_NEW_MEASUREMENTS`. Работающий агент, API, квота, роутеры и релизные конвейеры здесь не запускались и не менялись.
