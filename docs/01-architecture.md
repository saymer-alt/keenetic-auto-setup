# 01 — архитектура

Как это работает на самом деле.

Не «компоненты», а **потоки трафика и принятие решений**.

---

## Общая схема

```
Клиент (LAN)
      ↓
Keenetic + MagiTrickle      ← решение по домену: куда идёт этот трафик?
      ↓
ProxyN (SOCKS5 на 127.0.0.1:7890)   ← или mitun0 (TUN-интерфейс Mihomo)
      ↓
Mihomo (Clash Meta)
      ↓
VPN (VLESS / Reality / etc.)
      ↓
Интернет
```

Это упрощённая однопутевая схема. Полная модель — три пути трафика (DNS-классификация
MagiTrickle, прямой proxy-inbound, TUN `mitun0`), перехват транзитного DNS и роли всех
компонентов — в [ARCHITECTURE.md](../ARCHITECTURE.md), главном архитектурном документе.

Параллельно:

```
VoIP (UDP 1400,3478,3482)
      ↓
bypass_wa (mark)
      ↓
проектный ProxyN → 127.0.0.1:7890 → Mihomo
(альтернатива: ручной permit на VPN — мимо Mihomo)
```

И отдельно:

```
Watchdog
  ↓
проверка → рестарт Mihomo (если надо)
```

---

## Основная идея

Не «всё через прокси», а:

> **разные типы трафика идут разными путями**

---

## Потоки трафика

### 1. Обычный трафик (HTTP/HTTPS)

```
LAN → ProxyN → Mihomo → VPN → Интернет
```

Почему так:

* Mihomo умеет правила (domains, geoip)
* можно гибко управлять маршрутизацией
* SOCKS5 универсален

---

### 2. VoIP (Telegram / WhatsApp)

```
LAN → iptables (mark) → bypass_wa → проектный ProxyN → 127.0.0.1:7890 → Mihomo
(альтернатива — ручной permit на VPN-интерфейс: тогда мимо Mihomo)
```

Почему у VoIP отдельный путь:

* VoIP = UDP + WebRTC
* через прокси-цепочки «по умолчанию»:

  * задержки
  * обрывы
  * иногда вообще не соединяется

👉 Поэтому:

> bypass_wa выводит голосовой трафик из DNS-классификации MagiTrickle в
> выделенную политику. Штатно политика ведёт его через проектный ProxyN
> в Mihomo — дальше по правилам Mihomo; при ручном permit на VPN-интерфейс
> трафик уходит в VPN напрямую, минуя Mihomo.

---

### 3. Прямой трафик (опционально)

```
LAN → Keenetic → провайдер
```

Используется для:

* локальных ресурсов
* GEOIP private
* fallback

---

## Компоненты

### Mihomo (Clash Meta)

Роль:

* основной прокси
* rule-based routing
* работа с VLESS / Reality

Слушает:

```
127.0.0.1:7890 (mixed-порт: HTTP + SOCKS5)
```

---

### Project ProxyN (Keenetic)

Связывает систему Keenetic с Mihomo:

* весь трафик с политики → в SOCKS5 `127.0.0.1:7890`
* точка входа для маршрутизации

Установщик находит или создаёт такой интерфейс сам: `Proxy0`, а если он занят
чужой конфигурацией (не совпали description `mihomo t2sN` и upstream) — первый
свободный `ProxyN`; чужой интерфейс при этом не изменяется.

---

### MagiTrickle

Решает:

> какой домен куда отправить

Пример:

* `youtube.com` → через VPN
* `local` → напрямую

Работает через DNS и policy routing. Чтобы MagiTrickle видел DNS клиентов, установщик
включает перехват транзитного DNS (`dns-proxy intercept enable`): классические
(port-53) запросы, адресованные напрямую внешним резолверам, перенаправляются
в DNS-прокси роутера. DoH/DoT это не затрагивает.

---

### bypass_wa (iptables)

Решает:

> как не убить голосовую связь

* маркирует UDP-трафик
* отправляет его в отдельную policy → проектный ProxyN → Mihomo
* альтернатива: ручной permit на VPN-интерфейс — тогда мимо Mihomo

---

### S00ubifs

Решает:

> как не убить флешку

* переносит `/opt/tmp`, `/opt/var/log` и `/opt/var/run` в RAM
* убирает постоянные записи на диск

---

### Watchdog

Решает:

> что делать, когда всё сломалось

Проверяет (по порядку):

1. есть ли интернет (WAN; двухступенчато: обычные цели → whitelist)
2. принимает ли порт Mihomo соединения (7890)
3. работает ли сквозной туннель SOCKS5h

Если WAN есть, а порт/туннель не работают:

```
→ рестарт Mihomo (не чаще раза в 300 секунд)
```

---

## Почему не "просто VPN на роутере"

Стандартный сценарий:

```
LAN → VPN → Интернет
```

Проблемы:

* нет гибкой маршрутизации
* всё идёт через VPN
* VoIP страдает
* при падении VPN всё ломается

---

## Почему не "всё через Mihomo"

Пробовали. Не работает стабильно.

Проблемы:

* UDP (VoIP)
* задержки
* нестабильные звонки

---

## Почему именно такая схема

Потому что она:

* переживает падения прокси
* не ломает голос
* масштабируется (20+ роутеров)
* не убивает флешку

---

## Что происходит при сбое

### Сценарий 1: Mihomo умер

```
watchdog → port check fail → restart
```

---

### Сценарий 2: недоступен upstream через Mihomo

```
tunnel check (GET через SOCKS5h) → fail → restart
```

(если upstream лежит — рестарт не поможет, но чинит подвисания; рестарт
выполняется только при подтверждённом WAN и не чаще раза в 300 секунд —
порт `7890` проверяется отдельным шагом)

---

### Сценарий 3: интернет пропал

```
WAN check → fail → ничего не делаем
```

👉 важно:

> не рестартить Mihomo, если проблема не в нём

---

## Сценарий "всё сломалось"

Что делать:

1.

```bash
/opt/etc/init.d/S99mihomo status
```

2.

```bash
cat /opt/var/log/mihomo_watchdog.log
```

3.

```bash
curl -x socks5://127.0.0.1:7890 https://ipinfo.io
```

Это не «VPN на роутере».

Это:

> **система маршрутизации + самовосстановление + обход проблем сети**
