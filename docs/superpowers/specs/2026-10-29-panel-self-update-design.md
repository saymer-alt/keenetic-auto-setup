# Ручное обновление KAS Control Center — проект #273

Статус: согласован владельцем 29.10.2026; реализация подготовлена локально.
Публикация, CI и полный firmware/service-lab сценарий ещё не выполнены.
Основание: #273, рабочая test15 на KN-1010 и исправления #278.
База исходников: `fe9db3a4066f1543baa82d11868fc60317682c0c`.

## Зачем и что уже известно

Сейчас обновление панели требует скачивания IPK, проверки SHA256, SSH/opkg и
отдельного запуска службы. Пользователь запросил эти действия из панели.
Это адаптер к Entware opkg, а не новый пакетный менеджер.

Проверка исходников показала:

- `packaging/preinst.sh` останавливает старую панель и ждёт drain до 60 секунд.
- `packaging/postinst.sh` намеренно не запускает службу после установки.
- Обработчики Mihomo/MT используют worker в процессе панели и `importRunning`.
  Такой шаблон нельзя копировать для самообновления: preinst остановит панель,
  а ожидание того же worker в shutdown создаст взаимное ожидание.
- Настройки, пароль, порт и policy доступа не входят в package payload.
- Runtime identity уже есть в `/api/components`; build metadata — в BUILD_INFO.
- Все опубликованные test-IPK — prerelease. `latest` не является каналом панели.
- Имена assets содержат `.test15`, тогда как CI-рецепт задаёт `~testN`.
  Версию нельзя восстанавливать из имени asset: нужен точный control.Version.

Польза: меньше ручных операций и ошибок при штатном обновлении. Стоимость:
отдельный worker, небольшая запись состояния, release manifest, lifecycle-тесты.
Фоновый опрос и постоянная история пакетов не нужны. Риск: панель может не
вернуться после частичной ошибки opkg; WAN не должен зависеть от этого процесса.

## Подходы и выбор

1. Сохранить SSH-инструкцию. Нет нового кода, но запрос обновления из Web не решён.
2. Менять бинарник самостоятельно. Короче, но нарушает владение opkg и игнорирует
   hooks/metadata. Не подходит существующей IPK-установке.
3. Отдельный worker с фиксированной командой opkg. Сохраняет стандартный lifecycle,
   переживает остановку панели и подтверждает запуск. Рекомендуемый вариант.

KeeneticOS обновляет собственные компоненты, а не этот сторонний Entware IPK.
Ожидание новой прошивки задачу не решает. Внешний пакетный Web UI или feed могли бы
управлять opkg, но добавляют сервис либо инфраструктуру и не решают сами по себе
самоостановку, подтверждение runtime и статус в существующей панели.

## Область

Обновляется только установленный через opkg `kas-control-center`.
Не меняются Mihomo, MT, watchdog, YAML, DNS, маршруты и сетевые политики.
Настройки/пароли/порт/ограничение доступа сохраняются побайтно, секреты не выводятся.
RU/EN; нейтральные названия сети, без предположения о домашнем использовании.
Только явные «Проверить» и «Обновить» с подтверждением. Автообновления нет.
Хранение предыдущих IPK и автоматический откат не входят в первый этап.
Test15 на реальном роутере в рамках разработки не переустанавливается.

## Канал и происхождение

Проектное решение: существующие immutable release assets плюс один небольшой
channel index в выделенном релизе `kas-web-channel-experimental`, без feed и
без смены `latest`. Index указывает ровно на один проверенный immutable релиз
и включает manifest этого кандидата. Публикация/изменение index — отдельное явное
действие после CI, не автоматический выбор любого нового PR-артефакта.
Manifest содержит schema, channel, точную control.Version, полный source SHA,
architecture, asset name/size/SHA256, unpacked size и binary SHA256.
Experimental допускает только prerelease `kas-web-ipk-*`; stable — отдельный
index/tag `kas-web-channel-stable` и формат кандидата `kas-web-v*`, non-prerelease.
Канал фиксируется в compiled identity и BUILD_INFO; неизвестный канал не выводится
из имени версии. Переключения на stable/между каналами в первом этапе нет.

Метаданные запрашиваются только по кнопке: максимум 3 GET (channel release,
index asset, candidate release), общий срок 30 секунд, каждый JSON до 1 MiB.
Список всех releases не сканируется. Rate limit/неполный ответ дают UNKNOWN.
Manifest без дубликатов ключей/ABI и с ограниченными числовыми полями.
Неопубликованные/draft/неполные релизы исключаются. Старые релизы без manifest
не устанавливаются этим механизмом; отсутствие пригодного релиза явно сообщается.
Порядок API, дата публикации, SHA и номер test не являются сравнением версий.
Сравнение — только фиксированным `opkg compare-versions`, с проверкой exit semantics
на настоящем Entware. При неоднозначности/ошибке не предлагать установку.

URL формируется сервером из проверенных tag/name своего репозитория. Браузер не
передаёт URL, команду или путь. TLS/CA обязательны. Redirects для asset допускаются
только HTTPS на наблюдавшиеся GitHub release asset hosts, с ограничением числа
переходов; userinfo, смена схемы, локальные/IP назначения запрещены. Проверки
сертификата не отключаются. SHA256 обеспечивает целостность относительно доверенных
метаданных GitHub, но не является независимой подписью автора.

## Предварительная проверка и место

Установленная версия берётся из защищённого opkg control/status, запущенная —
из compiled identity. При расхождении показать обе и запретить новую установку
до устранения неопределённости; не запускать чужую/ручную установку.

До скачивания проверить место для compressed asset; до остановки службы — место
для полного пика: IPK, worker, проверки/распаковки, opkg staging и запаса на metadata.
Проверять фактические файловые системы `/opt`, staging и opkg temp; если совпадают,
суммировать потребность. Начальный консервативный предел payload — 32 MiB, IPK —
16 MiB; конкретный резерв opkg определить тестом реальной установки и отразить
константой с обоснованием. Пока резерв не доказан, installation gate закрыт.
Использовать Statfs/Go API, не GNU `stat -c`; отрицательные/переполненные значения
и неизвестное место дают отказ. Проверить inode availability, если ФС её сообщает.

Скачанный IPK сверить по размеру и SHA256; потоково разобрать gzip-tar контейнер
проекта с лимитами. Не исполнять hooks для проверки и не распаковывать произвольные
пути. Допускается только ожидаемый package payload; reject links/devices,
path traversal, дубликаты и лишние/неизвестные файлы. control: exact package,
Version, ABI, Source; BUILD_INFO и ELF: source/version/ABI/binary digest.
Depends/Pre-Depends/Conflicts/Replaces/Provides в текущем рецепте отсутствуют;
кандидат с такими полями отклоняется до opkg, чтобы не изменить другие пакеты.
Только затем запускать штатный opkg. Несогласованность manifest/IPK — отказ.

## Worker и исключительность

HTTP-подтверждение использует существующие Origin/auth/JSON guards. Под mutex
занимается исключительный слот; конкурирующие Doctor, import, filter, settings,
access и component updates отказывают BUSY. Затем создаётся root-owned 0700
рабочий каталог и 0600 job/state, атомарные записи с синхронизацией.
Persistent gate и одна запись результата: `/opt/etc/kas-control-center-update/`
(0700, root). Не использовать tmpfs `/opt/var/run` для защиты после reboot.
Runner/IPK хранятся отдельно в приватном временном staging; state пишет только
смены фазы, а не каждую секунду опроса.

Отдельный process group/session worker запускается из проверенной приватной копии
текущего исполняемого файла; не зависит от HTTP context и удерживаемых pipe браузера.
Копия — временный runner, не сохранённая предыдущая версия для отката.
Worker получает только путь фиксированного private job, проверяет его содержимое
и ownership. Parent PID и file descriptors не служат единственной авторизацией.

После принятия job панель запрещает новые мутации, но её shutdown НЕ ждёт этого
worker как importRunning. Все текущие операции завершены до выдачи job. Отдельный
межпроцессный marker блокирует мутации и в новой панели до завершения проверки.
Init должен уметь запустить панель в recovery/read-only состоянии при таком marker.

Worker повторно проверяет установленную версию и неизменность кандидата, запускает
только `opkg install <private validated IPK>`, без force и без upgrade-all.
Нельзя удалять lock opkg или завершать посторонний opkg; отказ/занятость сообщаются.
Настоящий opkg и его hooks владеют install-lock; отдельное «проверили файл lock»
не считается защитой от гонки. Инсталляцию нельзя timeout-kill после начала мутации.

После opkg success worker явно вызывает фиксированный init start. Подтверждает
новый процесс через PID/proc executable, opkg metadata и свежую runtime identity
по локальному API с теми же auth-настройками, без утечки пароля. Если API auth
нельзя проверить без секрета, использовать отдельный закрытый runtime receipt от
нового процесса, привязанный к случайному operation nonce, boot/process identity
и полному source SHA. Проектное предпочтение — private receipt вместо обхода auth.

Worker держит gate до проверки receipt; затем atomic terminal state и снятие gate.
Новый процесс публикует receipt только после успешного bind/listener setup.
Нулевой exit opkg/ответ до перезапуска недостаточны для OK.
Состояние содержит phase, operation ID, target version/SHA, timestamps и error code;
никаких произвольных stdout, URL подписок и секретов.

## Ошибки и восстановление

Download/checksum/ABI/место/metadata failures до opkg оставляют старую службу активной.
При неуспешном opkg нельзя предполагать, что payload остался прежним. Сначала
проверить согласованность файлов и package metadata; запускать только подтверждённый
целостный установленный payload. Иначе сохранить FAIL и инструкцию ручного recovery.
Никаких обещаний атомарности/rollback от самого opkg.

После install success и start failure результат FAIL/START_FAILED, не OK и не откат.
Закрытие браузера не отменяет job. UI хранит только operation ID для переподключения,
не пароли; опрашивает состояние, затем новую runtime identity. Private receipt
доказывает запуск worker; окончательное UI-подтверждение требует свежего ответа
`/api/components` через обычную авторизацию браузера с точным target version/SHA.
Старый success ID
не выдаётся за новую операцию. Лимит ожидания UI не убивает worker.
При пропаже питания/worker marker не удаляется автоматически по таймеру: состояние
UNKNOWN/RECOVERY_REQUIRED, операции остаются закрыты до проверенного recovery.
Фиксированный CLI `kas-control-center -recover-panel-update` проверяет отсутствие
worker по PID/starttime/exe и отсутствие активного opkg, целостность установленного
payload/opkg metadata и запускает только проверенный payload. После receipt он
снимает gate; при любой неопределённости не удаляет marker и выдаёт код ошибки.
Команда не устанавливает произвольные пакеты и не реализует откат.
Успешная/безопасно отказавшая job удаляет временные IPK/runner, оставляя одну
малую запись результата. Неограниченная история не создаётся.

## Проверка до установки на роутер

1. Разбор release/manifest/IPK: wrong channel/ABI, malformed/duplicate data,
   SHA/size mismatch, link/path traversal, compression bomb, altered hooks/payload.
2. Реальный Entware compare-versions: test9/15/16, `~` против `.`, same/downgrade;
   установку никогда не авторизует лексикографический compare.
3. Недостаток места на общей/разной ФС, inode limits, переполнения до stop/opkg.
4. Настоящий opkg install→upgrade в offline-root с сохранением user settings.
5. Disposable service VM: настоящий old daemon, worker, preinst drain, новый daemon,
   private receipt, отключение браузера, второй запрос, занятый opkg, start failure.
   Доказать отсутствие взаимного ожидания и повторной установки.
6. Chromium RU/EN, переподключение, устаревший operation ID, недоступный новый listener.
7. Ported firmware emulator на доступном ABI: успешный Web update и проверка настроек.
   Отдельно фиксировать host fixtures и настоящую firmware, не смешивать результаты.
8. После CI — отдельная ручная приёмка тестового устройства владельцем. Без неё
   не утверждать аппаратную поддержку или продвигать main/stable/latest.

Test15 ещё не содержит эту функцию. Для аппаратной проверки после CI потребуется
один обычный upgrade IPK до версии с worker/UI, затем переход на следующую версию
через Web. Это будущий bootstrap функции, не переустановка test15 сейчас.

## Порядок реализации и остановки

Сначала metadata/check-only и release manifest generator, затем archive preflight,
потом независимый worker/state/gate, затем Web flow и живой service-lab. Это один
этап #273 с последовательными проверяемыми частями, не несколько новых подсистем.
Изменения #278 включаются как база следующей сборки, опубликованная test15 неизменна.

STOP: невозможно доказать независимость worker, безопасное завершение hooks,
пиковое место, ownership или runtime identity. После двух безрезультатных попыток
одной проблемы — отчёт владельцу вместо расширения области. До устранения этих
пунктов остаётся SSH-инструкция; опасную кнопку «Обновить» не публиковать.

Документ фиксирует предложения исполнителя (manifest, receipt и механизм gate),
а не выдаёт их за ранее утверждённые решения владельца. Владелец подтвердил реализацию этой схемы 29.10.2026.
Владелец отдельно разрешил commit/push и draft PR для CI.
Публикация релиза и изменение реального роутера не разрешены.
