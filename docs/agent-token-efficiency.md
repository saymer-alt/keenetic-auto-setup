# Agent token efficiency — практические правила (issue #420)

**Решение владельца 05.11.2026 (issue #420):** лёгкие правила экономии агентной работы, работающие в ZCode, Codex Web, Kimi и других системах без установки [microsoft/TokenEconomizer](https://github.com/microsoft/TokenEconomizer). Это методика в документе, **не** плагин: TokenEconomizer не устанавливается, hooks и настройки Codex/ZCode не меняются. Поддержка TokenEconomizer в Codex Web не подтверждена; его бенчмарки (SWE-Bench и др.) — результаты Microsoft, **не** этого проекта и не этого правила.

## 1. Loop Guard

После **двух безрезультатных одинаковых попыток** при неизменном состоянии (тот же SHA, та же команда, та же ошибка) — не делать третью «такую же»: сменить гипотезу, собрать новую диагностику или пометить задачу/этап `BLOCKED` и идти дальше по безопасной части. Исключения (не считаются «одинаковой попыткой»): легитимный retry инфраструктурного сбоя (сетевой таймаут, rerun failed job после документированного flake), ожидание длительного CI, повтор после реально изменённого кода/состояния. Правило про мышление, а не про скорость: повторы без новой информации — самая дешёвая для обнаружения и самая дорогая при исполнении трата.

*Подтверждённый случай:* kas-update Stage 2B (issue #390) — три нативных QEMU-прогона (41905387849 → 41916892031 → 41969660793, ~15–25 мин каждый) при неизменном kas_ref `57e5d67`; оба первых FAIL были в harness (stderr-only ассерт, teardown SSH-holder), а не в продукте. Дешёвый host-прогон новых ассертов до dispatch сэкономил бы два полных прогона.

## 2. Evidence Reuse

Результат проверки (CI, тест, отчёт) переиспользуется только при совпадении **SHA, кода, окружения и области тестирования**. Старый зелёный CI не подтверждает новый SHA; локальный PASS не подтверждает GitHub CI на финальном SHA; эмулятор не подтверждает железо. Перед повторным исследованием проблемы — прочитать уже merged состояние (PR/issues): часть работы могла быть сделана.

*Подтверждённые случаи:* link-generators #286 — локальные PASS при красном GitHub CI на итоговом SHA `3b032d5` (UX18/UX54, provenance): цикл ревью потрачен на уже опровергнутое состояние. KAS #320 — часть исправлений уже была в merged PR #325; полезной дельтой оказались отрицательные PTY-тесты #365, а не переписывание импортёра.

## 3. Environment Facts

Проверенные особенности среды фиксируются в формате **факт + источник + дата + условия применимости**; гипотезы сохраняются как гипотезы, секреты — никогда. Факт без границы применимости («всегда так») запрещён: среда меняется. Перед новой отладкой «странного» поведения — сначала проверить накопленные факты, потом гипотезы.

*Подтверждённый случай:* Windows-клоны KAS с CRLF дают ложные падения чистого `main` (cp1251 в maintenance/lifecycle-регрессиях, `contracts.sh` S00ubifs, CRLF-фикстура doctor-тестов, `updates_transaction_test` «canonical lock seam moved» на подсчёте `\nacquire_lock\n`). Каждый такой случай до фиксации факта стоил циклов отладки «продукта», который не сломан; авторитетный гейт — Linux CI.

## 4. Tool Calls

Запросы к инструментам — адресные: точный файл/строка/SHA/гейт, а не перечитывание всего репозитория и полных журналов без новой информационной потребности. Дешёвая локальная проверка (grep по тестам на изменяемый контракт, `sh -n`, юнит-тест пакета) выполняется **до** дорогого dispatch (нативные прогоны, полный CI-матрикс). Если действие может упасть на ожидаемом контракте (переименован маркер, удалён токен), проверить потребителей заранее.

*Подтверждённый случай:* KAS Web PR #423 — полный матрикс из 17 job'ов (включая 3 нативных QEMU) прогнался до первого же честного browser-FAIL, причиной которого был пин удаляемого сырого токена в `panel-browser-check.cjs`; grep тестов по убираемому токену до push нашёл бы это бесплатно.

## 5. Build Economy

Порядок: локальный целевой тест → обязательные тяжёлые проверки один раз в подходящей точке (финальный SHA, перед review/merge) → не ослаблять релизные gates и не добавлять «быстрые обходы». Тяжёлая проверка, запущенная до готовности кода, повторяется платно; попытка сэкономить на обязательном гейте стоит дороже отдельного GO-цикла.

*Подтверждённый случай:* тот же PR #423 — обновление browser-чека стоило одного повторного прогона матрицы; после инфра-сбоя GitHub (`commit_refs_rules` + зависшая синхронизация PR-головы ~10 мин) лечение close+reopen оказалось дешевле и надёжнее пустых коммитов-«пинков».

## 6. Reports

Отчёт — навигация к доказательствам: SHA, результат по гейтам, evidence (ссылки на run/артефакты), blockers, следующий шаг. Без повторения длинных логов: лог цитируется фрагментом только если он сам по себе evidence (диагностика из gates.json, сообщение об ошибке). Формат статусов — раздельно `planned / implemented / CI verified / emulator verified / hardware verified / not verified` (уже закреплено стандартом; здесь повторено как напоминание для кратких отчётов).

## Матрица измерения (шаблон)

Заполняется на **сопоставимых задачах и моделях**; недоступная метрика — `NOT_AVAILABLE`, не выдумывается. Результаты TokenEconomizer сюда не переносить.

| Метрика | Значение | Как получить |
|---|---|---|
| input / output / cache tokens | `NOT_AVAILABLE` (если платформа не показывает) | статистика платформы |
| стоимость (бонусный лимит / деньги) | фактическая или расчётная | аккаунт платформы |
| tool calls всего | счёт сессии | журнал агента |
| повторные безрезультатные вызовы | счёт по правилу §1 | журнал агента |
| wall-clock time | фактический | таймер сессии/CI |
| обязательные тесты пройдены | число/список гейтов | CI/логи |
| проверенный результат достигнут | да/нет + что считается | Definition of Done задания |
| замечания ревью / регрессии | список | PR review, CI после merge |

Сравнение A/B (плагин vs без) имеет смысл только как отдельный эксперимент из Этапа 2 issue #420 — с owner GO, на тестовой рабочей копии, `toolprune=propose`, `microskills=off`, с проверкой restore/uninstall. До такого эксперимента эффективность этих правил оценивается по матрице выше без утверждений о процентах.

## 7. Сессионный бюджет для ZCode / API (пилот, 06.11.2026)

Цель — **больше проверенного рабочего результата на токен**, а не «истраченные 300M за ночь». Это ориентиры для планирования, **не доказанная экономия** и не ограничение безопасности/обязательных проверок. Если платформа не показывает токены по задачам, писать `NOT_AVAILABLE`, не подставлять оценки вместо измерений. Бонусные токены и денежная стоимость API — разные метрики; кэш может уменьшить счёт, но не обязательно расход бонусного лимита.

### Перед длинной сессией

1. Выбрать не более **трёх основных направлений**, предпочитая завершение уже открытых PR новым исследованиям. Сверить текущие HEAD, Draft/merge/CI/status и реальные блокеры **до** кодирования; пересмотреть очередь, если работа уже завершена другим агентом.
2. Для каждого направления записать **один измеримый следующий результат**, минимальный затрагиваемый набор файлов, обязательные проверки, предел полномочий и условие STOP. При неопределённости — короткий read-only triage вместо многодневной реализации.
3. Держать компактный handoff: `issue/PR | base/head SHA | доказанный PASS/FAIL/NOT_TESTED | blocker | next exact action`. Передавать ссылку и SHA, а не повторно вставлять весь лог или целое дерево исходников.
4. Короткий checkpoint после завершения направления и **перед каждым тяжёлым QEMU/полным CI**: что изменилось с предыдущего прогона, какие дешёвые тесты прошли, зачем нужен повтор. Не перезапускать дорогостоящие матрицы только ради траты квоты.

### Пробные мягкие лимиты на одну задачу

| Тип работы | Стартовый ориентир, токенов | На границе бюджета |
|---|---:|---|
| Небольшой баг + узкий тест | 1–3 млн | Зафиксировать diff, проверить минимальную регрессию |
| Ревью подготовленного PR | 1–5 млн | Сформулировать конкретный GO / NO-GO / blocker с SHA |
| Средняя правка | 5–10 млн | Разделить необязательные улучшения и проверенный fix |
| Сложная интеграция | 10–30 млн | Сохранить работающий slice, пересмотреть зависимости |
| QEMU / Entware расследование | 20–50 млн | Зафиксировать узкий диагностический факт и STOP, если нет новой гипотезы |

Это **не квоты качества**, не SLA и не разрешение прекращать критическую транзакцию посередине. При выходе за ориентир агент отмечает причину и новый план; при отсутствии телеметрии ориентиры остаются только бюджетом планирования. Настраивать их по фактическим измерениям не менее чем нескольких сопоставимых задач, **не** по одному ночному прогону.

### На выходе из каждого блока

Короткая строка учёта: `task | token input/output/cache (или NOT_AVAILABLE) | calls | futile repeats | final SHA | tested gates | verified deliverable | remaining blocker`. Для API отдельно фиксировать наблюдаемую плату по биллингу, для бесплатной сессии — списание бонусной квоты; **не переводить** одно в другое без тарифов и точного распределения токенов.

Приоритет следующего блока: `готовый PR с незакрытым gate → воспроизводимый пользовательский дефект → блокирующая интеграция → исследование`. Если безопасные задачи закончились раньше истечения бесплатного окна, **останавливаться**, а не выдумывать дополнительные исследования. Никакого автоматического merge/stable/release/FIELD без owner GO. Правила §1–6 и обязательные KAS gates выше любого ориентира по расходу.
