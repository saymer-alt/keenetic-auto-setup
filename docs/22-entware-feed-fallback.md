# OPKG / Entware не скачивает пакеты: диагностика и китайское зеркало NJU

Инструкция для Keenetic/Netcraze с уже установленным **Entware**. Подходит, если `opkg update` выдаёт ошибки, не может получить `Packages.gz` или зависает при подключении к `bin.entware.net`.

**Коротко:** если обычный доступ к feed ограничен, сначала можно попробовать уже действующий VPN (на самом роутере либо на вышестоящем шлюзе). Если это не помогло, есть альтернативное зеркало Entware университета Нанкина (NJU): [`mirrors.nju.edu.cn/entware/`](https://mirrors.nju.edu.cn/entware/). Это **зеркало пакетов**, а не «китайская версия OPKG». Переключение — только вручную, с резервной копией и возможностью отката. KAS сам не меняет источники пакетов.

> **Важно:** недоступность `bin.entware.net` не доказывает именно блокировку провайдером: возможны DNS, маршрут, временный сбой сервера, проблемы HTTP/TLS или неверная архитектура. Подмена зеркала может не помочь. Зеркало стороннее: проверяйте адрес, актуальность и доверие к источнику. Не отключайте проверку сертификатов/подписей ради установки.

## 1. Проверьте, что именно не работает

Начните с обычной команды:

```sh
opkg update
```

Посмотрите, какие URL действительно записаны на **этом роутере**:

```sh
echo "=== /opt/etc/opkg.conf ==="
grep -n '^[[:space:]]*src/gz[[:space:]]' /opt/etc/opkg.conf 2>/dev/null

echo "=== /opt/etc/opkg/*.conf ==="
for f in /opt/etc/opkg/*.conf; do
    [ -f "$f" ] || continue
    echo "--- $f"
    grep -n '^[[:space:]]*src/gz[[:space:]]' "$f"
done
```

В Keenetic WebCLI для **просмотра** главного файла также встречается команда `exec /opt/bin/cat /opt/etc/opkg.conf`. Дальнейшие операции с резервной копией и заменой удобнее и надёжнее выполнять через SSH.

Проверяйте **исходный URL из своего `src/gz`**, а не чужую архитектуру. Например, для `aarch64-k3.10`:

```sh
curl -4 -I -fSsL --connect-timeout 5 --max-time 15 \
  http://bin.entware.net/aarch64-k3.10/Packages.gz

curl -4 -I -fSsL --connect-timeout 5 --max-time 15 \
  https://mirrors.nju.edu.cn/entware/aarch64-k3.10/Packages.gz
```

Эти проверки используют `curl`, **если он уже установлен**; если `curl` ещё нет и `opkg` не работает, не пытайтесь «для проверки» установить его из недоступного репозитория. HTTP HEAD показывает только достижимость по данному маршруту и не гарантирует успешный `opkg update`. Для MIPS/других CPU замените **весь архитектурный путь** на тот, который уже используется в исходном feed.

## 2. Сначала попробуйте подключение через уже работающий VPN

Если официальный Entware feed не открывается по прямому пути, **не обязательно сразу менять `opkg.conf`**. Иногда достаточно, чтобы соединения к репозиторию проходили через **уже работающий VPN** с доступом к этому ресурсу:

- **VPN на том же Keenetic.** Если VPN-клиент уже настроен и работает, можно временно выбрать VPN как предпочтительный интернет-выход или соответствующую политику маршрутизации. Но важно: **через VPN должны идти запросы самого роутера** (в том числе `opkg update`, DNS и HTTP/HTTPS к репозиторию), а не только трафик LAN-клиентов или отдельных сайтов. Одного статуса «VPN подключён» недостаточно.
- **Через другой роутер.** Подключите проверяемый Keenetic WAN-портом к LAN второго роутера, который уже выводит нужный трафик через VPN; тогда второй роутер может выступать интернет-шлюзом для первого. Проверьте, что и DNS, и соединения к Entware идут по ожидаемому пути. Это альтернативный временный способ, когда на первом устройстве ещё нет работающего VPN.

После проверки маршрута повторите:

```sh
opkg update
```

Если официальный feed заработал — **ничего переписывать в OPKG не надо**: сохраняйте исходные адреса и ставьте пакеты через доверенный основной источник.

> **Осторожно с приоритетами соединений:** назначение VPN основным выходом способно затронуть весь интернет на роутере и устройствах за ним, а также удалённый доступ. Изменяйте приоритеты только при наличии доступа для отката, сохраните предыдущую схему и верните её после проверки. Маршрут через VPN не гарантирует доступности сайта и не исправляет недостоверные подписи либо повреждённые индексы. Не публикуем универсальные команды по смене default route или DNS: они зависят от конкретной конфигурации Keenetic.

Если VPN не помогает или его нет — используйте диагностику и проверенное зеркало ниже.

## 3. Когда имеет смысл NJU

[Каталог NJU для aarch64-k3.10](https://mirrors.nju.edu.cn/entware/aarch64-k3.10/) содержит `Packages.gz` и подкаталог `keenetic/` (проверка каталога: 18.10.2026). Сам индекс в корне каталога имел дату **01.09.2026**, а `keenetic/` обновлялся отдельно: это показывает, почему наличие файла ещё не гарантирует одинаковую свежесть всех веток.

Перед переключением убедитесь, что:
- исходный `bin.entware.net` действительно недоступен или ненадёжен, а нужный `Packages.gz` NJU доступен из вашей сети;
- название архитектуры и все суффиксы URL сохраняются без изменений, например `aarch64-k3.10/keenetic/` остаётся `aarch64-k3.10/keenetic/`;
- в настройках есть именно официальный Entware feed; сторонние `MagiTrickle` и другие пользовательские репозитории **не изменяем**;
- OPKG умеет получать индекс по новому HTTPS URL и необходимые проверки подлинности остаются включены.

## 4. Ручное переключение с резервной копией

**Это пример только для случая, когда официальные записи `src/gz` с `http://bin.entware.net/` находятся в `/opt/etc/opkg.conf`.** Если они в другом файле либо указан другой URL — не запускайте замену вслепую; сначала изучите соответствующий feed-файл.

Проверьте старые строки командой из раздела 1. Затем **в SSH**:

```sh
OPKG_FILE=/opt/etc/opkg.conf
OPKG_BACKUP="/opt/etc/opkg.conf.bak.$(date +%Y%m%d-%H%M%S)"

cp -p "$OPKG_FILE" "$OPKG_BACKUP" &&
sed -i '/^[[:space:]]*src\/gz[[:space:]]/s#http://bin\.entware\.net/#https://mirrors.nju.edu.cn/entware/#g' "$OPKG_FILE" &&
echo "Backup: $OPKG_BACKUP"
```

Эта команда меняет **только строки `src/gz` в указанном файле** и только точный префикс официального Entware. Архитектура и подкаталоги остаются прежними; другие файлы и репозитории она не редактирует.

Проверьте результат перед установкой любых пакетов:

```sh
grep -n '^[[:space:]]*src/gz[[:space:]]' /opt/etc/opkg.conf
opkg update
```

Если `opkg update` сообщает ошибки хотя бы одного обязательного источника, HTTPS не поддерживается конкретной сборкой OPKG, источник/архитектура не совпадает либо проверка подлинности не проходит — **не используйте это зеркало для установки пакетов**, верните предыдущую конфигурацию. Не добавляйте `--force-checksum` или иные флаги обхода проверки подлинности.

### Откат

В той же SSH-сессии значение `$OPKG_BACKUP` сохранено после команды выше. Для возврата:

```sh
cp -p "$OPKG_BACKUP" "$OPKG_FILE"
grep -n '^[[:space:]]*src/gz[[:space:]]' "$OPKG_FILE"
opkg update
```

Если SSH-сессия уже закрыта, найдите созданную копию в `/opt/etc/opkg.conf.bak.*` и явно подставьте **её полный путь** вместо `"$OPKG_BACKUP"`. Не заменяйте файл первой попавшейся копией без просмотра даты и содержания.

Исторически встречалась короткая команда глобальной замены `sed -i 's,http://bin.entware.net/,http://mirrors.nju.edu.cn/entware/,g' /opt/etc/opkg.conf`. Она использовала **HTTP**, не делала backup и могла менять не только активные `src/gz` — поэтому для публичной инструкции выше выбран более ограниченный и обратимый вариант.

## 5. Если не открывается GitHub Raw, а OPKG работает

Это **другая проблема**. Китайское зеркало NJU не заменяет `raw.githubusercontent.com` и не исправляет загрузку `setup.sh`.

Обычная установка KAS:

```sh
opkg update && opkg install curl && \
curl -fSsL https://raw.githubusercontent.com/saymer-alt/keenetic-auto-setup/stable/setup.sh | sh
```

Если зависание случилось **до появления первого вывода установщика**, попробуйте штатный совместимый TLS-вариант:

```sh
curl -4 -fSsL --connect-timeout 5 --max-time 20 --curves X25519 \
  https://raw.githubusercontent.com/saymer-alt/keenetic-auto-setup/stable/setup.sh | sh
```

После запуска `setup.sh` у KAS есть отдельная цепочка резервных способов получения дочерних скриптов. Она **не спасает первый download `setup.sh`**, если тот вообще не скачался. При полной недоступности GitHub используйте [документированный offline/SCP-сценарий](03-install.md), а не отключение TLS-проверки. Подробности: [мастер установки](14-setup.md), [устранение неполадок](08-troubleshooting.md).

## 6. Чего делать не стоит

- Не менять feed URL автоматически на всех роутерах и архитектурах, не подставлять всем `aarch64-k3.10`.
- Не переписывать сторонние MagiTrickle-репозитории вместе с Entware.
- Не переустанавливать Entware и не переключать накопитель OPKG «Не выбран» → назад только из-за сетевой ошибки: можно размонтировать `/opt` и остановить работающие службы.
- Не отключать TLS, проверку подписей/пакетов и не проводить массовый `opkg upgrade` ради диагностики.
- Не путать сетевой сбой OPKG с проблемами Mihomo/Netfilter; сначала сохраните текст ошибки.
