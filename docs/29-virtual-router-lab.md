# Виртуальная лаборатория Keenetic — первая итерация (22.10.2026)

Статус: **эксперимент / draft, без изменений production**. Цель — убрать ручные многошаговые проверки после каждого изменения KAS, KeenWhite/WDTT и KNVR, не подменяя аппаратные результаты имитацией.

## Источник и границы

- Upstream: [stavultras/router-emulator](https://github.com/stavultras/router-emulator), GPL-2.0, версия **v3.8**. Исходный код QEMU не копируем в KAS, сохраняем происхождение и используем опубликованные пакеты.
- Самостоятельный fork эмулятора: **ещё не создан**. Требуется нативная операция **Fork** через GitHub под `saymer-alt/router-emulator` (интеграция GitHub в этом сеансе не предоставляет создание форка).
- Аппаратный пресет KN-1012 есть, однако **загрузка KeeneticOS на KN-1012 не подтверждена**. Для него upstream прямо требует дампы своего устройства; пресет не эквивалентен рабочей KeeneticOS.
- Временно CI запускает **OpenWrt на Cudy WR3000P v1 / MT7981**, а не KeeneticOS. Зелёный результат подтверждает только загрузку OpenWrt, доступность LuCI и восстановление после эмулированного сброса, **не работоспособность KAS, ndmc, Proxy Client, Entware или WDTT**.

## Первый исполняемый прототип

Файл: `.github/workflows/router-emulator-lab.yml`.

1. Ручной `workflow_dispatch`, отдельный от основных KAS CI, без расписания и изменений рабочих релизов.
2. Скачивает релиз upstream v3.8 для Linux x86_64 и отдельный архив пресетов, проверяет **пинованные SHA-256** из релиза.
3. Создаёт NAND из официальных OpenWrt 25.12.5 через upstream `tools/prepare-nand.sh` (проверка официальных `sha256sums` находится внутри upstream инструмента).
4. Headless QEMU: проверяет BootROM/BL2, U-Boot, ядро и приглашение OpenWrt с `tests/quick.py`.
5. Второй headless прогон в `-w offline -l user`: проверяет страницу LuCI через 127.0.0.1:8080, даёт `system_reset` через QEMU monitor, ждёт второго BL2 и повторной доступности LuCI.
6. Сохраняет **только логи и HTML контрольной страницы**, без флеш-образов, дампов, ключей и настроек реальных устройств. Тайм-аут workflow — 30 минут; это верхний предел CI, не время ручного тестирования.

Workflow *не протестирован в GitHub Actions*: до первой успешной проверки его результаты и время исполнения неизвестны. После утверждения PR запустить вручную и сохранить ссылку на run/логи в задаче.

## Следующий этап (после нативного fork)

### E0 — поддержка эмулятора

- Закрепить upstream commit/tag и добавить автоматическую проверку новых upstream releases, не вливать изменения QEMU автоматически.
- В форке хранить отдельно upstream QEMU и наши сценарии `ci/keenetic/`; CI KAS и KeenWhite смогут вызывать общий инструмент по закреплённому коммиту.
- Провести сравнение моделей KN-1012, KN-3811/3812, NC-1812 и KN-1010 **по реально доступной аппаратной эмуляции**, не считать совпадение SoC гарантией поддержки устройства.

### E1 — реальная KeeneticOS (gate)

- Проверить законность/техническую возможность локального дампа с **запасного** устройства, провести редактирование секретов и идентификаторов *до* потенциальной передачи образов. По умолчанию **никаких дампов в публичном GitHub, Actions artifacts, issue, логах или сторонних хранилищах**.
- Образы должны оставаться локальными у владельца или на собственном изолированном self-hosted runner после отдельного решения и аудита секретов.
- Gate `ndmc -c 'show version'`, `opkg --version`, `/opt`, сетевые порты, reset, startup, USB, RAM, mount, swap, интерфейсы. При отсутствии KeeneticOS — **SKIP / BLOCKED**, а не PASS.

### E2 — тесты продуктов (только E1 PASS)

| Проект | Сценарий | Результат |
|---|---|---|
| KAS | чистая установка, повтор, update, rollback, uninstall | PASS/FAIL; полное отсутствие побочных изменений |
| KeenWhite/WDTT | offline preflight, установка, DNS, ограничения RAM и workers, fail-close, reboot | PASS/FAIL без утечки трафика |
| KNVR | подмена виртуального USB-накопителя, start/stop, сохранность файлов | PASS/FAIL только в пределах эмуляции |
| Mihomo | конфиг-тест и process supervision | PASS/FAIL; транспорт E2E на реальном канале отдельно |

### E3 — аппаратная финальная валидация

- Ночные/регулярные CI: только после E1/E2 PASS. Ветка разработчика получает автоматический отчёт + лог; релиз не одобряется по одним mock/OpenWrt тестам.
- Разделить короткие offline mock, QEMU boot, KeeneticOS integration, физическое железо и live network E2E. Каждый тест помечает **тип доказательства**, model/hw_id, firmware, arch, внутренний/внешний /opt, zRAM/SWAP, commit.
- Для деструктивных операций требуются одноразовый flash overlay/snapshot, изоляция трафика, rollback и лимиты времени. Никакого физического WAN bridge, `-l nic`, теста на домашнем Titan 4210, изменения VPS или доступа к production.

## Критерий выпуска рабочего автотестирования

Первый milestone: **один нажатый Run workflow → детерминированный результат boot + reset → логи без секретов**. Следующий milestone: подтверждённая KeeneticOS на подходящем эмуляторе → автоматический clean-install/upgrade/uninstall KAS. Последний этап — физическая сертификация без прежних ручных 30-минутных прогонов на каждое изменение.
