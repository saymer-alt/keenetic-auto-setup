# Sniffer Mihomo: откуда ядро берёт домен без DNS

Sniffer — механизм Mihomo, который пытается восстановить доменное имя из уже пришедшего соединения. Он **не является DNS**, не подменяет DNS-сервер и не «расшифровывает Интернет».

Практический смысл: соединение могло прийти в Mihomo уже как обращение к IP, но в данных протокола всё ещё может быть виден hostname. Если Mihomo его извлечёт, доменные rules (`DOMAIN`, `DOMAIN-SUFFIX`, `GEOSITE` и т. п.) получают дополнительный источник домена.

Официальный quick-config Mihomo показывает sniffer для HTTP, TLS и QUIC:
<https://wiki.metacubex.one/ru/example/conf/>.

---

## DNS и sniffer решают разные задачи

~~~text
DNS:     домен → IP
Sniffer: соединение/IP → попытка восстановить домен из протокола
~~~

DNS знает имя до соединения, если запрос проходил через известный Mihomo DNS/fake-ip контекст. Sniffer работает уже на входящем соединении. Поэтому механизмы дополняют друг друга, но не заменяют один другой.

---

## Минимальная структура

В актуальном официальном примере используется такая форма:

~~~yaml
sniffer:
  enable: true
  sniff:
    HTTP:
      ports: [80, 8080-8880]
      override-destination: true
    TLS:
      ports: [443, 8443]
    QUIC:
      ports: [443, 8443]
  skip-domain:
    - "Mijia Cloud"
    - "+.push.apple.com"
~~~

Это пример возможностей ядра, **не bootstrap-конфиг нашего проекта**.

---

## Что именно можно извлечь

### HTTP

В обычном HTTP hostname может быть доступен из HTTP-заголовков. Поэтому sniffer способен связать соединение с доменом даже если inbound изначально пришёл к IP.

### TLS

В TLS hostname может быть доступен из метаданных рукопожатия, если он действительно виден парсеру. Sniffer не расшифровывает защищённый payload.

### QUIC

Mihomo умеет включать отдельный QUIC sniffer на заданных портах. Результат зависит от того, содержит ли конкретное соединение доступные для распознавания данные о hostname.

Главное ограничение общее: **если протокол/соединение не раскрывает пригодный hostname, sniffer не может его выдумать**.

---

## `ports` — где вообще пытаться sniff

Список `ports` ограничивает, на каких destination-портах включается конкретный parser. На роутере это полезно и логически, и ресурсно: нет смысла пытаться разбирать каждым sniffer'ом весь трафик на всех портах.

Официальный пример использует типовые HTTP/TLS/QUIC диапазоны, но это не означает, что их надо копировать без понимания своей схемы.

---

## `override-destination`

В protocol-блоке может быть включён `override-destination: true`. Смысл: успешно извлечённый домен может использоваться как фактическое назначение для дальнейшей обработки вместо исходного IP-направления.

Это уже не просто «добавили метаданные для rules», поэтому опцию стоит включать осознанно. Если конкретный сервис плохо переносит такую подмену, его лучше исключить или не использовать override для этого parser'а.

---

## `skip-domain`

`skip-domain` задаёт домены, для которых результат sniffing не должен применяться. Это полезно для локальных/служебных имён, приложений с проблемным override и известных исключений конкретной сети.

В официальном примере есть `+.push.apple.com`; это пример upstream-конфига, а не универсальная обязательная строка проекта.

---

## Как sniffer связан с rules

Доменные rules работают только тогда, когда ядро знает домен. Источниками домена могут быть:

1. имя, пришедшее через proxy inbound;
2. DNS/fake-ip mapping;
3. sniffer.

После этого rules идут сверху вниз и выбирают первое совпадение. Подробно: [30-rules.md](30-rules.md).

---

## Как sniffer связан с fake-ip

Fake-ip и sniffer часто решают похожую практическую проблему — сохранить доменную информацию для маршрутизации — но находятся в разных местах цепочки:

- fake-ip строит mapping через DNS;
- sniffer читает уже начавшееся соединение.

Включение sniffer не означает, что обязательно нужен fake-ip, и наоборот.

---

## Что у нас в проекте

Текущий bootstrap `keenetic-auto-setup` **не добавляет `sniffer:` автоматически**.

Исторический пакетный placeholder содержал sniffer-блок; поэтому [26-dns-i-fake-ip.md](26-dns-i-fake-ip.md) раньше объясняла его рядом с DNS. Рабочий пользовательский config или генератор может включать sniffer самостоятельно.

Проект не делает sniffer install prerequisite и не проверяет его наличие Doctor'ом.

---

## На слабом Keenetic

Не надо превращать sniffer в «включить всё на всех портах на всякий случай». Нормальный подход:

1. включать только нужные parsers;
2. ограничивать их реальными портами;
3. использовать `override-destination` только когда понятен эффект;
4. исключать проблемные домены через `skip-domain`;
5. проверять результат по Connections/логам, а не по одному факту валидного YAML.

---

## Когда sniffer не поможет

Он не решает отсутствие сетевого маршрута, мёртвый proxy, неправильный DNS upstream, MTU-проблему, протокол без доступного hostname или неверный порядок rules.

То есть «sniffer включён» — не общий индикатор здоровья прокси.

---

## Диагностика

Если доменное правило не срабатывает:

1. посмотрите Connections в MetaCubeXD — есть ли домен у соединения;
2. проверьте порядок rules;
3. проверьте, попадает ли destination port в нужный sniffer parser;
4. временно используйте более подробный лог, если без него причина не видна;
5. не путайте проблему sniffing с DNS или маршрутом до proxy.

См. [44-logs.md](44-logs.md).
