# Как собрать всё в одну картину

Эта статья — свод Part II. Обе модели входа трафика в ядро рядом, со ссылками на
статьи, где разобран каждый кусок.

Прежде всего — о статусе схем ниже:

> Это **архитектурные модели**, а не дамп живого трафика. Модель A опирается на
> подтверждённую архитектуру проекта (install.sh, placeholder-конфиг, ARCHITECTURE).
> Модель B построена по официальной документации Mihomo — в этом проекте TUN не
> настроен и live-проверен не был ([31-tun.md](31-tun.md)).

---

## Модель A — базовая схема проекта (прокси-порт)

```text
Клиент (LAN)
   │  DNS-запрос
   ▼
DNS Keenetic ──► MagiTrickle: классификация домена      [DNS-уровень Keenetic]
   │
   │  решение: DIRECT / Proxy0 / mitun0 / ...
   ▼
Proxy0 (SOCKS5) ──► 127.0.0.1:7890                      [вход в ядро]
   │
   ▼
Mihomo: правила сверху вниз                              [30-rules.md]
   │  «первое совпавшее правило»
   ▼
группа / узел / DIRECT                                   [29](29-proxy-groups.md)/[28](28-proxies.md)
   │
   ▼
сервер (VLESS/…) ──► Интернет
```

Особенности модели:

- DNS клиентов обслуживает **Keenetic**, а не ядро — DNS Mihomo в этой схеме
  работает на внутренние нужды ([26-dns-i-fake-ip.md](26-dns-i-fake-ip.md),
  базовый тезис).
- Классификация «какой домен куда» — у MagiTrickle; правила ядра — про выходы для
  уже попавшего трафика.
- Fake-ip в этой схеме клиенту практически не встречается.

---

## Модель B — схема с TUN (в проекте не включена)

```text
Клиент (LAN)
   │  обычный IP-трафик (DNS и всё остальное)
   ▼
TUN-интерфейс (например, mitun0)                         [вход в ядро, прозрачный]
   │  auto-route направляет трафик в интерфейс;
   │  dns-hijack заворачивает DNS-запросы в ядро
   ▼
Mihomo: внутренний DNS (fake-ip) + правила сверху вниз   [26](26-dns-i-fake-ip.md)/[30](30-rules.md)
   │
   ▼
группа / узел / DIRECT ──► Интернет
```

Особенности модели:

- Приложениям не нужны никакие прокси-настройки — захват прозрачный.
- **DNS клиентов начинает обслуживать ядро** (dns-hijack) — fake-ip становится
  видимым, тезис статьи 26 перестаёт действовать в этой схеме.
- Keenetic видит TUN как обычный интерфейс — на него можно навести политику.

---

## Это две модели, а не две стадии

Главное, что нужно вынести:

> **Модель A и модель B — два разных способа входа трафика в ядро, а не два
> обязательных этапа одного процесса.** Внутри ядра (правила → группы → узлы)
> всё одинаково; различается только то, *как* трафик туда попадает и *кто* при
> этом обслуживает DNS. В конкретной системе действует та схема, которую вы
> настроили; в базовой установке проекта действует модель A.

| Вопрос | Модель A (база проекта) | Модель B (TUN) |
| --- | --- | --- |
| Как трафик входит в ядро | Proxy0 → порт `7890` | TUN-интерфейс (auto-route) |
| Настройки на клиентах | не нужны (роутер решает) | не нужны (прозрачно) |
| Кто обслуживает DNS клиентов | DNS Keenetic (MagiTrickle видит домены) | DNS Mihomo (dns-hijack, fake-ip) |
| Кто решает «какой домен куда» | MagiTrickle + правила ядра | правила ядра (домены видны ядру) |
| Статус в проекте | установлена установщиком (**Проверено в проекте**) | не включена, live-проверок нет |
