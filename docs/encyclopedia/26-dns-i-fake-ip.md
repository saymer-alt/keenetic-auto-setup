# DNS Mihomo и fake-ip

Вопрос этой статьи: **«В конфиге Mihomo есть большой блок `dns:` — что он делает и
почему у меня в панели адреса `198.18.x.x»?**

Прежде чем разбирать поля — главное предупреждение:

> **В этой системе два разных DNS, и это не одно и то же.**
> **DNS Keenetic** обслуживает клиентов домашней сети — на нём держится классификация
> MagiTrickle. **DNS Mihomo** — внутренняя служба самого ядра для его собственных
> нужд. В базовой схеме проекта клиенты LAN **не используют** DNS Mihomo
> (доказательство — ниже).

---

## Сначала выясните, какой у вас конфиг

Это принципиально: **не у каждого пользователя Mihomo в этом проекте один и тот же
DNS-блок.**

- Установщик ставит ядро с **placeholder-конфигом** `/opt/etc/mihomo/config.yaml`, в
  котором DNS-блок присутствует и заполнен (**Проверено в проекте** — конфиг пакета).
- README прямо говорит: placeholder — **минимальный**, его заменяют своим конфигом.
- Конфиги, собранные в
  [link-generators](https://github.com/saymer-alt/link-generators), **DNS-блок не
  генерируют вообще** (**Проверено в проекте** — по коду генератора). Без `dns:`
  (или при `enable: false`) ядро резолвит домены через **системный DNS** — то есть
  сервер из `/opt/etc/resolv.conf`: в стандартной Entware-установке это DNS Keenetic;
  если `resolv.conf` переписан вручную — тот сервер, что там указан
  (*поведение Mihomo, подтверждено кодом ядра: `Enable` по умолчанию `false`*).

Поэтому дальше в статье формулировка всегда одна: **«в пакетном placeholder-конфиге
сейчас настроено так»** — а не «Mihomo в этом проекте всегда работает так». Если вы
заменили конфиг, сверяйтесь со своим `config.yaml`:

```bash
grep -n -A5 "^dns:" /opt/etc/mihomo/config.yaml
```

## Зачем Mihomo вообще собственный DNS

Ядру нужно самой превращать домены в адреса минимум в трёх случаях:

1. **Соединение, попавшее к ядру, должно быть проверено по доменным правилам** —
   для этого нужен домен (откуда он берётся — см. fake-ip и sniffer ниже);
2. **домен вашего прокси-сервера** из `proxies` надо превратить в адрес — для этого
   отдельный резолвер (`proxy-server-nameserver`);
3. **в сценариях, где ядро само отвечает клиентам на DNS-запросы** (например, при
   работе через TUN) — тогда его DNS-служба слушает запросы. В базовой схеме проекта
   этот сценарий не используется.

Если DNS-блока нет — ядро не перестаёт работать: по коду ядра `enable` по умолчанию
`false`, то есть резолвинг идёт через системный DNS (*поведение Mihomo,
подтверждено исходником и документацией*).

## `listen: 127.0.0.1:1053` — адрес и порт

```yaml
listen: 127.0.0.1:1053
```

Это адрес, на котором **встроенная DNS-служба ядра** принимает запросы (udp/tcp).

- `127.0.0.1` — только loopback **роутера**: из домашней сети на этот порт попасть
  нельзя (**Проверено в проекте** — так в placeholder-конфиге).
- `1053` — просто выбранный проектом порт; ничего «обязательного» в нём нет
  (*в примере официальной документации DNS-служба слушает на `0.0.0.0:1053` — порт
  тот же, но bind на всех интерфейсах; `127.0.0.1` в placeholder'е — более закрытый
  вариант, доступ только с самого роутера*).

### Базовый тезис: клиенты LAN не используют DNS Mihomo

> **В базовой схеме клиенты LAN не используют DNS Mihomo.**
> Это **вывод из текущей конфигурации и схемы проекта**, а не результат отдельного
> live-теста. Основания, все три из конфига и кода установки:
>
> 1. `listen` привязан к `127.0.0.1` — loopback роутера, из LAN недостижим;
> 2. секции `tun` в placeholder-конфиге нет — значит, нет и перехвата DNS-запросов
>    через TUN;
> 3. проект нигде не перенаправляет DNS-клиентов LAN на `1053`.

Клиенты идут в DNS Keenetic (установщик дополнительно включает перехват «прямых»
port-53 запросов к внешним резолверам — это сторона KeeneticOS/MagiTrickle, он
разобран в [HOWTO, раздел 6.1](../HOWTO_RU.md#61-перехват-транзитного-dns-управляется-установщиком)).
Чтобы DNS Mihomo начали использовать клиенты, нужен TUN-вход с dns-hijack либо
ручное направление на `1053` — это за пределами текущей схемы и этой статьи.

## `enhanced-mode: fake-ip` — что это такое

```yaml
enhanced-mode: fake-ip
fake-ip-range: 198.18.0.1/16
```

**Механизм** (*общее поведение Mihomo, по официальной документации*): в режиме
fake-ip ядро, получив DNS-запрос «какой адрес у домена», **сразу** отвечает адресом
из служебного диапазона `fake-ip-range` и запоминает пару «домен ↔ выданный адрес».
Настоящий резолвинг происходит позже — когда соединение к этому адресу реально
устанавливается. Зачем: ядро **сразу знает домен** соединения и может применять
доменные правила без ожидания резолвинга.

Что важно понимать без иллюзий:

- **fake-ip — это не «подмена интернета»**: служебный адрес живёт только внутри
  маршрутизации ядра; до сервера назначения доходит настоящий запрос по настоящему
  адресу, который ядро получает при установке соединения.
- **Дефолт Mihomo — другой режим** (`redir-host`): fake-ip в placeholder — это
  **проектный выбор**, не обязательная настройка.
- **`fake-ip включён в placeholder ≠ «вся LAN работает через fake-ip»`.** В базовой
  схеме LAN-клиенты DNS Mihomo не используют (тезис выше): fake-ip выдаётся только
  тем, чьи запросы дошли до DNS ядра. Пока нет TUN и перенаправления на `1053`,
  вы этот механизм практически не увидите — он станет актуален вместе с TUN
  ([31-tun.md](31-tun.md)).

### `fake-ip-range` и адреса `198.18.x.x`

`198.18.0.1/16` — диапазон, из которого ядро выдаёт служебные адреса. **Увидели в
панели или логах адрес `198.18.x.x` — это fake-ip из этого конфига, а не реальный
внешний IP и не ошибка сети** (то же — в [словаре](01-slovar.md)). Диапазон
настраиваемый, это не «магический адрес Mihomo»; при этом `198.18.0.1/16` —
встроенный дефолт Mihomo, так что placeholder здесь ни от чего не отступает
(подтверждено кодом ядра). Пара «домен ↔ адрес» сохраняется
между рестартами — в placeholder включено `profile: store-fake-ip: true`
(**Проверено в проекте**).

### `fake-ip-filter` — кому fake-ip не выдаётся

Список доменов, для которых ядро отвечает **настоящим** адресом, минуя fake-ip.
Зачем: служебным доменам (проверка доступности сети Windows, NTP, `.lan`/`.local`)
служебные адреса только ломают жизнь. Список в placeholder
(`*.lan`, `*.local`, `+.msftconnecttest.com`, `+.pool.ntp.org`, `time.*.com`…) —
**проектный**, его можно и нужно править под себя, а не считать обязательным.

## `nameserver`, `proxy-server-nameserver`, `fallback` — чем ядро резолвит

В placeholder-конфиге (**Проверено в проекте**):

```yaml
proxy-server-nameserver:      # только для доменов ваших прокси-серверов
  - https://1.1.1.1/dns-query
  - https://8.8.8.8/dns-query

nameserver:                   # основной резолвинг ядра
  - https://1.1.1.1/dns-query
  - https://8.8.8.8/dns-query

fallback:                     # второй эшелон
  - tls://1.0.0.1
  - tls://8.8.4.4
```

- **`nameserver`** — основные резолверы ядра. Здесь — DoH-серверы, заданные прямо
  IP-адресами: запросы шифруются и уходят **мимо DNS Keenetic**. Это **внутренний**
  путь ядра — он не меняет то, каким DNS пользуются клиенты LAN.
- **`proxy-server-nameserver`** — отдельный резолвер **только для доменов ваших
  прокси-серверов** из `proxies`. Если ваш сервер задан доменом (типичный VLESS),
  ядро резолвит его именно отсюда — отдельно от всего остального.
- **`fallback`** — второй эшелон. Аккуратно, это самое тонкое место конфига:
  по официальной документации Mihomo, **при наличии `fallback` включается
  дефолтный фильтр** `geoip-code: cn`: ответы основных серверов, не похожие на
  адреса Китая, считаются «загрязнёнными», и ядро берёт ответ из `fallback`.
  В placeholder `fallback` задан, а `fallback-filter` явно **не** задан — значит,
  действует именно этот дефолт. **Так следует из документации Mihomo; live-замера
  на нашей сборке не делалось.** Это описание того, как конфиг устроен, а не
  рекомендация его менять.

Про IPv6: в placeholder-конфиге `ipv6: true` (и на верхнем уровне, и в DNS-блоке) —
это свойство placeholder-конфига; общая позиция проекта по IPv6 в базовой схеме —
см. [../../ARCHITECTURE.md](../../ARCHITECTURE.md) (конфиги от link-generators,
например, собираются с `ipv6: false`).

## `default-nameserver` — не «главный DNS»

```yaml
default-nameserver:
  - 1.1.1.1
  - 8.8.8.8
```

Название провоцирует ошибку: это **не** «основные DNS-серверы Mihomo». По
документации это bootstrap-резолвер: он нужен, чтобы разрешить **доменные имена
самих DNS-серверов** из других полей (например, если бы `nameserver` был задан как
`https://cloudflare-dns.com/dns-query`, его домен надо сначала разрезолвить — вот
для этого и `default-nameserver`).

Нюанс именно нашего placeholder: `nameserver` и `proxy-server-nameserver` заданы
**IP-адресами**, доменных имён среди DNS-серверов нет — поэтому в этом конкретном
конфиге `default-nameserver` фактически не имеет работы. Он станет нужен, как
только вы впишете DNS-сервер доменом.

## Sniffer — не DNS

В placeholder включён ещё один блок — `sniffer`. Он к DNS **отношения не имеет**,
но служит той же цели — добыть домен:

- **DNS** превращает домен в адрес (запрос «какой адрес у домена?»);
- **sniffer** идёт наоборот: смотрит в сам трафик (HTTP/TLS/QUIC — в конфиге
  указаны их порты) и **извлекает доменное имя из соединения** (например, из
  TLS-приветствия). Это помогает ядру применять доменные правила к соединениям,
  которые пришли «голым» IP-адресом, без домена от DNS.

Плюс `override-destination` — результат обнаружения используется как фактический
адрес назначения соединения, а `skip-domain` не трогает служебные домены
(`+.lan`, `+.push.apple.com`…). Весь этот блок — *общее поведение Mihomo по
официальной документации*; значения в placeholder — **Проверено в проекте**.
Подробный разбор sniffer — материал отдельной будущей статьи.

## Сводка: механизм Mihomo vs значение в placeholder

| Поле | Механизм (Mihomo, по документации) | Значение в placeholder (проект) |
| --- | --- | --- |
| `enable` | вкл/выкл DNS ядра; `false` → системный DNS | `true` |
| `listen` | адрес DNS-службы ядра | `127.0.0.1:1053` (наш выбор) |
| `enhanced-mode` | режим ответов; **дефолт `redir-host`** | `fake-ip` (наш выбор) |
| `fake-ip-range` | диапазон служебных адресов | `198.18.0.1/16` |
| `fake-ip-filter` | домены без fake-ip | служебные домены (наш список) |
| `nameserver` | основной резолвинг ядра | DoH 1.1.1.1 / 8.8.8.8 (по IP) |
| `proxy-server-nameserver` | резолвинг доменов прокси-узлов | DoH 1.1.1.1 / 8.8.8.8 |
| `fallback` | второй эшелон + **дефолтный фильтр geoip cn** | tls://1.0.0.1, tls://8.8.4.4 |
| `default-nameserver` | bootstrap: резолвинг имён DNS-серверов | 1.1.1.1, 8.8.8.8 (в этом конфиге не задействован) |

Чего в этом конфиге **нет** (и что поэтому не «работает у нас»): `nameserver-policy`,
`respect-rules`, `direct-nameserver`, dns-hijack через TUN. Это возможности ядра из
документации — рассказывать о них как о части нашей установки нельзя.

## Честные оговорки

- **Проверено в проекте**: состав и значения DNS/sniffer-блоков placeholder-конфига,
  отсутствие `tun`, адрес `listen` на loopback, отсутствие перенаправления клиентов
  на `1053`, отсутствие DNS-блока в генераторе link-generators.
- **Общее поведение Mihomo** (официальная документация, не live-прогон): семантика
  fake-ip/redir-host и её дефолт, назначение всех перечисленных полей, дефолтный
  fallback-фильтр `geoip cn`, «без DNS-блока — системный DNS», поведение sniffer.
- Тезис «клиенты LAN не используют DNS Mihomo» — **вывод из конфигурации**; как
  относится поведение этого DNS-блока к вашим доменным правилам в базовой схеме —
  зависит от непроверенной детали (что именно передаёт Keenetic в SOCKS5 — домен или
  адрес), поэтому категоричных утверждений здесь нет.
- Живые проверки — за оператором: содержимое connections в панели, фактическое
  поведение fallback-фильтра на текущей сборке.
