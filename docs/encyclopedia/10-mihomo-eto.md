# Что такое Mihomo

Вопрос этой статьи: **«Я установил это на Keenetic. Что такое Mihomo и зачем он мне
вообще нужен?»**

---

## Сначала простыми словами

> **Mihomo — сетевое ядро (прокси-движок): программа, которая принимает сетевой
> трафик, определяет по правилам, куда его направить, и умеет работать с разными
> типами прокси-серверов и туннелей.**

Это вся суть. Всё остальное — детали того, *как именно* он принимает, решает и
направляет.

Более точное определение (своими словами по официальной
[wiki Mihomo](https://wiki.metacubex.one/ru/)): Mihomo — платформенно-независимое
ядро на Go, которое маршрутизирует каждое соединение по настраиваемым правилам между
своими **входами** (inbound) и **выходами** (outbound). Термины inbound/outbound —
в [словаре](01-slovar.md).

Одна строка истории, чтобы не путаться в названиях: Mihomo — это продолжение ядра
Clash (оригинальный проект прекращён в конце 2023 года), которое развивалось под
именем Clash.Meta и затем было переименовано в Mihomo. Это история экосистемы по
публичным источникам; в документах этого проекта все три имени означают одно и то же
ядро.

---

## Что Mihomo НЕ делает

Правильная ментальная модель держится на отрицаниях:

- **Mihomo ≠ KeeneticOS.** Это не часть прошивки роутера. Обычная программа в Entware,
  которая запускается скриптом и живёт, пока работает роутер.
- **Mihomo ≠ MagiTrickle.** MagiTrickle — отдельный компонент на стороне роутера:
  он настраивает и поддерживает правила, по которым механизмы KeeneticOS направляют
  выбранные домены в нужный интерфейс (в том числе в Mihomo). Mihomo исполняет свою
  часть — обрабатывает то, что до него дошло, по *своим* правилам.
- **Mihomo ≠ MetaCubeX.** MetaCubeX — это экосистема и, в обиходе, веб-панель.
  Панель к Mihomo подключается, но не является им. Подробно:
  [11-metacubex-eto.md](11-metacubex-eto.md).
- **Mihomo ≠ один конкретный VPN-протокол.** Это не «VLESS-клиент» и не «WireGuard
  на роутере» — это движок, который умеет работать с многими типами прокси и туннелей
  одновременно.
- **Mihomo ≠ web-панель.** Ни metacubexd, ни любая другая панель не нужны ему для
  работы.
- **Mihomo ≠ DNS-сервер сам по себе.** В конфиге есть вспомогательный DNS-блок — но
  это инструмент внутри маршрутизации, а не «замена DNS роутера». Подробности —
  [26-dns-i-fake-ip.md](26-dns-i-fake-ip.md).
- **Mihomo не обязан использовать TUN.** В базовой схеме этого проекта TUN вообще не
  настроен — всё работает через обычный прокси-порт (см. ниже).
- **Mihomo работает без MetaCubeX и без web UI** — установка по умолчанию этого
  проекта ставит ровно ядро, без всякого интерфейса (**Проверено в проекте**).

## Где Mihomo находится в нашей системе

Упрощённая схема (упрощение — осознанное; полная модель с тремя путями трафика — в
[../../ARCHITECTURE.md](../../ARCHITECTURE.md)):

```text
Клиент (телефон, ноутбук, телевизор)
   │
   ▼
KeeneticOS ── DNS и правила перенаправления: какие домены и устройства куда
   │
   ▼
MagiTrickle: классифицирует домен → правило для сетевого стека роутера
   │
   │  перенаправление выполняют механизмы KeeneticOS (firewall/routing/NAT)
   ├── DIRECT ─────────────────► провайдер ──► Интернет
   │
   └── Proxy0 (SOCKS5, 127.0.0.1:7890)  ◄── основной вход в Mihomo в этом проекте
         │
         ▼
      Mihomo: свои правила выбирают выход
         ├── DIRECT  (напрямую)
         ├── proxy / proxy-group  (через сервер)
         └── …другие варианты из вашего config.yaml
         │
         ▼
      Интернет
```

> **Две разные роли, которые важно не склеивать.** Сетевой стек роутера
> (firewall/routing/NAT — настраиваемые в том числе MagiTrickle) определяет, какие
> соединения вообще попадут в Mihomo; правила Mihomo — что он сделает с уже
> поступившим соединением. В базовой схеме через Mihomo идёт только выбранный
> трафик, а не весь LAN: значительная часть логики классификации и перенаправления
> выполняется средствами KeeneticOS, и направлять через Mihomo весь LAN-трафик этой
> архитектуре не требуется (а обработка большего объёма трафика ядром имеет
> вычислительную цену). При этом сам Mihomo умеет классифицировать и
> маршрутизировать попавший к нему трафик — вплоть до схемы с TUN, где он сам
> становится точкой перехвата ([31-tun.md](31-tun.md)).

Про второй вход — TUN (`mitun0`): он **не настроен в базовой установке проекта**
(**Проверено в проекте**: в разворачиваемом конфиге нет секции `tun`). Он появляется
только если вы сами добавите `tun` в свой `config.yaml` — и тогда имя устройства
задаётся там же. Пока вы этого не сделали, единственный вход в Mihomo — порт `7890`
со стороны Keenetic (интерфейс Proxy0).

И отдельно — канал управления, который не имеет отношения к пользовательскому
трафику:

```text
Браузер (панель MetaCubeX)
   │
   ▼
external-controller (API, порт 9090 — только если включён)
   │
   ▼
Mihomo
```

> **Это канал управления, а не пользовательский трафик.** По нему идут команды
> и статистика для панели. Пользовательский трафик в панель не заходит.

## Что происходит внутри Mihomo

Самая простая модель работы ядра:

```text
входящий трафик
      ▼
определение соединения (куда оно идёт: домен / IP / порт)
      ▼
DNS / IP / домен / правила
      ▼
выбор маршрута: первое совпавшее правило
      ▼
DIRECT  /  proxy-group  /  proxy
      ▼
выход
```

«Правила» здесь — просто список условий «если …, то направить …» из `config.yaml`.
Как они устроены, какие бывают и как их писать — отдельная тема Part II (правила —
[30-rules.md](30-rules.md), группы — [29-proxy-groups.md](29-proxy-groups.md), DNS —
[26-dns-i-fake-ip.md](26-dns-i-fake-ip.md)); сейчас достаточно модели
«первое совпавшее правило выбирает выход».

## Mihomo в этом проекте

Только то, что реально используется и подтверждено кодом и конфигом проекта:

| Элемент | Что это здесь | Пометка |
| --- | --- | --- |
| Версия | mihomo — свежий релиз из `saymer-alt/entware-go` (на момент написания — **1.19.30**); так ставит универсальный `install.sh`. Запасной `install_7621.sh` для mipsel ставит зафиксированную более старую сборку (на момент написания — 1.19.23); какой установщик и почему — [docs/07](../07-install.md) | Проверено в проекте |
| Запуск | `/opt/etc/init.d/S99mihomo` (`status` / `restart`) | Проверено в проекте |
| Рабочий каталог и конфиг | `/opt/etc/mihomo`, конфиг — `config.yaml` | Проверено в проекте (`-d /opt/etc/mihomo`) |
| Вход | **mixed-port `127.0.0.1:7890`** (одновременно HTTP- и SOCKS5-прокси) | Проверено в проекте (базовый конфиг) |
| Точка входа от Keenetic | **проектный ProxyN** — локальная SOCKS5-точка входа в Mihomo (прокси-интерфейс KeeneticOS, цель `127.0.0.1:7890`), подпись `mihomo t2sN`; установщик сам находит или создаёт его: `Proxy0`, если тот свободен, иначе первый свободный `ProxyN` (занятый чужим конфигурацией `Proxy0` не трогается) | Проверено в проекте (install.sh) |
| TUN (`mitun0`) | В базовой установке **не настроен**; появляется, только если добавить `tun` в свой конфиг | Проверено в проекте (базовый конфиг) |
| Controller | **Выключен по умолчанию** — в bootstrap-конфиге строк `external-controller`/`secret`/`external-ui` нет вовсе (в старом пакетном placeholder они были закомментированы); включается вручную — [12-pervyj-vhod-v-ui.md](12-pervyj-vhod-v-ui.md) | Проверено в проекте |
| Связь с DNS/MagiTrickle | Классификацию доменов ведёт MagiTrickle на стороне роутера (наблюдая DNS KeeneticOS). **В текущем bootstrap DNS-блока у Mihomo нет** — без пользовательского `dns:` ядро резолвит через системный резолвер; `1053`/fake-ip относились к историческому пакетному placeholder | Проверено в проекте; разбор — [26-dns-i-fake-ip.md](26-dns-i-fake-ip.md) |
| Что ещё включено | `mode: rule`, sniffer и profile-кэши — только в **историческом пакетном placeholder**; в текущем bootstrap-конфиге этих блоков нет. Без `mode:` ядро работает с документированным дефолтом `rule`, sniffer и profile-кэши не активны | Проверено в проекте (bootstrap); разбор — [27-porty-i-config-yaml.md](27-porty-i-config-yaml.md), [26-dns-i-fake-ip.md](26-dns-i-fake-ip.md) |

Важно: всё, что Mihomo умеет *в принципе* (десятки типов прокси, провайдеры, гео-базы,
разные режимы DNS и т.д.) — это возможности **ядра**, а не части нашей установки.
Наша установка использует из них скромный набор, перечисленный выше.

## Один пример (на минимальном конфиге из README)

В минимальном рабочем примере из README у Mihomo две строки правил:
`GEOIP,private,DIRECT` и `MATCH,Proxy`, один сервер в `proxies` и одна группа
`Proxy`. Что происходит, когда устройство из домашней сети открывает сайт, попавшее
под правило Proxy0:

```text
браузер запрашивает сайт
   → Keenetic/MagiTrickle направляет это соединение в Proxy0
   → Proxy0 передаёт его на 127.0.0.1:7890 (в Mihomo)
   → Mihomo смотрит правила сверху вниз:
       GEOIP,private?  нет → следующая строка
       MATCH,Proxy?    да → выход через группу Proxy
   → группа Proxy указывает на сервер из proxies
   → соединение уходит на этот сервер и дальше в интернет
```

Какие правила у вас — определяет ваш `config.yaml`; проект не навязывает ни одного
конкретного правила (приведённый пример — из README).

## Минимальная диагностика

Три-четыре безопасные проверки (все — из документации проекта; подробности — в
[HOWTO, раздел 11](../HOWTO_RU.md#11-быстрая-диагностика)):

```bash
/opt/etc/init.d/S99mihomo status        # жив ли процесс: ожидаем alive
mihomo -d /opt/etc/mihomo -t            # валидация конфига без запуска
netstat -tln | grep 7890                # слушает ли вход (127.0.0.1:7890)
curl --proxy 127.0.0.1:7890 http://google.com/generate_204   # сквозной ответ: 204
```

Если что-то из этого не так — начните с [HOWTO, раздел Диагностика](../HOWTO_RU.md#12-типовые-проблемы);
эта статья не про troubleshooting.
