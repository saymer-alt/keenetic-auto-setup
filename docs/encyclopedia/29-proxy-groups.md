# Proxy Groups — группы узлов

Вопрос этой статьи: **«Зачем нужны proxy-groups и как группа решает, через какой
сервер пойдёт трафик?»**

Группа — это **контейнер над узлами** ([28-proxies.md](28-proxies.md)) с правилом
выбора. Её смысл: правило маршрутизации ссылается на **одно имя**, а что стоит за
именем — один сервер или десять с автопереключением — меняется без правки правил.

---

## Общий скелет

По официальной документации у группы обязательны `name` и `type`; узлы
перечисляются в `proxies` (там могут быть и узлы, и другие группы):

```yaml
proxy-groups:
  - name: "Proxy"          # имя, под которым на группу ссылаются правила
    type: select           # тип группы: как выбирается выход
    proxies:
      - "server"           # узлы из proxies (пример из README)
```

Это минимальный рабочий пример из README проекта: одна группа с одним узлом.

---

## Типы групп

Названия и назначение типов — по официальным разделам документации:

| Тип | Официальное название | Как выбирается выход |
| --- | --- | --- |
| `select` | ручной выбор | выбранный сейчас узел; переключаете вручную (в панели) |
| `url-test` | автоматический выбор | периодическая проверка адреса из `url` с интервалом `interval`; выход — самый быстрый из доступных |
| `fallback` | автоматический откат | выход — первый доступный по порядку списка; упал — берётся следующий |
| `load-balance` | балансировка нагрузки | соединения распределяются по узлам группы |
| `relay` | цепочка прокси | узлы соединяются в цепочку друг за другом |

Подтверждённые документацией детали: `interval` — если не равен 0, включается
периодическая проверка; `lazy` по умолчанию `true` (неиспользуемая группа не
тестируется); `max-failed-times` по умолчанию 5. Прочие тонкости типов
(`tolerance`, стратегии балансировки) — в официальной документации, здесь они не
нужны.

Для новичка почти всегда достаточно `select`: простой и предсказуемый.

## Как группа связана с правилами

Правило называет группу **по имени** ([30-rules.md](30-rules.md)):

```text
правило:  MATCH,Proxy        → «всё остальное — в группу Proxy»
группа:   Proxy (select)     → сейчас выбран узел "server"
узел:     server             → VLESS-сервер из proxies
```

Имя группы — как переменная: правила фиксируются на имени, а содержимое группы
меняется свободно. Переключение узла в группе меняет направление **новых**
соединений — уже установленные продолжаются по-старому (это поведение видно в
панели — [11-metacubex-eto.md](11-metacubex-eto.md)).

## Группа есть — трафик не обязательно идёт через неё

Частая ошибка новичка: «добавил группу — значит, трафик пошёл через неё». Нет.
Группа — просто **именованный вариант выхода**. Реально через неё пойдёт только тот
трафик, на который укажут правила (или другой путь входа, вроде выбора в панели
режима global — про режимы ядра см. [27-porty-i-config-yaml.md](27-porty-i-config-yaml.md)).

Крайний случай — наш placeholder: в нём группа `GLOBAL` (тип `select`, в списке
`DIRECT` и `REJECT`, узел-пример закомментирован) есть, а секции `rules` **нет
вообще** (**Проверено в проекте**). То есть «из коробки» группа существует, но ни
одно правило на неё не ссылается — ещё одна причина, почему после установки нужен
свой конфиг.

---

## Встроенные группы и режим global

Пара слов из официальной документации: в режиме ядра `global` трафик направляется
через встроенную группу `GLOBAL` (выбор узла в ней). В базовом режиме `rule`, на
котором построен проект, работают ваши правила и ваши группы. Больше про режимы —
[27-porty-i-config-yaml.md](27-porty-i-config-yaml.md).
