# Rules — правила маршрутизации

Вопрос этой статьи: **«Как ядро решает, через какой сервер или напрямую пойдёт
конкретное соединение?»**

Правило (`rule`) — одна строка в `config.yaml`: **«если соединение подходит под
условие — отправить в указанный выход»**. Список правил — и есть маршрутизация ядра.

---

## Синтаксис и порядок

```yaml
rules:
  - ТИП,аргумент,выход
```

- **выход** — `DIRECT` (напрямую), `REJECT` (запретить) или имя прокси/группы
  ([28](28-proxies.md)/[29](29-proxy-groups.md)).
- **Порядок важен**: по официальной документации правила сопоставляются **сверху
  вниз**, и работает первое совпавшее — та самая модель «первое совпавшее правило
  выбирает выход» из [10-mihomo-eto.md](10-mihomo-eto.md).
- Любопытная деталь из документации: если правило выбрало узел **без поддержки
  UDP**, а соединение — UDP, сопоставление продолжится по правилам ниже.

Интересный факт из документации о `MATCH` и протоколе сравнения: правило типа
`MATCH` «сопоставляет все запросы без условий» — безусловный финальный выход. На
странице документации он всегда показан последним; обязательность `MATCH` и
поведение ядра, если ни одно правило не совпало, а `MATCH` нет, документацией на
этой странице не описаны — утверждать здесь этого не будем.

## Основные семейства условий (в объёме понимания)

| Семейство | Примеры типов | Что сверяет |
| --- | --- | --- |
| Домен | `DOMAIN`, `DOMAIN-SUFFIX`, `DOMAIN-KEYWORD`, `DOMAIN-REGEX`, `GEOSITE` | домен соединения; `GEOSITE` — категории из GEO-данных ([43-geodata.md](43-geodata.md)) |
| IP назначения | `IP-CIDR`, `IP-CIDR6`, `GEOIP`, `IP-ASN` | адрес/подсеть/страну/автономную систему |
| IP источника | `SRC-IP-CIDR`, `SRC-GEOIP`, `SRC-IP-ASN` | адрес/страну/автономную систему клиента-источника |
| Порты | `DST-PORT`, `SRC-PORT` | порт назначения/источника |
| Процесс | `PROCESS-NAME` и др. | процесс, породивший соединение (на роутере — процессы самого роутера; процессы клиентов ядру не видны, так что в Keenetic-схемах тип малоприменим) |
| Прочее | `NETWORK` (tcp/udp), `IN-PORT`, `RULE-SET`, логические `AND`/`OR`/`NOT`, `SUB-RULE` | дополнительные условия; `RULE-SET` требует `rule-providers` — отдельная тема |

Пример из минимального конфига README (**Проверено в проекте**):

```yaml
rules:
  - GEOIP,private,DIRECT   # частные (локальные) адреса — напрямую
  - MATCH,Proxy            # всё остальное — в группу Proxy
```

Читается сверху вниз: сначала «если адрес назначения частный — DIRECT», затем
`MATCH` ловит всё остальное и отправляет в группу.

## Быстрый DIRECT для одного клиента

Если трафик клиента **уже входит в Mihomo**, его можно отправить напрямую правилом по исходному IP. Например, для клиента `192.168.1.201`:

```yaml
rules:
  - SRC-IP-CIDR,192.168.1.201/32,DIRECT
  # остальные правила ниже
```

Правила читаются сверху вниз, поэтому такое исключение должно находиться выше общих proxy-правил. Это правило действует только внутри Mihomo: оно не отменяет решения MagiTrickle/Keenetic о том, попадёт ли конкретный трафик в Mihomo вообще. Для полного исключения устройства на уровне роутера используйте отдельную policy/сегмент Keenetic; отдельный сегмент, не включённый в MagiTrickle `link:`, также не участвует в его DNS-классификации. Не путайте эти два уровня.

## `GEOIP`, `GEOSITE` и большие списки

Mihomo умеет `GEOIP`, `GEOSITE` и `RULE-SET`, поэтому технически можно строить схему вроде «локальные/региональные ресурсы DIRECT, остальное через Proxy». Но это уже маршрутизация **внутри Mihomo**, а не замена доменным группам MagiTrickle. Большие geo/rule-наборы требуют соответствующих баз/provider-файлов и добавляют работу самому Mihomo; на роутере это следует вводить только после практического измерения ресурсов, а не считать бесплатной заменой точечных правил.

## `no-resolve` — правила по IP и цена резолвинга

IP-правила (`IP-CIDR`, `GEOIP`…) сравнивают **адрес**. Если соединение пришло с
доменом, ядру, чтобы сравнить, пришлось бы запустить DNS-резолвинг. Модификатор
`no-resolve` у IP-правила означает: «не резолви ради этого правила — пропусти его»
(*по официальной документации; там же нюанс: если резолвинг уже случился при более
раннем правиле, IP-правило сработает и с `no-resolve`*).

Связь с [26-dns-i-fake-ip.md](26-dns-i-fake-ip.md): это одна из точек, где правилам
нужна доменная/адресная информация — но сами правила **не являются DNS**: они лишь
потребляют результат.

## Откуда правило берёт домен: DNS и sniffer

Чтобы доменные правила (`DOMAIN-SUFFIX`, `GEOSITE`…) сработали, ядро должно знать
домен соединения. Домен приходит из:

- DNS-механизма ядра — fake-ip-маппинг или сопоставление через встроенный DNS
  (разбор — [26-dns-i-fake-ip.md](26-dns-i-fake-ip.md));
- **sniffer** — извлечение домена прямо из трафика (TLS/HTTP/QUIC) — обзор рядом
  с DNS в [26-dns-i-fake-ip.md](26-dns-i-fake-ip.md), подробности в
  [33-sniffer.md](33-sniffer.md).

Правила, DNS и sniffer — три разных механизма; правила только используют то, что
те дали.

## Правила в нашем проекте

- В placeholder-конфиге секции `rules` **нет** (**Проверено в проекте**) — «из
  коробки» правила не настроены; рабочий набор задаёте вы (или генератор).
- В базовой схеме проекта **какие соединения вообще попадут в ядро, определяется
  на стороне роутера**: MagiTrickle настраивает и поддерживает правила, по которым
  механизмы KeeneticOS направляют выбранные домены в Proxy0; свои правила ядро
  применяет уже к тому, что дошло ([10-mihomo-eto.md](10-mihomo-eto.md), карта
  системы). Правила Mihomo и правила MagiTrickle — разные роли в одной схеме:
  первые — про выходы ядра, вторые — про то, какие домены вообще поедут в ядро.
- Не запускайте `mihomo -t` параллельно с работающим демоном: проект соблюдает правило одного Mihomo. Для обычной read-only диагностики используйте `mihomo-doctor.sh`; исполняемую проверку `mihomo -d /opt/etc/mihomo -t` делайте только при остановленном сервисе ([27-porty-i-config-yaml.md](27-porty-i-config-yaml.md)).
