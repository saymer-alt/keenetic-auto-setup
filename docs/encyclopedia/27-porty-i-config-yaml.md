# Порты и анатомия config.yaml

Вопрос этой статьи: **«Какие порты используются в схеме и как читать верхний уровень
`config.yaml`?»**

Установщик оставляет в `/opt/etc/mihomo/config.yaml` **bootstrap-конфиг проекта**
(минимум с `mixed-port: 7890`), который вы заменяете своим рабочим конфигом;
пользовательский конфиг установщик не перезаписывает.

Откуда берётся этот файл: пакет mihomo
([entware-go](https://github.com/saymer-alt/entware-go/releases)) ставит
**placeholder** — сейчас это четыре строки (`tproxy-port`, `redir-port` и ссылка
на документацию, без `mixed-port`); установщик распознаёт нетронутый placeholder
и заменяет его bootstrap'ом. Ранее пакетный placeholder был развёрнутым примером
конфига (с `allow-lan`, `dns`, `sniffer` — его анатомия разобрана ниже и в
[26-dns-i-fake-ip.md](26-dns-i-fake-ip.md) как историческая). Механизмы Mihomo от
версии стартового конфига не зависят — это общее поведение ядра по официальной
документации.

## Карта верхнего уровня (исторический пакетный placeholder)

В placeholder-конфиге прежней версии пакета было ровно эти ключи и блоки
(**Проверено в проекте** на тот пакет; текущий пакетный placeholder — только
`tproxy-port`/`redir-port`, а bootstrap проекта — только `mixed-port: 7890`):

| Ключ/блок | Что это | Где разобрано |
| --- | --- | --- |
| `mixed-port: 7890` | вход ядра: HTTP+SOCKS5 на одном порту | эта статья |
| `allow-lan: false` | доступ к портам прокси из LAN | эта статья |
| `bind-address: 127.0.0.1` | адрес, на котором слушают порты прокси | эта статья |
| `mode: rule` | режим ядра: решения по правилам | [30-rules.md](30-rules.md) |
| `log-level: info` | детальность логов (значения — по официальной документации) | статья о логах появится позже |
| `ipv6: true` | принимать ли ядром IPv6 | ARCHITECTURE (позиция проекта по IPv6) |
| `profile` | кэши: выбранные узлы, fake-ip-пары | [26-dns-i-fake-ip.md](26-dns-i-fake-ip.md) |
| `unified-delay`, `tcp-concurrent` | оптимизации ядра | по официальной документации |
| `sniffer` | извлечение доменов из трафика | [26-dns-i-fake-ip.md](26-dns-i-fake-ip.md) |
| `dns` | встроенная DNS-служба ядра | [26-dns-i-fake-ip.md](26-dns-i-fake-ip.md) |
| `proxies` | исходящие серверы (в placeholder — пуст, пример закомментирован) | [28-proxies.md](28-proxies.md) |
| `proxy-groups` | группы: в placeholder — одна `GLOBAL` | [29-proxy-groups.md](29-proxy-groups.md) |

Чего в историческом placeholder **нет**: `rules`, `tun`, активного
`external-controller` (его пример — закомментирован,
[12-pervyj-vhod-v-ui.md](12-pervyj-vhod-v-ui.md)), `proxy-providers`/`rule-providers`
(возможности ядра, не наши настройки). В bootstrap-конфиге проекта `rules`, `tun`
и `external-controller` тоже отсутствуют — bootstrap задаёт только
`mixed-port: 7890`.

Закомментированная строка (`#`) = выключенная настройка. Это тот же принцип, из-за
которого controller по умолчанию выключен.

## Входящие порты ядра: механизм

По официальной документации Mihomo умеет несколько видов входящих портов:

| Параметр | Что слушает | Нюансы |
| --- | --- | --- |
| `port` | HTTP(S)-прокси | только HTTP-клиенты |
| `socks-port` | SOCKS-прокси | socks4/4a/5 |
| `mixed-port` | **HTTP(S) и SOCKS5 на одном сокете** | любой HTTP- или SOCKS-клиент |
| `redir-port` | прозрачный redirect | только TCP; Linux/macOS |
| `tproxy-port` | прозрачный tproxy | TCP+UDP; только Linux |

Дефолтных значений у портов **нет** — это настройки, которые задают явно (порт `7890`
в примерах документации — пример, не встроенное значение). Прозрачные порты
(`redir`/`tproxy`) в схеме проекта не используются.

В bootstrap проекта настроен один вход — `mixed-port: 7890`. Один порт «умеет» и
HTTP-, и SOCKS5-клиентов, поэтому и Keenetic (через проектный Proxy-интерфейс
`ProxyN`), и браузерные расширения могут ходить в одну и ту же точку.

## `allow-lan` и `bind-address` — кто и откуда может подключаться

```yaml
allow-lan: false
bind-address: 127.0.0.1
```

- **`allow-lan`** — «разрешает другим устройствам использовать порты прокси для
  доступа в интернет» (*формулировка официальной документации*). При `false` порты
  прокси обслуживают только само устройство, где работает ядро.
- **`bind-address`** — привязка к адресу: `*` (все адреса) или конкретный IP.

В историческом placeholder связка `allow-lan: false` + `bind-address: 127.0.0.1`
была задана явно. В bootstrap проекта `allow-lan` не указан — действует
документированный дефолт `false`, и результат тот же: вход `7890` слушает
**только loopback роутера**. Именно поэтому работает проектный Proxy-интерфейс —
`ProxyN`, нацеленный установщиком на `127.0.0.1:7890`: Keenetic ходит к ядру с
того же роутера. И именно поэтому браузер с ПК на `192.168.1.1:7890` без
`allow-lan: true` не подключится — сценарий FoxyProxy начинается с включения
`allow-lan: true`. Граница безопасности: открытие `7890` в LAN — не повод
открывать его в WAN (firewall остаётся закрытым) — см. README/HOWTO.

## Порты в нашей схеме: кто что слушает

| Порт | Кто слушает | Для чего | Статус |
| --- | --- | --- | --- |
| **7890** | Mihomo | mixed-вход (HTTP+SOCKS5); сюда смотрит проектный Proxy-интерфейс (`ProxyN`) | Проверено в проекте |
| **1053** | Mihomo | встроенная DNS-служба, только loopback | историческое: был в старом placeholder с DNS-блоком; в bootstrap DNS-блока нет — [26](26-dns-i-fake-ip.md) |
| **9090** | Mihomo | controller API — **только если включён** | [12-pervyj-vhod-v-ui.md](12-pervyj-vhod-v-ui.md) |
| 53 | **Keenetic** (DNS-прокси) | DNS клиентов LAN | инфраструктура Keenetic, не Mihomo |
| 80/443 | **KeeneticOS** | web-интерфейс роутера | инфраструктура Keenetic, не Mihomo |
| 443 и др. (у серверов) | — | **исходящие** соединения к вашим прокси-серверам | это не «слушающие» порты роутера |

Два уровня, которые важно не смешивать: порты, которые Mihomo **слушает** (входы), и
порты, к которым Mihomo **подключается сам** (адреса серверов из `proxies`).

## Осторожно: смена порта ломает проектный Proxy (ProxyN)

Проектный Proxy-интерфейс создан установщиком с целью `127.0.0.1:7890`
(**Проверено в проекте** — install.sh). Если вы поменяете `mixed-port` в конфиге
на другое значение, этот интерфейс потеряет цель, и трафик, который Keenetic
направляет в него, перестанет доходить до ядра; та же цель зашита в watchdog и
самопроверку установки. Менять порт входа можно только осознанно — вместе с
обновлением проектного Proxy-интерфейса, а он — installer-managed настройка
(чувствительная зона, см. AGENTS.md проекта). Проще оставить `7890` как есть.

## Как читать верхний уровень config.yaml

- Ключи верхнего уровня (типа `mode: rule`) и блоки (типа `dns:`) — плоский список;
  вложенность задаётся отступами (**2 пробела**, не табуляция).
- Внутри блоков — свои ключи и списки (`- элемент`).
- `#` в начале строки — комментарий; «раскомментировать» = включить настройку.
- После любой правки — проверка без запуска:

```bash
mihomo -d /opt/etc/mihomo -t
```

- Ошибка YAML почти всегда в отступах или опечатке — ядро назовёт проблемное место.

## Общие параметры ядра vs наши значения

- `mode` — значения `rule`/`global`/`direct`, **дефолт `rule`**; у нас `rule`.
- `ipv6` — по документации дефолт `true`; у нас `true` (позиция проекта по IPv6 —
  [../../ARCHITECTURE.md](../../ARCHITECTURE.md)).
- `log-level` — значения `silent`/`error`/`warning`/`info`/`debug`; у нас `info`
  (дефолт на странице документации не указан).
- `unified-delay`, `tcp-concurrent` — оптимизации ядра; включены в placeholder,
  глубокого разбора в энциклопедии не требуют.
