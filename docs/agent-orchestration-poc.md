Статика бандла 0.17.1 подтверждает механизм без fallback на `oauth:*:user_info`. Негативный контроль GO-A2: ephemeral-конфиг без единого секрета с полностью валидным selection `account:zai-individual-coding-plan` / `GLM-5.3` / `reasoningLevel: low` и пустыми правилами → exit 1, 3 с, `Select a model before sending a message`, 0 модельных вызовов; fallback на платные правила структурно исключён (правил нет). ## 3. Что делает POC (`scripts/orchestration-poc/kas_orchestrate.py`)

- `fetch --issue N` — валидация (gh auth; **gh-аккаунт = владелец репозитория** через `gh api user` → `STOP_BAD_ACCOUNT`; repo-allowlist; схема Issue: number/title/body/url/updatedAt — любое расхождение = `STOP_MALFORMED_ISSUE`; `state==OPEN`), чтение ровно одной Issue, фиксация `base_sha` из `git rev-parse`, генерация компактного task contract (поля из Stage 1 #430: `task_id, run_id, issue, repo, base_sha, allowed_paths, intent, DoD, required_gates, token_budget_soft, stop_conditions, owner_go_scope, status`) и handoff, где исполнитель получает команду `gh issue view N --repo R` — **текст задачи никем не перепечатывается**.
- `dispatch --executor dry-run|mock|zcode-cli` — **stale SHA перепроверяется перед dispatch** (`HEAD != base_sha` → `STOP_STALE_SHA`, state не меняется); при реальном dispatch (`mock`/`zcode-cli`) дополнительно считывается та же Issue по номеру, проверяются OPEN, точное совпадение номера/URL и сохранённый `updatedAt` (изменение → `STOP_ISSUE_CHANGED`, закрытие → `STOP_ISSUE_CLOSED`, отказ сети → `STOP_NETWORK`, никаких вызовов модели до проверки); dry-run печатает точную команду (всегда `--mode plan`, yolo/build/edit запрещены конструкцией, обязателен env `ELECTRON_RUN_AS_NODE=1`) и **не занимает задачу** (state остаётся READY); mock имитирует полный цикл для тестов — **это НЕ доказательство полноценной автоматизации**; zcode-cli запускает headless с таймаутом: **ненулевой exit code → `STOP_EXECUTOR_FAILED`, задача → BLOCKED — ложный PASS невозможен**; таймаут → `STOP_EXECUTOR_TIMEOUT`, BLOCKED; при любом сбое исполнителя задача переводится в BLOCKED в журнале.
- `checkpoint` — **stale SHA перепроверяется** перед генерацией; локальный структурированный чекпоинт (`task_id | run_id | base/head SHA | PASS/FAIL/BLOCKED/NOT_TESTED | evidence | blocker | next owner decision`); **PASS принимается только «заслуженным»**: state REVIEW_READY после завершённого dispatch + journal-событие `executor:zcode-cli:ok` того же **task_id и уникального run_id после `fetched`** (каждый fetch создаёт новый run_id, reset сохраняет журнал, но старый успех не считается), иначе `STOP_PASS_UNEARNED` — ручной `--status PASS` без реального прогона исполнителя, а также PASS после mock/dry-run, отклоняются; публикация в GitHub заблокирована двойным opt-in и в POC не вызывается.
- **Межпроцессная блокировка**: OS-lock (`fcntl`/`msvcrt`) на `<state-dir>/.lock` на время любой команды; конфликт → `STOP_LOCKED`; lock освобождается ОС при смерти процесса, stale-файл невозможен.
- STOP-условия (exit 2): `NO_AUTH, BAD_ACCOUNT, BAD_REPO, ISSUE_CLOSED, MALFORMED_ISSUE, NETWORK, DUPLICATE, ACTIVE_TASK, STALE_SHA, OVERSIZE (тело >50 KB усекается маркером), WRITE_NOT_ALLOWED, UNSAFE_MODE, EXECUTOR_MISSING/TIMEOUT/FAILED, LOCKED, STATE_CORRUPT, STATE_INCOMPLETE, PASS_UNEARNED (ручной PASS без зафиксированного успешного прогона реального исполнителя), CONFIRM_REQUIRED`.
- State: `<state-dir>/current_task.json` + append-only `events.jsonl` (кэш; GitHub остаётся источником истины). По умолчанию вне репозитория.

**Live-демо на Issue #430 (read-only, ветка POC `7791868`):** `fetch` → `task_id issue-430-7791868268f9`, base SHA = HEAD ветки, account-проверка пройдена; `dispatch dry-run` → корректная команда, state READY сохранён; `checkpoint NOT_TESTED` → файл создан; `reset --confirm` → state очищен. Отдельным прогоном подтверждён live fail-closed: реальный транзиентный сбой GitHub → `STOP_NETWORK`, повтор после сбоя успешен.


**Safety update (07.11.2026, follow-up to #444):** исторические доказательства 17/17 и live dry-run в §2 относятся к исходной версии POC. Добавлены fail-closed проверки неизменности Issue перед реальным исполнителем: сохранение `updatedAt`, проверка точного Issue number/URL, повторный `gh issue view`, STOP при редактировании/закрытии/сетевом отказе и отрицательные mock-тесты. **Реальный Z.AI headless model call и отсутствие ручных переносов остаются NOT_VERIFIED.** Новый набор тестов и соответствующий CI необходимо подтвердить на новом SHA; первоначальная проверка #444 сама по себе не покрывает follow-up.

## 5. Следующий минимальный шаг до полного конвейера (нужны owner GO)

1. **GO-A (model selection) — ВЫПОЛНЕН 07.11.2026: `BLOCKED_PROVIDER_UNVERIFIED` (факт 9).** Ранняя гипотеза этого пункта (задать `config.defaultModelSelection = {"providerId": "builtin:zai-coding-plan", "modelId": "GLM-5.3-Flash"}` через env-override) опровергнута эмпирически: selection не применяется, headless уходит на первое personal-правило. GO-A2 добавил два независимых условия: обязательный `reasoningLevel` из `values` модели и (главное) credential identity-pointer.
2. **GO-A2 (account-provider proof) — ВЫПОЛНЕН 07.11.2026: `BLOCKED_CREDENTIAL_POINTER` (факт 10).** На этой машине identity-pointer `account-provider:account:zai-individual-coding-plan:identity` отсутствует; валидный selection (`account:zai-individual-coding-plan` / `GLM-5.3` / `reasoningLevel: low`) не применяется, 0 модельных вызовов. **Дальнейший шаг требует нового owner GO** (изменение credentials): `zcode.cjs login zai` (пишет identity-pointer, подтверждено #744 для 0.16.9) либо эквивалентная ручная фиксация credential-записи. Без этого headless Coding Plan недостижим; альтернатива — оставить `zcode-cli`-исполнителя BLOCKED и работать через dry-run + ручной запуск.
3. **GO-B (write):** разрешить `gh issue comment` только после независимой проверки HEAD/CI/evidence и fail-closed тестов. Сейчас `--post` намеренно всегда выдаёт STOP; double opt-in **не означает разрешённую запись**.
4. **GO-C (установка, опционально):** OpenCode официально позволяет выбрать **Z.AI Coding Plan** и ввести plan API key (https://opencode.ai/docs/providers). Сначала отдельно подтвердить локальную квоту/биллинг; GitHub Actions (https://opencode.ai/docs/github) потребует GO на workflow/secrets.
5. После 1–2 — заменить `dry-run` на реального исполнителя на одном небольшом Issue (не #430) и заполнить таблицу метрик из `docs/agent-token-efficiency.md`.

**Дальнейший шаг:** GO-A3 завершился `FAILED_AUTH_TIMEOUT` без авторизации/изменения credentials ([Issue #430](https://github.com/saymer-alt/keenetic-auto-setup/issues/430#issuecomment-6712955646)). Повторный логин, model dispatch и GitHub posting остаются вне данного PR.

## 6. Границы

POC не содержит: авто-merge, тегов/релизов, изменений `main`/`stable`, Actions/webhooks/серверов, доступа к роутерам, секретов. ## 6. Isolated run IDs and GO-A3 result (08.11.2026; candidate)

- **GO-A3 fact:** ZCode CLI v0.17.1 on Windows 10 first failed at the official CLI provider-config bootstrap path. Using both documented runtime provider-path environment variables reached official OAuth, but the browser flow timed out (`FAILED_AUTH_TIMEOUT`). Original credential/config/cache files stayed unchanged, identity-pointer was not created, and **0 model calls** occurred. No further login, handmade pointer, auth URL processing, or billable fallback is authorized here. [Full owner-approved GO-A3 report](https://github.com/saymer-alt/keenetic-auto-setup/issues/430#issuecomment-6712955646).
- **POC run identity:** Every `fetch` generates an independent random UUID4 hex `run_id`, even when Issue and SHA produce identical `task_id`. The contract, journal, status, handoff and checkpoint record the run identity. `checkpoint PASS` now requires a real `zcode-cli` success in the same `task_id` AND `run_id` cycle, following its `fetched` event. Old or malformed local state fails closed. The JSONL journal is **not tamper-proof**, and executor exit 0 is NOT independent CI/FIELD proof.
- **Ordering:** earned-PASS validation and local checkpoint rendering occur before a proposed GitHub posting attempt. The posting stub remains disabled even with `--post --confirm` and `KAS_ORCH_ALLOW_WRITE=1`; no GitHub write is enabled.
- **Offline test scope:** 39 mock-only unittest tests (previous 35), including mismatch/missing run IDs and proof-before-post tests. Full CI/E2E for this candidate is **NOT TESTED until GitHub completes checks on its exact PR head**.
- **Reuse-first option:** OpenCode officially supports selecting a Z.AI Coding Plan provider ([docs](https://opencode.ai/docs/providers)) and has GitHub Issue/PR automation ([docs](https://opencode.ai/docs/github)). It could reduce manual forwarding without custom agent runtime. Actual current-plan accounting in hosted Actions, key scope, permission safety and token use remain unverified. Installing Actions, provisioning secrets or running billable requests needs separate owner GO.
