# Диагностика загрузки скриптов KAS и доступности GitHub

`kas-download-check.sh` — автономный **read-only** диагностический инструмент (issues [#158](https://github.com/saymer-alt/keenetic-auto-setup/issues/158), [#266](https://github.com/saymer-alt/keenetic-auto-setup/issues/266), [#270](https://github.com/saymer-alt/keenetic-auto-setup/issues/270)). Он проверяет по стадиям ту же цепочку, которой пользуется установка и обновление KAS: инструменты → время/CA → DNS → TCP → TLS/HTTP → ограниченная передача → проверка полученного файла. Обычный Doctor внешних сетевых проб не делает; этот режим — отдельный явный запуск.

## Что инструмент делает и чего не делает

- Ничего не меняет: DNS, маршруты, firewall, интерфейсы, ProxyN, Mihomo, MagiTrickle и конфигурация не затрагиваются.
- Скачанные байты **никогда не исполняются**: проверяются только shebang, маркеры проекта и `sh -n` (как в `bootstrap.sh`).
- Не выводит секреты, подписки, токены и YAML; отчёт ограничен по размеру.
- Не объявляет причину (DPI, блокировка провайдера, неисправность GitHub) установленной: статус каждого источника показывается отдельно, успех одной альтернативы не доказывает общую причину.
- Ограничения каждой попытки: connect 7s, total 25s, максимум 256 KiB — как в загрузчике KAS.

## Запуск

```sh
sh kas-download-check.sh                     # стабильная ветка, setup.sh
sh kas-download-check.sh --ref main          # другая ветка
sh kas-download-check.sh --script config-import.sh
sh kas-download-check.sh --report /opt/tmp/kas-dl-report.txt
KAS_MOSHUB_URL='https://…' sh kas-download-check.sh --moshub   # опциональное зеркало
```

Статусы: `PASS / FAIL / UNKNOWN / NOT TESTED / UNSUPPORTED`. Коды возврата: `0` — хотя бы один источник вернул валидный скрипт; `1` — ни один; `2` — ошибка использования.

## Проверяемые источники (по отдельности)

| Источник | Что показывает |
| --- | --- |
| RAW обычный TLS | основной путь установки/обновления |
| RAW IPv4 + X25519 | compatibility-путь из docs/03 (случай `curl (35)`, KN-1010/NC-1812); `UNSUPPORTED`, если curl не умеет `--curves` |
| RAW через wget | независимый транспорт; `NOT TESTED`, если wget не установлен |
| GitHub Contents API | media-путь без raw-CDN |
| Зеркало (Mos.Hub) | только с `--moshub` и `KAS_MOSHUB_URL`; подтверждённого публичного зеркала в репозитории пока нет — без него статус `NOT TESTED` |

## Интерпретация типовых результатов

- `exit 6` — DNS: смотрите резолвер на роутере; остальные стадии при этом закономерно падают.
- `exit 7` — TCP 443 недоступен: маршрутизация/провайдер, а не TLS.
- `exit 35` — TLS handshake: известный полевой случай #255; compatibility-путь IPv4+X25519 и Contents API показываются отдельно.
- `exit 60` — проверка сертификата: типичные причины — неверное время устройства или отсутствие `ca-bundle`.
- `HTTP 404/5xx` — неверный ref/URL или проблема сервиса; адрес и ref печатаются.
- `mid-transfer` (18) — соединение оборвалось во время передачи; частичный файл исполнен быть не может.

Инструмент честно разделяет: что подтверждено наблюдениями (exit-коды, http_code, размеры, маркеры), а что остаётся гипотезой (конкретная причина сбоя сети). Полный отчёт (`--report`) пригоден для вставки в Issue.

## Ограничения

- POSIX sh / BusyBox ash / Entware; необязательные утилиты (`wget`, `nslookup`, `mktemp`) отсутствуют — это отражается в отчёте статусами `NOT TESTED`/`UNKNOWN`, а не падением.
- `telnet://`-приём для TCP-стадии использует сам curl; если сборка curl без telnet — стадия помечается `UNKNOWN`.
- Windows/GitHub-CI прогон и офлайн-регрессия (`tests/download-check-regression.py`, 19 кейсов + отчёт + изоляция PATH) доказывают логику, но **не** являются полевым PASS на Keenetic/Entware — первая аппаратная проверка на KN-1010 остаётся за владельцем.
