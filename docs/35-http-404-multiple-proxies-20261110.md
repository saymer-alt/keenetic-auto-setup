# HTTP 404 при двух Nginx: где на самом деле обработался запрос

> 10.11.2026 — инженерная заметка по сообщению из чата MagiTrickle (Ponywka), не инцидент KAS. **Источник: пересланные скриншоты и сообщение автора; мы не имеем независимого live-trace серверов.**

## Наблюдение

- В конфигурации одного Nginx объявлен `server { listen 80; server_name magitrickle.dev; location / { root /var/www/50_bin.magitrickle.dev; } include /etc/nginx/default.d/*.conf; }`.
- В контейнере/среде `/srv/docker/services/nginx` команда `./nginx -t` сообщила, что синтаксис корректен, а `./nginx -s reload` — о передаче сигнала (`signal process started`).
- Клиент отправил HTTP-запрос на частный LAN-адрес с `Host: magitrickle.dev` и получил `404 Not Found`, тело которого завершалось `openresty`.
- Автор затем вспомнил о **другом** локальном Nginx Proxy Manager (NPM). Это сильная гипотеза, что запрос попал не в тот Nginx, который перезагрузили, но одного ответа `openresty` и сообщения недостаточно, чтобы независимо доказать точную цепочку перенаправления.

## Продолжение от 10.11.2026, 10:38 МСК: HTTP-хосты перенесены домой

Ponywka сообщил, что после обнаружения второго домашнего Nginx Proxy Manager сайты `https://magitrickle.dev/` и `https://bin.magitrickle.dev/packages/` теперь **обслуживаются на его домашней инфраструктуре**. Это объясняет контекст прежнего `404/openresty` (ошибочный выбор reverse proxy наиболее вероятен), но внешний request trace не опубликован: не классифицировать как проверенную идентичность каждого backend. Его слова о недоверии к дата-центрам РФ/Beget — личная мотивировка, а не независимый вывод KAS.

**Для KAS важнее доступность загрузок, не местонахождение сервера:** KAS `install.sh` получает `https://bin.magitrickle.dev/packages/add_repo.sh` и прерывает установку при недоступности этого файла. Дальнейшие DNS/TLS/timeouts/fallback acceptance и прошлый полевой эпизод KN-1010 отслеживаются в [#483](https://github.com/saymer-alt/keenetic-auto-setup/issues/483), **не** смешивать с диагностикой HTTP 404 и не переносить авто-логику в этот docs-only PR. Основной сайт может открываться, а пакетный endpoint — нет; проверять каждый URL отдельно. Не хардкодить домашний IP, не обходить TLS и подписи/целостность feed.

## Что является, а что не является доказательством

| Проверка | Подтверждает | Не подтверждает |
| --- | --- | --- |
| `nginx -t` | Синтаксис файлов, выбранных данным бинарником/контекстом | Что запросы LAN/доменов идут именно в этот экземпляр; существование/доступность нужного файла |
| `nginx -s reload` | Команда reload принята данным экземпляром | Что обновилась конфигурация другого Nginx или NPM; что новый виртуальный хост выбран |
| `curl -H 'Host: ...' http://LAN-IP/` | Ответ конкретного IP/порта при данном HTTP Host | Что выбран нужный backend или документ-root, что внешняя DNS/TLS/SNI-трасса совпадает |
| Тело `404 ... openresty` | Ответ с сигнатурой OpenResty | Само по себе точную идентичность сервера, контейнера или причину отсутствия ресурса |

Возможные причины 404: запрос пришёл в другой reverse proxy; неверный virtual-host; указан неправильный filesystem path; в `location /` не найден файл `index` (или upstream отдаёт 404); перепутаны DNS/адреса/порты. Сам по себе `root` не гарантирует существование `/index.html`. Не исправлять файловые права или конфиг без проверки upstream.

## Локальный read-only маршрут диагностики (на своем сервере)

1. **Кто владеет портом:** `ss -lntp` и фактические Docker publish mappings (`docker ps --format 'table {{.Names}}\t{{.Ports}}'`). В Docker отдельно проверить host:80→container port и сеть контейнеров. Даже если порт 80 свободен у одного контейнера, он может быть занят на хосте другим прокси.
2. **Какой конфиг загружен:** у целевого Nginx `nginx -T` или эквивалент с тем же бинарником/параметрами/контейнером, где проверялось `nginx -t`; проверить `listen`, `server_name`, `default_server`, `include`, `location`, `root`/`alias`, index, backend. Команды чтения конфигурации могут показывать секреты — никогда не публиковать полный дамп без редактирования.
3. **Адресный HTTP-тест:** с каждой целевой машины и, когда это возможно, из каждого контейнера выполнить `curl -i --connect-timeout 3 -H 'Host: magitrickle.dev' http://127.0.0.1/` (внутри контейнера localhost означает сам контейнер!), а затем аналогичный тест по **нужному** внутреннему IP/порту. Не предполагать, что `127.0.0.1` хоста и контейнера одинаковы.
4. **Различить 404 от 502/403:** `404` говорит, что *какой-то* HTTP-обработчик дал ответ «не найдено»; `502` — проблема gateway/upstream; `403` — запрет доступа или Host/Origin/auth gate. Это диагностические ориентиры, не универсальная диагностика root cause.
5. **Для HTTPS:** проверять вместе IP, DNS, SNI, TLS-сертификат и Host через `curl --resolve`/`--connect-to` при необходимости; `-H 'Host: ...'` на HTTP не доказывает корректность HTTPS/SNI. Не отключать проверку TLS ради удобства.
6. **Только после подтверждения пути** принимать решение о исправлении NPM proxy host, upstream, DNS, `listen`, `root`/`index` или повторном reload. Не выполнять автоматическое изменение reverse proxies ради устранения диагностического 404.

## Применение к KAS Web и смежным проектам

- У KAS WEB свои listener/Host/Origin и KeenDNS reverse-proxy контракты; связанный исторический KAS [#349](https://github.com/saymer-alt/keenetic-auto-setup/issues/349) о 502/403 и доступности. Не приписывать этим случаям причину NPM без фактического доказательства.
- При будущих read-only web-диагностиках полезно **разделять** `CONFIG_OK`, `PROCESS_RUNNING`, `LISTENING_PORT`, `HTTP_ENDPOINT_MATCH`, `PROXY_CHAIN_MATCH`, `AUTH/ORIGIN_OK`, `FUNCTIONAL_RESPONSE_OK`; эти статусы не тождественны. Не создавать отдельный фоновый health-monitor или третий Doctor только ради этого эпизода.
- Если URL отвечает 404, логировать безопасные метаданные: vantage (LAN/WAN/router/container), target host, порт/схема, HTTP status, response Server header при наличии и **без** секретных заголовков/тела. Сигнатура OpenResty служит подсказкой, не доказательством конкретного NPM.
- Поскольку это чужая среда и KAS не проверял её, **реального KAS бага нет**. Любая реализация диагностики требует отдельной Issue/Proof Before Build и тестов на допустимых маршрутах, без увеличения surface сети и без обхода аутентификации.
