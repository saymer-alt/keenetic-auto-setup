# KAS-VERIFY-001 — независимая проверка и честные доказательства

**Решение владельца: 10.11.2026.** План внедрения: [Issue #504](https://github.com/saymer-alt/keenetic-auto-setup/issues/504). Дополняет [Конституцию](CONSTITUTION.md), [стратегию тестирования](TESTING_STRATEGY.md), [контракт задач](AGENT-TASK-CONTRACT.md).

## Обязательные правила

1. **Мнение ИИ, согласие нескольких агентов, текст Issue/PR и зелёная надпись в UI — не доказательство.** PASS допускается только для конкретного теста после фактического исполнения в подходящей среде, проверки наблюдаемого результата относительно заранее согласованного контракта и привязки к точному SHA.
2. **NOT_TESTED не превращается в PASS на основании предположения.** Также не повышать UNKNOWN, SKIPPED, UNSUPPORTED, TIMEOUT, отсутствие артефакта, чужой/старый SHA или MOCK-результат. Для обязательного испытания без доказательства итог — BLOCKED; подтверждённое нарушение — FAIL. Не обходить проверки через skip/continue-on-error.
3. Статусы PLANNED, IMPLEMENTED, MOCK PASS, CI PASS, EMULATOR PASS, FIELD PASS, MERGED и PUBLISHED всегда разные. CI PASS не равен FIELD PASS. Список реально выполненных сценариев, артефакт и URL CI должны быть проверяемы независимо от утверждений агента.
4. Агент, изменяющий production-код, не имеет права скрытно ослаблять тесты, менять ожидаемые результаты под реализацию, отключать проверки, удалять негативные сценарии или объявлять их несущественными. Любое ослабление — отдельное обсуждение и owner GO. Все изменения тестов должны быть видны в diff.
5. Для задач с риском владелец утверждает **пользовательские инварианты**, а не внутреннее устройство алгоритма: наблюдаемый успех, запреты, негативные сценарии и восстановление. Если требования ошибочны, тест тоже может быть ложноположительным — нужен независимый review сценариев.
6. Проверка GitHub CI относится только к **точному checkout SHA**. В PR merge SHA и head SHA могут различаться; оба фиксируются отдельно. Нельзя переносить результаты старого коммита на новый. Физические испытания требуют отдельного разрешения владельца с резервной копией и откатом.

## Уровни доказательств (не взаимозаменяемы)

| Класс | Что подтверждает | Чего не подтверждает |
| --- | --- | --- |
| STATIC | Синтаксис/структуру | Работу программы |
| LOCAL_MOCK / CI_LINUX_MOCK | Поведение на контролируемых фикстурах и негативных сценариях | Живой DNS, WAN, firmware и реальный роутер |
| QEMU_USER | Выполнение бинарника под эмуляцией ISA | Полноценную KeeneticOS |
| KEENETIC_EMULATOR | Наблюдение в гостевой системе с доказанной изоляцией | Физическое устройство |
| PHYSICAL_ROUTER | Конкретный экземпляр/модель, прошивку, ABI и сценарий | Любые другие платформы и ситуации |

## Пять механизмов

1. **Контрактные тесты.** Перед кодом записать на понятном русском инвариант, запрещённые побочные эффекты, позитивный/негативный исход и oracle, который не зависит от сообщения самого проверяемого компонента.
2. **Black-box.** Проверять entrypoint извне: сервисная идентичность, фактический порт, реальный DNS-ответ, таблица маршрутизации, сохранение конфигурации и rollback. Например, exit code 0 установщика MagiTrickle не доказывает, что DNS работает. Мок нельзя называть живым наблюдением.
3. **Fault injection.** Изолированно моделировать обрыв передачи, отказ OPKG, недоступность DNS, занятый порт, умерший процесс, неполную запись и таймаут. Проверять не только обнаружение, но и сохранность предыдущего состояния. На рабочих роутерах без отдельного owner GO разрушительные испытания запрещены.
4. **Mutation testing.** Намеренно ломать копию production-кода и доказывать, что существующие тесты ловят дефект. Выжившие мутации — пробел покрытия. Негативные мутации JSON-отчёта проверяют **только валидатор доказательств**, а не качество тестирования runtime.
5. **Аппаратная приёмка.** Отдельная матрица по модели/прошивке/ABI, ограниченный сценарий, восстановление, внешний наблюдатель, время и SHA. Если устройство недоступно, честный статус FIELD NOT_TESTED.

## Как защищаемся от одинаковой ошибки нескольких ИИ

- Ожидаемый результат формулируется до изменения кода и не переписывается для удовлетворения реализации.
- Отдельный проверяющий пытается придумать сценарий, где все тесты зелёные, а реальное требование нарушено.
- Метаморфные проверки: изменяем одну предпосылку, требование сохраняется. Например, при отказе всех прокси запрещённый DIRECT не должен внезапно стать разрешённым.
- Изменения контрактов, тестов, CI, AGENTS.md и этого документа отдельно отмечаются в PR; при ослаблении — отдельное согласие владельца.
- Сам репозиторий не является доверенной внешней инстанцией: обладатель прав записи может изменить и программу, и тесты. Нужны branch rulesets, проверка diff, независимая проверка CI run через GitHub API, при возможности отдельный защищённый workflow. CODEOWNERS сам по себе без соответствующей защиты недостаточен.
- Две ИИ-модели с одинаковыми предпосылками не заменяют внешнего наблюдения, заранее зафиксированного контракта и негативных тестов.

## Этап A — то, что действительно автоматизировано

Скрипт [independent-verification.py](../tests/independent-verification.py) запускается без LLM:

- `python3 tests/independent-verification.py selftest` — 9 намеренно испорченных комбинаций отчёта; NOT_TESTED, SKIPPED, отсутствующий exit code, несоответствие SHA/источника и прочие дефекты обязаны блокироваться. Это **метатест отчёта**, не mutation coverage production-кода.
- `python3 tests/independent-verification.py run --report /tmp/kas-independent-verification.json` — повторный фактический запуск трёх существующих регрессий MagiTrickle runtime, rollback fault и watchdog diagnostics; отсутствие теста, timeout или ненулевой exit завершает команду с ошибкой.
- В CI результат привязан к checkout SHA, записывается secret-free JSON с test ID, кодом завершения, digest вывода, source и явными FIELD NOT_TESTED / EMULATOR NOT_TESTED; артефакт загружается отдельно. Прошедшие фикстуры классифицируются только как CI_LINUX_MOCK.

**Ограничения этапа A:** оболочка повторно запускает существующие mock-регрессии, но не создаёт нативную проверку роутера, сетевой black-box или отдельный production mutation score. Этапы B–F описаны в [Issue #504](https://github.com/saymer-alt/keenetic-auto-setup/issues/504) и остаются незавершёнными до объективной приёмки.

## Definition of Done для каждого рискованного PR

Согласованный ожидаемый результат; независимый источник наблюдения; идентификатор теста; результат и source; точный SHA; URL действительного CI run; негативная проверка; rollback; отдельный FIELD verdict, когда нужен; остаточные NOT_TESTED; отдельное решение владельца для merge, release и live-операций.
