# 35 — One-action настройка Mihomo в KAS Web: Stage A (issue #425, comment 6721367077)

**Статус:** Stage A — только проектирование и картирование существующих механизмов. Production-код не меняется. Документ отвечает на design-gate из решения владельца от 2026-11-08 (comment [6721367077](https://github.com/saymer-alt/keenetic-auto-setup/issues/425#issuecomment-6721367077)).

**Исходная точка:** Phase 0 `kas-mini` — экспериментальный генератор YAML в web4core ([PR web4core#28](https://github.com/saymer-alt/web4core/pull/28), Draft, head `519da90a6bc75049498169f0fcd7a02054f7e104`, 41/41 тестов, `mihomo -t` 4/4 на Mihomo v1.19.33). Вывод Phase 0: скачивание YAML — не целевой пользовательский исход. Цель следующего этапа — «вставил URI → одна кнопка → KAS сгенерировал, провалидировал, применил и перезапустил Mihomo, честно отчитался», без SSH и ручного сохранения/загрузки файла. Скачивание остаётся advanced/fallback-UX.

**Правило reuse (владелец):** канонический путь импорта уже существует; запрещено создавать второй привилегированный импортёр, второй механизм перезапуска, второй rollback-движок или фоновую службу. Всё новое — тонкий фронтенд-хэндофф к существующему бэкенду.

Все факты этого документа проверены 2026-11-08 на `main` @ `47b0f2f2` (kas-network-doctor/docs) и web4core @ `519da90`.

## 2. Инвентарь существующих механизмов (reuse-база)

### 2.1 Каноническая транзакция импорта — `config-import.sh`

Единственный владелец мутаций конфига. Последовательность (docs/13, скрипт `main`): staging candidate рядом с `config.yaml` → **проектный гейт `mixed-port: 7890` до остановки сервиса** (`grep -Eq '^[[:space:]]*mixed-port:[[:space:]]*7890…'`, строка 810: «Project contract missing… Existing config was not changed») → общий lifecycle lock (docs/19) → флаг `/tmp/mihomo.maintenance` для watchdog → остановка работающего Mihomo с подтверждением → `mihomo -t` (валидация одним инстансом) → backup предыдущего валидного конфига в `config.yaml.bak` → атомарный same-filesystem `mv` → запуск сервиса → проверка процесса **и порта 7890** → при ошибке validation/start/port — атомарный rollback из `.bak` и возврат прежнего состояния сервиса. Recovery-импорт (#320): отсутствующий/пустой/невалидный текущий конфиг не блокирует импорт; хороший `.bak` никогда не перезаписывается; повреждённый оригинал побайтово сохраняется в `config.yaml.invalid.N` через атомарный `ln` без `-f`. Опциональный гейт `KAS_EXPECTED_SOURCE` (filter editor): побайтовое сравнение on-disk конфига с одобренным снапшотом под lock'ом и перед rename.

`mihomo -t` — проверка синтаксиса/структуры конфига. Это **не** доказательство, что подписки скачались, узлы подключаются, TLS проходит и клиентский трафик маршрутизируется.

### 2.2 Бэкенд Web-импорта — `web/control-center/import.go` (уже в main)

- `POST /api/config/import` — единственный мутационный эндпоинт. Гейты: разрешённый Origin, `Content-Type: application/x-yaml`, `X-KAS-Confirm: apply`, `Sec-Fetch-Site: same-origin` (если предъявлен); ≤ 1 МиБ (клиент и сервер); UTF-8 без NUL; **быстрый контрактный гейт `mixed-port: 7890`** (`validYAMLBody`) до постановки в работу. Ошибки: `REQUEST_BLOCKED` 403, `FILE_TOO_LARGE` 413, `INVALID_YAML` 400, `BUSY` 409, `STAGING_FAILED` 503, `IMPORTER_UNAVAILABLE` 503.
- Очередей нет: при `panelUpdateBusy || importRunning || doctorRunning || shuttingDown` → `BUSY`. Staging: `/tmp/.kas-import-*.yaml`, `O_EXCL`, 0600, удаление в `defer`; путь от клиента не принимается.
- Запуск: `sh -s -- <staged-file>` с **встроенным при сборке** (`go generate`) снимком канонического `config-import.sh` той же ревизии. stdout/stderr импортёра **намеренно отбрасываются** (не в HTTP, не в логи): вывод валидации может содержать секреты конфига. Ответ 202 `{id, state: RUNNING, timestamp, source}`; работа продолжается после закрытия браузера (context не привязан к HTTP-запросу).
- `GET /api/config/operation` — состояние последней операции: `RUNNING` / `OK` (+`exit_code`) / `FAIL` (+`exit_code`, `IMPORT_FAILED`); пусто → `UNKNOWN` + `NO_OPERATION`. Запись **в памяти процесса, не персистентна**: рестарт панели посреди операции даёт `UNKNOWN` — честно, без выводов о rollback.
- Сопутствующее: `GET /api/config/download` — текущий on-disk YAML (fallback-UX уже существует); `GET /api/filter/providers` + node-list API — read-only имена провайдеров/узлов из живого Mihomo API (используется filter editor'ом).
- Безопасность listener'а: Host/Origin/CSRF-класс защит, отсутствие CORS, single-flight — без изменений.

### 2.3 Фронтенд панели — `web/control-center/web/app.js` (уже в main)

Секция «Конфигурация Mihomo»: файл или paste-textarea → `applyYAML()`: guard'ы занятости → `window.confirm` «Применить новую конфигурацию вместо текущего config.yaml?» → POST → polling `/api/config/operation` только пока `RUNNING` → честные состояния: `OK` с кодом завершения, `FAIL` с кодом завершения и советом «проверьте фактическое состояние через Doctor или SSH», коды ошибок, предупреждение «Mihomo может ненадолго перезапуститься… не перезагружайте роутер во время операции». Fake-успех при обрыве связи невозможен: наблюдение (`importObserved`) и показ результата отделены от факта применения.

**Вывод reuse:** бэкенд-транзакция, защита listener'а, single-flight, async-операция с ID, polling и честная отчётность уже реализованы и протестированы (Go-регрессии `import_test.go`). Интеграция генератора = **только фронтенд-хэндофф**: кнопка, confirmation, тот же POST. Ни один бэкенд-файл в этом этапе не обязан меняться.

### 3.2 Ключевой конфликт (гейт mixed-port)

UI kas-mini позволяет `mixedOn=off` и любой порт. Оба варианта **проваливают оба гейта**:

| Состояние генератора | YAML содержит | `validYAMLBody` (import.go) | `config-import.sh:810` |
| --- | --- | --- | --- |
| `mixedOn=ON`, `mixedPort=7890` (дефолт) | `mixed-port: 7890` | ✅ проходит | ✅ проходит |
| `mixedOn=off` | строка `mixed-port:` **удалена** (якорь-удаление) | ❌ 400 `INVALID_YAML` | ❌ abort до остановки сервиса |
| `mixedOn=ON`, `mixedPort=7891` | `mixed-port: 7891` | ❌ 400 `INVALID_YAML` | ❌ abort до остановки сервиса |

Это ровно несовместимость, зафиксированная владельцем. **Решение Stage A (дефолт владельца, не ослабляя гейт):**

1. **KAS-профиль генератора** — режим встраивания, в котором `mixedOn` зафиксирован ON, порт зафиксирован 7890, соответствующие инпуты скрыты/заблокированы с пояснением «контракт KAS». Импортируемый YAML всегда содержит `mixed-port: 7890`.
2. Режимы вне профиля (mixed-off, порт ≠ 7890) остаются только в **fallback download**-пути: кнопка скачивания генерирует YAML без POST в панель; подпись рядом с кнопкой: «этот вариант не устанавливается автоматически — примените вручную по docs/13». Никакой автозагрузки по paste/view (владелец: no hidden apply on mere paste/view).
3. Гейт импорта **не ослабляется и не параметризуется**. Изменение контракта `mixed-port: 7890` — отдельное owner-решение вне этого этапа.
4. Клиентский pre-check перед POST зеркалирует `validYAMLBody` (наличие строки `mixed-port: 7890`, размер, UTF-8) — fail-closed до сетевого запроса. Серверный гейт остаётся авторитетным.

## 4. Дизайн интеграции: тонкий хэндофф

### 4.1 Способ встраивания генератора

KAS Web — офлайн-панель без внешних ассетов. Единственный совместимый способ — **вендоренный собранный бандл** kas-mini (esbuild IIFE, внешних зависимостей нет) как статический файл панели:

- файл-проверка происхождения: заголовок с source-repo, commit-SHA, размером/контрольной суммой; обновление только явным sync-PR (аналог дисциплины `go generate` для `mihomo-doctor.sh`, но без go generate — сверка checksum в CI);
- генерация YAML остаётся **единственной** (в бандле web4core); панель не получает собственной реализации генератора, парсера URI или валидатора подписок — «не создавай второй механизм» относится и к генерации;
- разметка: kas-mini рендерится в выделенном контейнере секции «Конфигурация Mihomo»; handoff-поверхность — существующие `ui.canDownload()` (`!stale && yaml.length>0`) и содержимое `preview`-textarea; контракт бандла не меняется.

### 4.2 Один явный операторский шаг

- Кнопка **«Настроить и запустить Mihomo»** (RU/EN) активна только при `canDownload()`.
- Подтверждение — явный модальный шаг (не `window.confirm`-замалчивание), текст называет: замена **всего текущего** `config.yaml`, остановка и перезапуск Mihomo, наличие backup/rollback, запрет перезагрузки роутера посреди операции. Единственное действие оператора авторизует полную замену конфига.
- Дальше — существующий путь без изменений: `applyYAML()` → `POST /api/config/import` (`application/x-yaml`, `X-KAS-Confirm: apply`) → 202 → polling. Скачивание/preview остаются опциональным fallback.

### 4.3 Preflight fail-closed (клиент, до POST)

| Проверка | Механизм | Отказ |
| --- | --- | --- |
| Разбор URI/подписок | валидатор kas-mini (уже есть) | ошибка с указанием строки/URI, генерация не выполняется |
| Формат подписки | строгий URL-валидатор | честное сообщение; **не** заявляем конвертацию произвольных plaintext/base64-ссылок (владелец: без отдельного скоупа) |
| Контракт 7890 | KAS-профиль + клиентский mirror-чек YAML | блокировка POST, подсказка fallback download |
| Размер/кодировка | ≤ 1 МиБ, UTF-8, без NUL | блокировка POST |
| Занятость панели | существующие guard'ы UI (`submitting`, `RUNNING`, update/MT busy) + серверный `BUSY` 409 | кнопка заблокирована, причина показана |
| Доступность сервисов | `/api/status` (файлы-свидетельства, состояние честно UNKNOWN) — информативно; остановку/запуск выполняет импортёр | не блокирует POST (транзакция сама провалидирует) |
| Версия панели | существующий механизм версий/каналов — вне гейта импорта | — |

Скрытые/автоматические применения нет: paste URI и просмотр preview ничего не применяют.

### 4.4 Ограниченная stateful-операция и UI-состояния

Операция уже ограничена и stateful (202 + ID, продолжение после обрыва). Таблица состояний UI (все — существующая семантика, никаких новых):

| Состояние | Доказано | Что видит оператор |
| --- | --- | --- |
| idle / preflight-fail | ничего не изменено | причина отказа, fallback download |
| подтверждение | ничего не изменено | полный текст замены/перезапуска |
| RUNNING (poll) | транзакция идёт на роутере независимо от браузера | прогресс-баннер «Не выключайте роутер» |
| OK (exit 0) | конфиг валиден (`mihomo -t`), сервис запущен, порт 7890 слушается (внутри транзакции) | «применено, код 0» + слой проверки ниже (§5) |
| FAIL (exit ≠ 0) | отказ транзакции; rollback выполнен **самим импортёром** | код + совет проверить фактическое состояние (UI не утверждает rollback без независимой проверки — семантика уже в main) |
| BUSY 409 | параллельная операция | отказ, причина |
| Обрыв браузера | операция продолжается | при возврате polling показывает реальное последнее состояние; fake-успех невозможен |
| Рестарт панели посреди операции | запись операции в памяти потеряна | `UNKNOWN` + `NO_OPERATION` + совет Doctor/SSH; **никаких** выводов о rollback |

Дополнение этого контракта (персистентная запись операции) — возможное будущее расширение бэкенда, в минимальный этап не входит.

### 4.5 Восстановление после обрыва связи

Покрыто существующей механикой: операция отвязана от HTTP-запроса (`import.go`), polling возобновляется при возврате на страницу и после рестартов вкладки. Сценарий «панель обновилась/переустановилась во время импорта» даёт UNKNOWN — текст результата обязан это называть (уже так: «Check the actual state with Doctor/SSH»). Отдельного «восстановления» проектировать не нужно — единственное требование: не изобретать ложный успех/откат.

## 5. Проверка результата: три слоя доказательности

| Слой | Что это | Чем доказывается в этом этапе |
| --- | --- | --- |
| 1. Валидный конфиг | структура/syntax | exit 0 импортёра (`mihomo -t`) |
| 2. Сервис жив | Mihomo запущен и слушает | внутренняя проверка транзакции (процесс + порт 7890); после — `/api/status` (файлы-свидетельства, семантика UNKNOWN сохраняется) |
| 3. Реальная связность | подписки скачаны; трафик ходит | **(a)** ограниченная post-apply проверка через существующий read-only provider-names API: провайдеры загружены и содержат узлы > 0 → факт «Mihomo скачал и разобрал подписки»; API недоступен → честное UNKNOWN. **(b)** Интернет через прокси: `NOT TESTED` в этом этапе — панель не выполняет сетевых проб; Network Doctor остаётся CLI-инструментом (docs/33). Опциональный следующий шаг (отдельный GO): вызов существующего канонического route-check/Doctor-семейства из панели |

Пост-проверка (a) — единственная новая точка, и она переиспользует существующий бэкенд-API, не создавая нового механизма проб.

**Различение rollback и отказа подписки:** FAIL импортёра → импортёр откатил конфиг сам; успех импортёра при недоступном провайдере → конфиг валиден и применён, откат **не** выполняется (правильное поведение: проблема вне транзакции). Тексты результата обязаны это различать; автоматический «откат на неудачную подписку» не проектируется (никаких авто-исправлений — docs/33).
