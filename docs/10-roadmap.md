## 🚧 Ближайшие задачи (Short-term)

---

### 1. Улучшение install.sh

- [x] ранняя проверка RAM до сетевых загрузок/изменений
- [x] resource-profile contract 20260921_3: 128MB-класс — только внешний /opt + внешний storage-backed swap >=384 МБ, иначе installer FAIL; 256/512 МБ-класс — ожидается zRAM или внешний storage-backed swap, отсутствие обоих WARN; внешний swap <1× detected RAM WARN, 1×..3× INFO, preferred target 3× RAM, cap 2 ГиБ, >2 ГиБ installer ERROR/Doctor FAIL; >512 МБ-класса swap/zRAM опциональны; совместный zRAM + disk/file swap получает WARN по vendor guidance; updater существующих legacy-инсталляций profile-нарушения не блокирует
- [x] явная диагностика критических ошибок: Proxy client, полный read-back проектного ProxyN, обязательный bootstrap, DNS interception и финальный self-check
- [x] проверка обязательного DNS-контракта: `dns-proxy intercept enable` применяется и немедленно читается обратно
**Не активная задача:** отдельную диагностику здоровья upstream DNS добавлять только после воспроизводимого практического кейса; не превращать её в hard gate установки.

---

### 2. Watchdog: текущий объём считаем достаточным

- [x] защита от ложных рестартов (lock-файл, cooldown 300 с, whitelist-fallback
      WAN-проверки, jitter — уже в текущей версии watchdog)
- [x] уменьшить шум healthy-логов: проверки остаются каждые 5 минут, `[OK]` heartbeat — не чаще раза в 20 минут; WARN/restart/rate-limit, первый recovery `[OK]` и смена WAN-пути `primary ↔ whitelist` пишутся сразу
- [x] текущая проверка WAN → port 7890 → GET через SOCKS5h признана достаточной для рабочего профиля

**Осознанно не усложняем сейчас:** отдельные уровни логирования watchdog, дополнительные
фоновые probe'ы и более тяжёлую проверку upstream. На слабых роутерах каждая новая
периодическая проверка — это CPU/RAM/сеть, а текущая схема уже решает реальный кейс
самовосстановления. Возвращаться к расширению только после воспроизводимой полевой
проблемы, которую текущая проверка не видит.

---

### 3. Обновление и автообновление компонентов

- [x] обновление Mihomo без переустановки (`update-mihomo.sh`)
- [x] обновление watchdog (`update-watchdog.sh`)
- [x] безопасные ручные update-скрипты (валидация, maintenance coordination, rollback)
- [ ] **Следующий этап после v1.4.0:** отдельный opt-in `install-auto-update.sh`; основной `install.sh` автообновление не включает
- [ ] `install-auto-update.sh` устанавливает локальный auto-updater и суточный cron с jitter; пользователь включает этот механизм отдельным осознанным запуском
- [ ] auto-updater читает manifest из production/`stable` и обновляется только при двух разрешениях: локальный opt-in + GitHub-флаг, например `enabled=1` и `version=1.4.2`
- [ ] пользовательские `config.yaml`, MagiTrickle-конфиги и HWID-зависимые настройки автообновление не трогает

---

### 4. bypass_wa: не расширять без реального VoIP-кейса

Текущий фиксированный профиль оставляем как есть, пока звонки работают стабильно.

Отложенные идеи — **не активный техдолг**: расширяемый список портов, отключение через
переменную и дополнительные VoIP-сервисы. Возвращаемся к ним только после конкретного
воспроизводимого сценария. Для рабочего VoIP надёжность важнее универсальности.

## 🔧 Среднесрочные задачи (Mid-term)

---

### 5. Мониторинг (отложено по дизайну)

Отдельный health-check endpoint и собственный внешний сбор логов сейчас не нужны.
Doctor + watchdog + MetaCubeXD закрывают локальную эксплуатацию; внешний мониторинг
лучше добавлять существующим агентом, если такая задача реально появится.

Не строим второй monitoring stack внутри слабого роутера ради самой возможности.

---

### 6. Улучшение диагностики

- [x] единая read-only команда диагностики — `mihomo-doctor.sh`
- [x] вывод состояния системы, Mihomo, ProxyN, DNS, MagiTrickle, watchdog, истории и маршрутизации
- [x] финальный self-check в `install.sh`
- [x] маленький постоянный contract smoke test — `tests/contracts.sh`
- [x] отдельные CI-регрессии для высокорисковых транзакций — `tests/transaction-invariants.py` (updater rollback/order, watchdog atomic update/preservation, MIPS migrator)
**Правило развития Doctor:** расширять только по новым воспроизводимым полевым кейсам; не превращать его в repair tool.

## 🧪 Долгосрочные идеи (Long-term)

---

### 7. Web-интерфейс

Отдельный проектный GUI не строим: для управления Mihomo уже используется MetaCubeXD.

Документационная часть закрыта энциклопедией: интерфейс MetaCubeXD, Controller/API и
безопасность, proxy-providers, GEO-данные и логи. Если понадобится project-specific
status endpoint или кнопка обслуживания — это должна быть маленькая задача с реальным
кейсом, а не начало нового GUI.

локальными. Планируемый opt-in auto-updater обновляет только project-managed
компоненты и не превращается в систему централизованной конфигурации.

## 📌 Как принимать решения

Перед добавлением фичи:

1. Это реально нужно?
2. Это усложняет систему?
3. Это увеличивает риск поломки?

Если ответ "да" на 2 и 3:

👉 не добавлять
