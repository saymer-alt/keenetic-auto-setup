## 1. Перед началом

Проверьте каждый пункт — большинство неудачных установок упираются в один из них:

| Требование | Как проверить | Примечания |
| --- | --- | --- |
| Keenetic с **256 МБ RAM и больше** | спецификация / `free` на роутере | **128 МБ не поддерживаются.** tmpfs дестабилизирует такие устройства — проверено в продакшене, это не теоретическое предупреждение |
| **Установлен Entware** (`/opt` существует) | команда `opkg` работает | см. шаг 2 |
| **SSH-доступ** под root | `ssh root@192.168.1.1` | KeeneticOS: SSH включается в *Управление → Сеть* |
| **Интернет доступен с роутера** | `opkg update` проходит без ошибок | типовые блокеры — DNS и время (см. [Типовые проблемы](#12-типовые-проблемы)) |

Проверено на: KN-1810, KN-3811, KN-1913 (см. [CHANGELOG](../CHANGELOG.md)).

Какой установщик нужен:

```bash
opkg print-architecture | awk '/^arch/{print $2}'
```

- `aarch64-3.10` (или `armv7-3.2`) → **`install.sh`** (полный стек)
- `mipsel-3.4` → **`install_7621.sh`** (legacy, сокращённый стек — см. [раздел 13](#13-особенности-mt7621--mipsel))

## 2. Подготовка Keenetic и Entware

Тулкит устанавливается *в* Entware — сам Entware он не устанавливает.

1. В KeeneticOS включите компонент OPKG/Entware (*Общие настройки → Opkg / Entware* или через меню компонентов KeeneticOS в зависимости от прошивки) и выберите накопитель: внутренняя память (на моделях, которые это поддерживают) или USB-диск с файловой системой ext4.
2. Перезагрузите роутер, когда компонент попросит.
3. Проверьте по SSH:

```bash
ls /opt                    # корень Entware должен существовать
opkg update                # должно завершиться без ошибок
date                       # сбитое время → позже упадут SSL-ошибки
```

Если `opkg update` падает: сначала почините DNS (`cat /opt/etc/resolv.conf`, при необходимости `echo "nameserver 1.1.1.1" > /opt/etc/resolv.conf`) и время (`ntpd -q -p pool.ntp.org`) — это две самые частые причины.

## 3. Установка

### 3.1 Команда

**Современные роутеры (ARM, рекомендуется):**

```bash
opkg update && opkg install curl && \
curl -fSsL https://raw.githubusercontent.com/saymer-alt/keenetic-auto-setup/main/install.sh | sh
```

**Старые роутеры (MT7621/mipsel)** — legacy-установщик, обходит сломанный TLS:

```bash
curl -k -fSsL https://raw.githubusercontent.com/saymer-alt/keenetic-auto-setup/main/install_7621.sh | sh
```

### 3.2 Что именно делает `install.sh`

По порядку:

1. `opkg update`, затем ставит `ca-bundle`, `curl`, `jq`, `nano`, `cron` (уже установленные пропускает).
2. Создаёт политику маршрутизации `bypass_wa` (только если её ещё нет).
3. Включает **перехват транзитного DNS** Keenetic (`dns-proxy intercept enable`, затем `system configuration save` — применяется, только если ещё не включён): классические port-53 запросы клиентов LAN, адресованные напрямую внешним резолверам, перенаправляются в DNS-прокси роутера, где их видит MagiTrickle (подробности — в [разделе 6.1](#6-magitrickle)). Это часть автоматической установки — ручного post-install шага для DNS нет. Только классический DNS; DoH/DoT не затрагиваются.
4. **Только в RAM-режиме:** скачивает `S00ubifs` в `/opt/etc/init.d/` и запускает его (tmpfs для `/opt/tmp`, `/opt/var/log`, `/opt/var/run`).
5. Определяет архитектуру и скачивает подходящий **mihomo `.ipk`** из релизов [`saymer-alt/entware-go`](https://github.com/saymer-alt/entware-go) (GitHub API с тремя fallback'ами: jq → grep по JSON → повторный запрос → парсинг HTML).
6. **Создаёт интерфейс Proxy0** — единственный мост Keenetic → Mihomo — на `127.0.0.1:7890` (SOCKS5, UDP включён) с человекочитаемым именем `mihomo t2s0` и сохраняет конфигурацию.
7. Устанавливает **MagiTrickle** (добавляет его репозиторий пакетов, ставит, запускает).
8. Ставит VoIP-хук `020-bypass_wa.sh` в `/opt/etc/ndm/netfilter.d/`.
9. Устанавливает **watchdog** в `/opt/etc/cron.5mins/` и подключает к cron (если уже есть run-parts-запись `cron.5mins` — используется она; иначе добавляется прямая строка в crontab).
10. Перезапускает `S99mihomo` и проверяет, что порт `7890` слушается.

### 3.3 Безопасно ли запускать повторно?

Установщик написан идемпотентным: каждый изменяющий шаг сначала проверяет, существует ли объект (пакеты, политика, Proxy0, запись в crontab). Повторный запуск ничего не задублирует.

Нюанс: mihomo `.ipk` скачивается при каждом запуске — `opkg` просто пропустит установку, если та же версия уже стоит.

Ещё нюанс: **если Proxy0 уже существует, его конфигурация не трогается** (включая человекочитаемое описание). Эта ветка нарочно «бестактная наоборот»: установщик никогда не переписывает уже работающую постоянную конфигурацию роутера.

То же относится к перехвату транзитного DNS: установщик сначала проверяет текущее состояние и включает его (с сохранением конфига) только если он не был включён. Если вы на конкретном роутере сознательно держите транзит DNS открытым — уберите этот блок из установщика перед повторным запуском: ре-запрос включит его снова.

### 3.4 Ожидаемый результат

```text
[setup] ...
[OK] Done
```

Предупреждение `WARN ... port 7890 not listening` в конце почти всегда означает, что `config.yaml` отсутствует или неверен — переходите к разделу 5.

## 4. RAM и disk режим

`install.sh [ram|disk]`, по умолчанию `ram`.

| | `ram` (по умолчанию) | `disk` |
| --- | --- | --- |
| Логи, tmp, pid-файлы | tmpfs (RAM) через `S00ubifs` | остаются на накопителе |
| Износ флешки | минимальный | обычный для Entware |
| Данные после reboot | логи пропадают (так задумано) | сохраняются |
| Кому подходит | внутренний флеш, долгая работа 24/7 | устройства с малой RAM, когда нужны постоянные логи |

`S00ubifs` подбирает размеры tmpfs по доступной RAM (профили <40 МБ, <80 МБ, ≥80 МБ свободной памяти). Подробности: [docs/06-s00ubifs.md](06-s00ubifs.md).

Ошиблись режимом: повторный запуск установщика с другим режимом безопасен (уже сделанные шаги пропускаются), но «хвосты» старого режима уберите руками — например `/opt/etc/init.d/S00ubifs` при переходе на `disk`.

## 5. Конфигурация Mihomo

Без валидного конфига ничего не работает. **После установки этот шаг обязателен.**

```bash
nano /opt/etc/mihomo/config.yaml
```

Минимальный рабочий пример:

```yaml
mixed-port: 7890
allow-lan: true
mode: rule
log-level: info

proxies:
  - name: "server"
    type: vless
    server: "YOUR_SERVER"
    port: 443
    uuid: "YOUR_UUID"
    tls: true

proxy-groups:
  - name: "Proxy"
    type: select
    proxies:
      - "server"

rules:
  - GEOIP,private,DIRECT
  - MATCH,Proxy
```

Примечания:

- `allow-lan: true` — именно это позволяет устройствам LAN (например, браузеру с FoxyProxy) обращаться к `<ip-роутера>:7890` напрямую. При `false` прокси отвечает только на самом роутере.
- DoH: «быстрые» резолверы часто оказываются нестабильными. Держитесь проверенных — `https://cloudflare-dns.com/dns-query`, `https://dns.google/dns-query`, `https://dns.quad9.net/dns-query`.
- Привязка исходящих интерфейсов: запустите прилагаемый хелпер — он выдаёт готовые строки `interface-name:` для ваших WAN-интерфейсов:

```bash
sh mihomo-interface-check.sh    # или скачайте его из репо прямо на роутер
```

Применить и проверить:

```bash
/opt/etc/init.d/S99mihomo restart
/opt/etc/init.d/S99mihomo status      # ожидаем: alive
curl -x socks5://127.0.0.1:7890 https://ipinfo.io   # ожидаем IP выходного сервера
```

Конфиг можно проверить на синтаксис без перезапуска:

```bash
mihomo -d /opt/etc/mihomo -t
```

Чтобы не писать YAML руками, а собрать конфиг из своих ссылок/подписок: [saymer-alt/link-generators](https://github.com/saymer-alt/link-generators) (работает полностью в браузере, ничего никуда не отправляется).

### 5.1 Браузерный прокси (FoxyProxy) и WebRTC

Браузерный сценарий из use cases в README: включите `allow-lan: true`, направьте браузерное расширение вроде FoxyProxy на `<ip-роутера>:7890` (SOCKS5) и добавьте шаблоны для нужных сайтов. Это покрывает обычный веб-трафик браузера.

**WebRTC — отдельный механизм, и рассматривать его нужно отдельно.** WebRTC устанавливает собственные медиа-пути (ICE/STUN) во многом независимо от прокси-настроек браузера; браузеры, как правило, не отправляют WebRTC через SOCKS5-прокси. Поэтому в прокси-сценарии сайт, выполняющий WebRTC/STUN-проверки, может увидеть сетевую информацию, отличающуюся от выхода прокси — например, публичный адрес, который наблюдает STUN-сервер. Что именно раскрывается — зависит от браузера, его версии и вашей сети: современные браузеры по умолчанию скрывают локальные адреса LAN за mDNS-именами, но поведение с рефлексивными (публичными) кандидатами различается, и единого утверждения «для всех браузеров» не существует. Это не гарантированная утечка — и не гарантированная защита: проверяйте на своей конфигурации.

Что делать, по браузерам (механизмы разные — универсальной настройки нет):

- **Chromium-семейство (Chrome, Edge, …):** встроенной пользовательской настройки нет; используйте расширение, управляющее обработкой IP в WebRTC (у uBlock Origin есть настройка защиты WebRTC; расширения типа «WebRTC Network Limiter» выставляют тот же браузерный policy).
- **Firefox:** `about:config` — `media.peerconnection.ice.default_address_only` и `media.peerconnection.ice.no_host` (ограничивают ICE-кандидатов), либо полностью отключите WebRTC — `media.peerconnection.enabled = false`, если браузерные звонки вам не нужны.
- **Safari:** сопоставимой встроенной настройки нет — возможности ограничены; если изоляция WebRTC важна, относитесь к Safari отдельно.

После настройки проверьте себя на тестовой странице WebRTC (например, browserleaks.com/webrtc) с включённым прокси: адреса, которые она показывает, не должны противоречить вашим ожиданиям от сценария.

Про scope: это предупреждение относится **только к браузерному прокси-сценарию**. При маршрутизации всей сети через Keenetic (настройка по умолчанию) UDP — включая WebRTC — идёт по policy-роутингу роутера, как и любой другой трафик, и браузерное ужесточение WebRTC этим проектом не требуется.

## 6. MagiTrickle

Ставится только `install.sh` (в 7621-установщике его нет).

MagiTrickle — уровень принятия решений: он смотрит на DNS-запросы и по каждому домену/подсети выбирает маршрут — напрямую или через туннель/политику вроде Proxy0. Сам трафик он не передаёт — это делает policy-роутинг Keenetic по его указаниям.

Практическая картина после установки:

- Домены, отправленные вами в прокси, идут `LAN → Proxy0 → Mihomo → ваши серверы → Интернет`. В MagiTrickle/Keenetic прокси-интерфейс отображается в нумерации `t2s` — установщик подписывает Proxy0 как **`mihomo t2s0`**, чтобы соответствие было видно с одного взгляда.
- Всё, что не совпало с правилами, идёт напрямую.
- VoIP-UDP (1400/3478/3482) до Mihomo всё равно не доходит — netfilter-хук `bypass_wa` помечает его в политику `bypass_wa` сразу на VPN-интерфейс.

За веб-интерфейс и управление правилами самого MagiTrickle отвечает его upstream-проект (`bin.magitrickle.dev`) — это за пределами данного репозитория.

### 6.1 Перехват транзитного DNS (управляется установщиком)

MagiTrickle может решать только для тех доменов, которые видит. Задуманная цепочка:

```
Клиент → DNS Keenetic → MagiTrickle → решение о маршруте
```

Если устройство отправляет запросы напрямую внешнему резолверу (прописанный руками `8.8.8.8`, приложение со своим DNS), этот трафик полностью минует уровень принятия решений, и маршрутизация такого устройства тихо выпадает из ваших правил. В KeeneticOS есть ровно под это средство: **перехват транзитных DNS-запросов** (в web UI настройка иногда подписана как разрешение транзитных запросов; CLI `dns-proxy intercept enable`, по умолчанию выключен). Включённый, он перенаправляет классические port-53 запросы, адресованные внешним серверам, в DNS-прокси роутера, где их видит MagiTrickle.

Установщик делает это автоматически — это **часть установки, а не ручной post-install шаг**. Он сначала проверяет текущее состояние (наличие `intercept enable` в running-config), применяет команду только при необходимости и сохраняет постоянный конфиг только при реальном изменении. Команда существует с KeeneticOS 3.06 (кратко отсутствовала в 3.08); при сбое установщик пишет предупреждение и продолжает.

Границы, чтобы никто не ждал лишнего:

- Это **только классический DNS** — это **не** защита от DoH/DoT. Браузер с включённым «безопасным DNS» (DoH) туннелирует запросы поверх HTTPS и проходит мимо порта 53 в любом случае; это клиентская настройка.
- Устройства с прописанными вручную внешними резолверами продолжают работать — их запросы отвечает DNS-прокси роутера через свои настроенные upstream'ы. Редкое исключение: то, что должно ходить на *конкретный* внешний DNS-сервер напрямую по порту 53 (нестандартный split-DNS/AD или DNSSEC-инструменты). Если такое есть — откат на конкретном роутере:

```
(config)> dns-proxy
(config-dnspx)> no intercept enable
(config-dnspx)> exit
(config)> system configuration save
```

… и уберите блок перехвата из установщика для этого роутера — иначе повторный запуск включит его снова. Всё остальное в вашей DNS-конфигурации (DoH/DoT-upstream'ы в конфиге Mihomo, собственные резолверы роутера, DNS из DHCP) остаётся нетронутым.

Проверка на роутере:

```bash
ndmc -c "show running-config" | grep "intercept enable"   # ожидаем одну строку в блоке dns-proxy
```

Функциональная проверка с клиента: запрос с явно указанным внешним резолвером (`nslookup example.com 8.8.8.8`) должен по-прежнему проходить — ответ приходит через роутер.

## 7. Watchdog в эксплуатации

### 7.1 Что и в каком порядке проверяется

Каждые 5 минут (cron) со случайной задержкой 0–24 с (busybox-совместимой: `date +%s % 25` — без `$RANDOM`):

1. **WAN — напрямую, без Mihomo.** Основные цели: `cp.cloudflare.com`, `www.google.com`. Если недоступны *все* — включается whitelist-fallback: `gosuslugi.ru`, `ya.ru`, `mail.ru`, `vk.ru`, `vk.com`. Ответил хотя бы один = WAN есть. Не ответил никто → watchdog выходит, **ничего не перезапуская** — отсутствие WAN не означает, что сломан Mihomo.
2. **Порт прокси** — `127.0.0.1:7890` должен принимать TCP-соединения. Порт закрыт → Mihomo, вероятно, упал → рестарт.
3. **Сквозной туннель** — реальный запрос через `socks5h://127.0.0.1:7890` (DNS тоже через туннель) до google должен пройти. Порт открыт, туннель мёртв → рестарт.

Ограничение частоты: минимум 300 с между рестартами, состояние в `/tmp/mihomo_watchdog.restart` с валидацией содержимого. Lock-файл `/tmp/mihomo_watchdog.lock` не даёт двум копиям работать одновременно.

### 7.2 Как читать лог

```bash
cat /opt/var/log/mihomo_watchdog.log
```

Типовые строки и их смысл:

| Строка лога | Что означает |
| --- | --- |
| `[WAN] Connectivity OK via http://...` | WAN подтверждён, проверки продолжаются |
| `[WAN] Primary targets unavailable, checking whitelist targets` | норма в сетях с ограниченным доступом |
| `[WARN] WAN unreachable (primary + whitelist targets failed)` | интернета нет — watchdog правильно ничего не делает |
| `[RESTART] Mihomo port unreachable` | Mihomo упал / не стартовал — перезапущен |
| `[RESTART] Proxy tunnel check failed` | порт открыт, туннель мёртв — часто проблема на VPN-сервере или в конфиге |
| `[RATE-LIMIT] Restart blocked (Ns < 300s)` | работает защита от циклов, это не ошибка |
| `[OK] All good` | всё здорово |

Ротация встроена: больше 500 строк → остаются последние 300. Логи лежат в tmpfs (RAM-режим) и пропадают при reboot — так задумано.

### 7.3 Какая копия реально запускается?

На роутере могут существовать две копии — **перед обновлением проверьте, какую именно запускает ваш crontab**:

```bash
grep mihomo_watchdog /opt/etc/crontab
```

- `install.sh` кладёт её в `/opt/etc/cron.5mins/mihomo_watchdog` (run-parts или прямая строка)
- `update-watchdog.sh` обновляет `/opt/bin/mihomo_watchdog.sh` (другой путь!)

### 7.4 Ручной отладочный запуск

```bash
sh -x /opt/etc/cron.5mins/mihomo_watchdog
```

Показывает jitter, выбор WAN-цели и каждое решение. При standalone-запуске убедитесь, что `/opt/var/log` существует (каталог создаёт установщик). Порядок проверок, lock-логику, jitter и правило «нет WAN → нет рестарта» не редактируйте — см. [docs/04-watchdog.md](04-watchdog.md).

## 8. Обновление Mihomo

```bash
curl -fSsL https://raw.githubusercontent.com/saymer-alt/keenetic-auto-setup/main/update-mihomo.sh | sh
# или локально на роутере:
sh update-mihomo.sh [--force]
```

Что происходит, по шагам:

1. Lock-файл не даёт запустить два обновления параллельно.
2. RAM-гейт: на устройствах с меньше чем 256 МБ обновление прерывается (защита от OOM).
3. Проверка архитектуры: aarch64 → `linux-arm64`, armv7 → `linux-armv7`. **MIPS/mipsel → намеренный отказ** (официальных бинарников Mihomo под неё не существует).
4. Получает последний тег релиза из `MetaCubeX/mihomo` (GitHub API с fallback'ом на web-redirect).
5. Сравнивает с установленной версией; версии совпали → выход (если нет `--force`).
6. Скачивает `.gz`-бинарник в `/tmp` (curl с fallback'ом на wget), распаковывает, запускает `binary -v` (проверка архитектуры), затем **тест конфига против вашего живого `config.yaml`**.
7. Проверка свободного места на целевой файловой системе (запас 4 МБ; старые `.backup/.old/.bak` рядом с бинарником чистятся; если места всё ещё мало — сервис останавливается, чтобы освободить «призрачные» блоки).
8. Останавливает сервис, делает backup старого бинарника в **`/tmp`** (RAM — не `/opt`), заменяет бинарник, проверяет версию и запуск (pidof, до 5 попыток).

**Автоматический откат** срабатывает на любом сбойном шаге: тест бинарника, тест конфига, место, замена, несовпадение версии, старт сервиса. Предыдущий бинарник восстанавливается, сервис снова запускается. Неудачное обновление должно оставить вас ровно там, где вы были.

Примечания:

- Backup в `/tmp` удаляется после успеха — **постоянной копии на `/opt` нет**. Для ручного даунгрейда скачайте нужный релизный бинарник сами (см. раздел 10).
- Updater ищет бинарник через `find /opt -name mihomo | head -1` — если у вас несколько копий, выбор не определён; держите одну.
- Обновляйтесь этим скриптом, а не вручную: ручная процедура существует для особых случаев в [mihomo_manual_update_arm.md](../mihomo_manual_update_arm.md) (RU).

## 9. Обновление watchdog

```bash
curl -fSsL https://raw.githubusercontent.com/saymer-alt/keenetic-auto-setup/main/update-watchdog.sh | sh
```

Updater: скачивает во временный файл → проверяет, что он непустой → проверяет sanity-маркер `MIHOMO WATCHDOG SCRIPT` → проверка синтаксиса `sh -n` → backup текущей копии в `/opt/var/log/mihomo_watchdog.sh.bak.<timestamp>` → атомарный `mv` на место.

**Нюанс с путями (важно):** он обновляет `/opt/bin/mihomo_watchdog.sh`, тогда как `install.sh` разворачивает в `/opt/etc/cron.5mins/mihomo_watchdog`. Перед обновлением проверьте, какая копия реально прописана в crontab (раздел 7.3) — иначе вы обновите файл, который никогда не выполняется.

## 10. Откат

**Автоматический (Mihomo updater).** Встроен в `update-mihomo.sh` на каждом критическом шаге — делать ничего не нужно, предыдущий бинарник возвращается сам.

**Ручной даунгрейд Mihomo (ARM).** Поскольку постоянный backup не хранится:

1. Выберите версию на [github.com/MetaCubeX/mihomo/releases](https://github.com/MetaCubeX/mihomo/releases).
2. На роутере:

```bash
cd /tmp
wget https://github.com/MetaCubeX/mihomo/releases/download/vX.Y.Z/mihomo-linux-arm64-vX.Y.Z.gz
gzip -d mihomo-linux-arm64-vX.Y.Z.gz && chmod +x mihomo-linux-arm64-vX.Y.Z
./mihomo-linux-arm64-vX.Y.Z -v                       # должна напечататься версия
which mihomo                                          # например /opt/bin/mihomo
/opt/etc/init.d/S99mihomo stop
mv /tmp/mihomo-linux-arm64-vX.Y.Z "$(which mihomo)"
/opt/etc/init.d/S99mihomo start
```

3. Проверьте: `mihomo -v`, `ps | grep mihomo`, затем curl-проверку прокси из раздела 5.

**Ручное восстановление watchdog** (если `update-watchdog.sh` пошёл не так): предыдущая копия лежит в `/opt/var/log/mihomo_watchdog.sh.bak.<timestamp>` — скопируйте её `cp` обратно на путь, который прописан в вашем crontab.

## 12. Типовые проблемы

Симптом → причина → решение.

**`opkg update` падает / `curl: (6) Could not resolve host`**
Сломан DNS в Entware. `echo "nameserver 1.1.1.1" > /opt/etc/resolv.conf` (и `8.8.8.8` второй строкой), повторить.

**SSL-ошибки при скачивании (`curl: (60)`, ошибки сертификатов opkg)**
Сбитые часы. `ntpd -q -p pool.ntp.org`, проверить `date`, повторить. Классика на только что загруженном роутере.

**Интернет есть, прокси не работает (особенно `proxy fail [502/...]`)**
Нестабильные/битые DoH-серверы в `config.yaml`. Перейдите на cloudflare-dns / dns.google / quad9. Заодно проверьте сам сервер: `curl -x socks5://127.0.0.1:7890 https://ipinfo.io`.

**`proxy fail [000/000]` / Mihomo не стартует**
Почти всегда `config.yaml` — отсутствует или неверен. `mihomo -d /opt/etc/mihomo -t` напечатает настоящую ошибку; запуск `mihomo -d /opt/etc/mihomo` в foreground покажет логи старта.

**«Всё установилось, но ничего не открывается»**
Нет `config.yaml` (раздел 5) или DNS на клиентах. Также проверьте, что собственный DNS роутера жив — никогда не «тестируйте» изменением default route/DNS как попало.

**Лог watchdog пустой**
Cron не запущен, либо строка в crontab указывает на другую копию скрипта (раздел 7.3). Проверьте `ps | grep cron` и `grep mihomo_watchdog /opt/etc/crontab`.

**Watchdog выполняется дважды (дубли строк в логе)**
Дубли строк в `/opt/etc/crontab` — легко нарожать ручной правкой. Удалите все строки с `mihomo_watchdog`, добавьте одну, перезапустите cron (`/opt/etc/init.d/S10cron restart`).

**`[RATE-LIMIT] Restart blocked` в логе**
Не ошибка — работает 300-секундная защита от циклов.

**Медленно открываются сайты / часть сервисов не работает, остальное в порядке**
Классический симптом MTU на туннелях. Поставьте MTU туннеля 1200–1300 (1500 ломается на DPI/PPPoE многих провайдеров). Это проблема MTU, а не маршрутизации.

**VoIP всё равно не работает**
Проверьте хук: `iptables -t mangle -L _CUST_BYPASS_WA_ -v -n` — счётчики должны расти во время звонка, а политика `bypass_wa` должна указывать на рабочий VPN-интерфейс. Пересоберите firewall или перезагрузитесь, чтобы хук применился заново. На MT7621 не покрывается вовсе (раздел 13).

**Роутер стал нестабильным после установки**
Почти всегда устройство на 128 МБ. Тулкит там не поддерживается; tmpfs доводит такие системы до предела. Максимум — режим `disk`, а лучше — железо помощнее.

**Логи пропали после reboot**
Так задумано в режиме `ram` (tmpfs). При необходимости сохраняйте их сами или используйте `disk`.

**Устройство с прописанным вручную внешним DNS ведёт себя иначе / не может достучаться до конкретного внешнего DNS-сервера**
Перехват транзитного DNS (раздел 6.1) перенаправляет классические port-53 запросы в DNS-прокси роутера. Это задуманное поведение; если конкретному устройству действительно нужен прямой доступ к своему DNS-серверу — откатите перехват для всего роутера командами из раздела 6.1.

## 13. Особенности MT7621 / mipsel

`install_7621.sh` существует потому, что MT7621 оснащается TLS-стеком, который не умеет говорить с современными серверами («`curl: (60)` и друзья»). Он обходит это через `--insecure` и HTTP-зеркало, **меняя проверку сертификатов на совместимость** — MITM теоретически возможен; источники зафиксированы, что снижает практический риск, но трейдофф понимайте.

Отличия от `install.sh`:

| | install.sh | install_7621.sh |
| --- | --- | --- |
| Архитектура | авто (aarch64/armv7) | mipsel |
| TLS | проверяется | `--insecure` + HTTP-зеркало |
| MagiTrickle | ✅ | ❌ не ставится |
| bypass_wa (VoIP) | ✅ | ❌ не ставится |
| Источник Mihomo | релизы `saymer-alt/entware-go` (latest) | HTTP-зеркало, fallback на запинованный `mihomo_1.19.23-1` ipk из тега `mihomo` этого репо |
| Watchdog / Proxy0 / S00ubifs | ✅ | ✅ |

Mihomo на MIPS: **официальных бинарников под mipsel нет** — `update-mihomo.sh` там намеренно отказывается работать. Не «чините» это подстановкой чужих сборок; используйте opkg-пакет или собирайте сами ([docs/09](09-limitations.md)).

Без MagiTrickle маршрутизация на MT7621 — «всё или ничего» (политики по интерфейсам настраиваются в KeeneticOS вручную); без `bypass_wa` VoIP-звонки идут через прокси и будут настолько хороши (или плохи), насколько ваш прокси умеет UDP.

## 14. Известные ограничения

- **128 МБ RAM: не поддерживается.** Не рекомендация — проверенный в продакшене сценарий отказа.
- **Watchdog чинит только Mihomo.** Он не починит мёртвый VPN-сервер, аварию у провайдера, DNS или ошибки в конфиге.
- **У Mihomo есть пределы в работе с UDP** — именно поэтому VoIP идёт мимо него.
- **Entware — не полноценный Linux.** Причуды BusyBox (`$RANDOM`, `pidof`, `ss`, `run-parts`), урезанные пакеты — держите это в голове, прежде чем «модернизировать» скрипты.
- **Логи в RAM пропадают при reboot** — плата за защиту флешки.
- Коммит в `main` этого репо меняет то, что выполнит следующий `curl | sh` — стейджинга и CI нет. Относитесь к обновлениям соответственно.

Больше границ и рассуждения за ними: [docs/09-limitations.md](09-limitations.md).
