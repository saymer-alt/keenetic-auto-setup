## Как на самом деле работает маршрутизация

Всё остальное в этом документе — DNS, watchdog, Mihomo, предупреждения — обретает смысл только после того, как ясна базовая модель. Прочитайте этот раздел до установки; дальнейший текст исходит из него.

### Базовая модель

```
Клиент → Keenetic → MagiTrickle (какой выход для этого трафика?) → Интернет
```

- **Keenetic** — платформа: интерфейсы, политики подключений, firewall, DNS.
- **MagiTrickle — не VPN и трафик не передаёт.** Это уровень принятия решений: он перехватывает DNS на настроенных интерфейсах, запоминает, какие IP принадлежат каким доменам, и применяет policy-роутинг, чтобы трафик к совпавшему назначению ушёл через выбранный вами выход. По официальной документации он работает подменой DNS на выбранных интерфейсах и сопоставлением ответов с доменами; маршрутизация выполняется firewall-метками и policy-правилами — сам MagiTrickle ничего не туннелирует.
- **Выходы взаимозаменяемы.** Прямой ISP, AWG, SSTP, OpenConnect, WireGuard, Mihomo — всё это просто назначения, на которые может указывать политика. В этом и смысл проекта: менять выход, не перестраивая систему.

Картина целиком:

```text
Клиент
  │
  ├── DNS → DNS Keenetic → MagiTrickle
  │                          (классификация)
  └── трафик → Keenetic
                    │
             решение MagiTrickle
                    │
          ┌─────────┼─────────┐
          ▼         ▼         ▼
        DIRECT     mitun0    Proxy0
                     │         │
                     ▼         ▼
                   Mihomo    Mihomo
                     │
              proxy-outbounds
                     │
                     ▼
                  Интернет
```

### Пять вещей, которые легко перепутать

- **VPN на всю сеть** — всё уходит в один туннель. Просто, но «всё или ничего».
- **Точечная маршрутизация** — каждое назначение идёт своим путём. Модель этого проекта.
- **DNS-классификация** — как система понимает, какой сайт есть какой: наблюдая DNS-запросы и сопоставляя домены с IP.
- **VPN-туннель** — один из возможных *выходов* (транспорт), а не сама маршрутизация.
- **Mihomo** — движок маршрутизации, живущий за одним из выходов. Не «тот самый VPN»: внутри него может быть множество серверов, подписок и политик балансировки, а Keenetic видит его как одно локальное назначение.

### MagiTrickle 101

MagiTrickle живёт на роутере, наблюдает DNS и решает по каждому домену, через какой выходной интерфейс должен пойти трафик. Он не VPN и не сам прокси — он принимает решение; носит трафик тот интерфейс, на который решение указывает.

Его официальная модель (по [документации MagiTrickle](https://magitrickle.dev/)) проста:

- **Group (группа)** — именованный контейнер, привязывающий набор доменов к одному выходу. Включается/выключается, меняет порядок («VPN», «Direct», «Торренты» — как назовёте).
- **Interface (интерфейс)** — настройка внутри группы: интерфейс Keenetic, через который уходит трафик группы (Proxy0, mitun0, VPN-интерфейс, …).
- **Rule (правило)** — матчер домена внутри группы. У каждого правила есть **Type (тип)** и **Condition (условие)**: тип определяет, *как* сверять (namespace = домен и все поддомены, wildcard, точный домен, регулярное выражение), условие — *что* сверять (`youtube.com`).

Конвейер решения для одного сайта выглядит так:

```text
youtube.com
     ↓
  Правило   (тип: namespace, условие: youtube.com)
     ↓
  Группа "VPN"  (интерфейс: mitun0)
     ↓
  mitun0 → Mihomo
```

Ещё раз: MagiTrickle этот трафик не носит и не проксирует — он решает, куда он должен пойти. Всё остальное в этом документе — про то, чтобы это решение было информированным, а выходы здоровыми.

**DNS и интерфейсы, которые смотрит MagiTrickle.** Всё описанное работает только для доменов, которые MagiTrickle реально видит, — именно поэтому следующий подраздел посвящён тому, как удержать DNS клиентов на роутере. В конфиге MagiTrickle указано, где он подменяет DNS:

```yaml
link:
  - br0
  - br1
```

По официальной документации `link` — это список интерфейсов, на которых MagiTrickle выполняет DNS-подмену; по умолчанию `br0` и `br1` — имена мостов роутера со стороны Entware (`br0` — домашний сегмент). На практике:

```text
192.168.1.0/24 (домашняя)  → br0 → MagiTrickle перехватывает DNS → классификация работает
192.168.2.0/24 (новая)     → brX → нет в списке → нет DNS-подмены → нет классификации
```

Поэтому, создавая дополнительную LAN/Wi-Fi-сеть, помните: MagiTrickle нужно навести и на этот интерфейс — добавьте его в `link:` конфига или настройте список интерфейсов в его web UI. DoH/DoT остаются отдельным случаем (см. следующий подраздел): шифрованный клиентский DNS вообще не касается точки подмены.

Это намеренно не полный мануал по MagiTrickle — полный справочник по интерфейсу, типам правил и конфигу ищите в [официальной документации](https://magitrickle.dev/).

### Почему клиент должен использовать DNS роутера

Уровень решений классифицирует по доменам и видит только те, что проходят через наблюдаемый им DNS. Поэтому обычный DNS клиента должен идти через Keenetic:

```
Клиент → DNS Keenetic → MagiTrickle → решение о маршруте
```

Если устройство отправляет запросы напрямую внешнему резолверу, часть DNS-пути идёт мимо контролируемой точки, и точечная маршрутизация для него превращается в угадывание. Именно поэтому установщик включает перехват транзитного DNS (раздел 6.1). Две вещи, которыми это **не** является: это не запрет какого-либо публичного DNS — сам роутер спокойно использует выбранный вами upstream (раздел 6.2) — и это не защита от DoH/DoT, поскольку шифрованный клиентский DNS проходит мимо порта 53 в любом случае.

### Почему VPN-клиент на устройстве мешает маршрутизации Keenetic

Роутер может маршрутизировать трафик клиента, пока тот приходит на роутер как обычный трафик — отдельные соединения, которые видно и которые можно классифицировать:

```
без клиентского VPN:
  Клиент ── сайт A / сайт B / сайт C ──> Keenetic+MagiTrickle ── решение по каждому ──> DIRECT / mitun0 / Mihomo
```

Если клиент сам устанавливает VPN-туннель, картина меняется:

```
с клиентским VPN:
  Клиент ══ [ один шифрованный туннель: A+B+C внутри ] ══> Keenetic ── видит туннель, не сайты ──> выход туннеля
```

В обычной модели клиентского VPN устройство шифрует и упаковывает свой трафик в единый поток к VPN-серверу. Keenetic видит (по преимуществу) этот поток, а не отдельные сайты внутри него — значит, MagiTrickle не может принимать посайтовые решения по трафику, который не появляется в виде отдельных соединений. Детали зависят от типа VPN и настроек клиента, но модель такая: роутерная точечная маршрутизация и клиентский VPN решают одну задачу в разных местах, и роутер управляет только тем, что доходит до него как обычный трафик.

### Два пути в Mihomo: прокси-интерфейс (ProxyN) и mitun0

Проект поставляет первый путь и поддерживает второй:

- **Прокси-интерфейс Mihomo** — *прокси-интерфейс* Keenetic (SOCKS5 на `127.0.0.1:7890`), создаваемый и настраиваемый установщиком. На чистом роутере он получает ID `Proxy0`; если этот ID занят, Keenetic выдаст следующий свободный (`Proxy1`, `Proxy2`, …) — отсюда общее имя `ProxyN`. Человекочитаемая подпись следует тому же номеру (`mihomo t2s0`, `mihomo t2s1`, …). Поскольку это полноценный интерфейс Keenetic, его можно использовать как назначение в политиках подключений — по клиенту или по сегменту. Это исторический путь, и он остаётся удобной «явной точкой назначения» в правилах Keenetic.
- **TUN-интерфейс Mihomo** — прозрачный путь на уровне IP. Mihomo создаёт TUN-устройство, имя которого задаётся в его собственном конфиге (настройки `tun`, параметр `device`); `mitun0` — распространённое имя для него в Keenetic-сетапах. Keenetic видит его как обычный интерфейс, на который так же можно навести политику. Трафик, входящий в TUN, — обычный IP-трафик, который Mihomo далее разруливает по своим правилам. Этот путь настраивается в `config.yaml` Mihomo, а не установщиком.

Коротко: `mitun0` лучше подходит как основной прозрачный путь для IP-трафика; Proxy0 — как отдельная точка назначения, на которую правила Keenetic могут ссылаться напрямую. Оба пути приводят в один и тот же Mihomo.

### Mihomo basics

Mihomo — выходной движок. Он принимает трафик от двух входов выше и действует по своему `config.yaml`:

```text
MagiTrickle
     ↓
  mitun0
     ↓
  Mihomo ── rules ──> VLESS / WireGuard(AWG) / другие прокси
```

```text
Браузер
   ↓
FoxyProxy
   ↓
Keenetic :7890
   ↓
Mihomo
```

Что нужно понимать в рамках этого проекта:

- **Mihomo принимает трафик** с обоих входов: TUN (`mitun0`) — прозрачный IP-трафик, mixed-порт `7890` — прокси-клиенты (FoxyProxy в браузере, Proxy0 со стороны Keenetic, любой SOCKS5/HTTP-клиент роутера).
- **Outbound — это просто одно из назначений, сконфигурированных в Mihomo**: записи в `proxies`/`proxy-groups` (например, серверы VLESS/Reality, туннели типа WireGuard, SOCKS- или HTTP-релеи). «Направить через Mihomo» всегда означает «Mihomo сам выберет один из своих outbound'ов по своим правилам».
- **Зачем существует `mitun0`** — чтобы обычный IP-трафик мог входить в Mihomo прозрачно, без прокси-настроек в каждом приложении (подраздел выше).
- **Почему остаётся Proxy0** — потому что на него могут напрямую ссылаться правила Keenetic; это естественное назначение для proxy-based политик отдельных клиентов или сегментов.
- **Конфигурация Mihomo — отдельная область.** Проект устанавливает Mihomo и следит за его здоровьем, но не пытается заменить его документацию — по proxies, groups, rules и настройкам TUN используйте [официальную wiki Mihomo](https://wiki.metacubex.one/) (TUN: [inbound/tun](https://wiki.metacubex.one/en/config/inbound/tun/)). Чтобы *собрать* конфиг из своих ссылок/подписок — [link-generators](https://github.com/saymer-alt/link-generators).

### Настройка интерфейса Mihomo ≠ маршрутизация Keenetic

Три разных понятия, которые легко слить в одно — держите их раздельно:

1. **Интерфейс Mihomo** — Linux-интерфейс, к которому Mihomo привязывает **собственные исходящие соединения** (`interface-name` в конфиге / настройках MetaCubeX; по официальной документации — *"mihomo's traffic outbound interface"*). Наш `mihomo-interface-check.sh` существует именно для этого: он показывает пригодные WAN-интерфейсы и выдаёт готовые строки `interface-name:`.
2. **Inbound Mihomo** — куда клиенты подключаются к Mihomo: mixed-порт `7890` или TUN (`mitun0`).
3. **Маршрутизация Keenetic** — kernel-level default gateway и политики, решающие, откуда трафик реально покидает роутер после попадания в таблицы маршрутизации.

Практическое следствие (типовое поведение на роутере с двумя WAN — проверьте на своей схеме):

```text
WAN1 = провайдер A (default gateway)     WAN2 = провайдер B
interface-name в Mihomo = WAN2

Клиент → 127.0.0.1:7890 → Mihomo → выбранный proxy → dialer привязан к WAN2   ✅ выход через ISP B
Клиент → mitun0 → Mihomo (TUN) → трафик передан kernel-роутингу → default gateway   ✅ выход через ISP A
```

Иными словами: **настройка интерфейса в MetaCubeX — не переключатель WAN для роутера.** Она привязывает исходящие сокеты самого Mihomo — прежде всего соединения к вашим прокси-серверам. Трафик, вошедший через `mitun0`, подчиняется правилам Mihomo как любой другой inbound, а всё, что уходит из него несвязанным/обычным потоком, следует обычным таблицам маршрутизации Keenetic — то есть default gateway (ISP A выше). Смежные TUN-опции, которые стоит знать: `auto-route` (затягивает трафик в TUN) и `auto-detect-interface` (автоопределение выходного интерфейса — документация прямо рекомендует задавать интерфейс вручную на устройствах, подключённых к нескольким выходным интерфейсам одновременно). Если нужен per-path выбор WAN для TUN-трафика — это задача policy-роутинга Keenetic, а не галочка в MetaCubeX.

### Mihomo работает и без web UI

Важно не смешивать три сущности: **ядро** (демон Mihomo), **controller** (REST API, который ядро предоставляет только при явной настройке `external-controller`) и **web UI** (панели в стиле MetaCubeX — metacubexd, yacd, zashboard; это отдельные интерфейсы поверх того API). Демон прекрасно работает вообще без дашборда — и установка по умолчанию в этом проекте делает ровно так: демон, без web UI на роутере.

- **Если `external-controller` не задан, API выключен и порт 9090 никто не слушает.** «Дефолтного» адреса у контроллера нет — значение по умолчанию в коде Mihomo пустое; распространённое `127.0.0.1:9090` — конвенция из примеров, а не встроенный дефолт.
- Семантика адреса `external-controller`: `127.0.0.1:9090` — bind только на loopback самого устройства, где работает Mihomo (панель с другого устройства к такому API не подключится); `192.168.1.1:9090` — bind на конкретный LAN-адрес роутера (рабочий вариант для панели с ПК); `0.0.0.0:9090` — bind на все IPv4-интерфейсы сразу, как «безопасный вариант по умолчанию» для новичка не предлагается.
- Дашборд может жить **на роутере** (`external-ui`: статические файлы страниц, которые API Mihomo раздаёт по пути `/ui`) — это место на диске, а не отдельный процесс.
- Или **целиком на другом устройстве**: публичные дашборды (например, хостуемые страницы metacubexd) могут подключаться к API роутера удалённо — тогда на роутере нет ничего, кроме самого демона.
- В любом случае UI — опциональный инструмент, а не обязательная часть Mihomo.

**Безопасность:** API контроллера может менять поведение Mihomo на лету — не выставляйте его в WAN. Держите loopback- или LAN-биндинг (контроллер и вовсе не включён — тоже корректный выбор), при LAN-доступе всегда задавайте `secret:`, а для удалённого управления добирайтесь до API через VPN или SSH-туннель (`ssh -L 9090:127.0.0.1:9090 root@router`), а не открыванием порта.

### Отдельные Wi-Fi/LAN-сети как практический use case

KeeneticOS позволяет создавать дополнительные сегменты сети — дополнительные гостевые Wi-Fi (на каждый диапазон) и проводные сегменты, каждый со своей подсетью и DHCP, — и привязывать их к политикам подключений. Доступное число сегментов зависит от модели и версии OS — смотрите страницу *Сегменты* в вашем web UI, а не какую-либо фиксированную цифру. Иллюстративная схема (это пример, а не обязательная конфигурация проекта):

```
Wi-Fi 1 (Home)  → ISP напрямую
Wi-Fi 2         → Proxy0 → Mihomo
Wi-Fi 3         → mitun0 → Mihomo (TUN)
```

Важный нюанс: **создание сегмента не ставит его под MagiTrickle автоматически.** MagiTrickle перехватывает DNS на интерфейсах, перечисленных в его конфигурации, — по умолчанию `br0` и `br1` (имена мостов роутера со стороны Entware; `br0` — домашний сегмент). У нового сегмента своё имя интерфейса, поэтому:

```
192.168.1.0/24 (br0)  → MagiTrickle работает
192.168.2.0/24 (brX)  → новый сегмент — автоматически не покрыт
                        → добавьте его в конфиг MagiTrickle (список `link:`) или включите в его web UI
```

### Продвинутые заметки: туннели через Mihomo и WARP colo

- **Цепочка роутерного туннеля через Mihomo.** Keenetic умеет строить собственные туннели (AWG, SSTP, OpenConnect, WireGuard). В продвинутой схеме трафик такого туннеля можно направить через Mihomo-прокси — тогда цепочка выйдет с публичным IP/страной удалённого прокси. Вложенные туннели делают MTU особенно важным: правильное значение специфично для каждой цепочки (одна из наших WARP-схем нормально работает на 1200 — это пример, а не рекомендация). См. пункт MTU в [Типовых проблемах](#12-типовые-проблемы).
- **WARP / MASQUE и Cloudflare colo.** Смена Cloudflare colo сама по себе **не** меняет страну выхода или публичный IP — colo и геолокация exit IP — разные вещи. При этом на практике другой colo может улучшить поведение отдельных сервисов (например, Telegram или YouTube), даже если exit IP остаётся прежним. То есть colo имеет практическое значение, но не является способом «выбрать страну выхода». Для исследования доступных/выбираемых colo есть инструмент [vernette/warpscout](https://github.com/vernette/warpscout) — детали в его документации.

### DNS ≠ маршрутизация

- DNS отвечает на вопрос: *«какой IP у этого домена?»*
- Маршрутизация отвечает на вопрос: *«куда отправить трафик к этому назначению?»*

Они связаны — в этом проекте решения о маршрутизации *управляются* DNS-классификацией — но это разные задачи разных компонентов. Именно поэтому DNS-проблемы маскируются под проблемы маршрутизации (раздел 6.2, [Типовые проблемы](#12-типовые-проблемы)), и почему починка DNS часто «чинит маршрутизацию» без всякого касания Mihomo.

### «Весь интернет через VPN» против точечной маршрутизации

```
Обычный VPN:   всё ──────────────> VPN

Этот проект:   сайт A  → DIRECT
               сайт B  → mitun0 (TUN Mihomo)
               сайт C  → Mihomo (Proxy0)
               VoIP    → bypass_wa → VPN напрямую
               local   → DIRECT
```

### Как отдельные предупреждения складываются в модель

- **DNS клиентов должен оставаться на роутере** — раздел 6.1 (на нём держится классификация).
- **Через какой upstream резолвит сам Keenetic** — раздел 6.2 (особенно в сетях с белыми списками).
- **У браузерного прокси есть слепое пятно WebRTC** — раздел 5.1 (собственный UDP-путь браузера обходит всё перечисленное).
- **Клиентские VPN скрывают трафик от роутера** — этот раздел.
- **Когда «сломалась маршрутизация», начинайте с DNS** — [Типовые проблемы](#12-типовые-проблемы), сценарий whitelist-сети.

## 2. Подготовка Keenetic и Entware

Тулкит устанавливается *в* Entware — сам Entware он не устанавливает.

1. В KeeneticOS включите компонент OPKG/Entware (*Общие настройки → Opkg / Entware* или через меню компонентов KeeneticOS в зависимости от прошивки) и выберите накопитель: внутренняя память (на моделях, которые это поддерживают) или USB-диск с файловой системой ext4.
2. Перезагрузите роутер, когда компонент попросит.
3. Проверьте по SSH:

```bash
ls /opt                    # корень Entware должен существовать
opkg update                # должно завершиться без ошибок
date                       # сбитое время → позже упадут SSL-ошибки
```

Если `opkg update` падает: сначала почините DNS (`cat /opt/etc/resolv.conf`, при необходимости `echo "nameserver 1.1.1.1" > /opt/etc/resolv.conf`) и время (`ntpd -q -p pool.ntp.org`) — это две самые частые причины.

## 3. Установка

### 3.1 Команда

**Основной путь — универсальный установщик** (автоопределение архитектуры: aarch64/armv7, а также mipsel/mips; mipsel-путь давно не проходил повторное тестирование):

```bash
opkg update && opkg install curl && \
curl -fSsL https://raw.githubusercontent.com/saymer-alt/keenetic-auto-setup/main/install.sh | sh
```

**MT7621, если универсальный установщик не проходит** — отдельный установщик для этих устройств; работает через `--insecure` и HTTP-зеркало (проверка сертификатов ослаблена — трейдофф описан в [разделе 13](#13-особенности-mt7621--mipsel)):

```bash
curl -k -fSsL https://raw.githubusercontent.com/saymer-alt/keenetic-auto-setup/main/install_7621.sh | sh
```

### 3.2 Что именно делает `install.sh`

По порядку:

1. `opkg update`, затем ставит `ca-bundle`, `curl`, `jq`, `nano`, `cron` (уже установленные пропускает).
2. Создаёт политику маршрутизации `bypass_wa` (только если её ещё нет).
3. Включает **перехват транзитного DNS** Keenetic (`dns-proxy intercept enable`, затем `system configuration save` — применяется, только если ещё не включён): классические port-53 запросы клиентов LAN, адресованные напрямую внешним резолверам, перенаправляются в DNS-прокси роутера, где их видит MagiTrickle (подробности — в [разделе 6.1](#6-magitrickle)). Это часть автоматической установки — ручного post-install шага для DNS нет. Только классический DNS; DoH/DoT не затрагиваются.
4. **Только в RAM-режиме:** скачивает `S00ubifs` в `/opt/etc/init.d/` и запускает его (tmpfs для `/opt/tmp`, `/opt/var/log`, `/opt/var/run`).
5. Определяет архитектуру и скачивает подходящий **mihomo `.ipk`** из релизов [`saymer-alt/entware-go`](https://github.com/saymer-alt/entware-go) (GitHub API с тремя fallback'ами: jq → grep по JSON → повторный запрос → парсинг HTML).
6. **Bootstrap `config.yaml`**: если конфига нет — создаёт минимальный с `mixed-port: 7890`; если на месте нетронутый placeholder пакета (порт входа он не задаёт) — заменяет его bootstrap'ом. Существующий пользовательский конфиг никогда не изменяется.
7. **Выбирает проектный Proxy-интерфейс**: ищет среди `Proxy0`, `Proxy1`, … интерфейс с проектными признаками — description `mihomo t2sN` **и** upstream `127.0.0.1:7890` — и использует найденный. Если проектного нет: свободный `Proxy0` создаётся; занятый чужой `Proxy0` **не трогается** — создаётся первый свободный `ProxyN`.
8. **Привязывает `bypass_wa`** к выбранному проектному Proxy: находит политику по description `bypass_wa` (имя политики роли не играет) и добавляет `permit global <ProxyN>`, если его ещё нет. Существующие permits (например, ручная привязка к VPN) не удаляются и не переупорядочиваются; если политики нет — установщик ограничивается предупреждением.
9. Устанавливает **MagiTrickle** (добавляет его репозиторий пакетов, ставит, запускает).
10. Ставит VoIP-хук `020-bypass_wa.sh` в `/opt/etc/ndm/netfilter.d/`.
11. Устанавливает **watchdog** в `/opt/etc/cron.5mins/` и подключает к cron (если уже есть run-parts-запись `cron.5mins` — используется она; иначе добавляется прямая строка в crontab).
12. Перезапускает `S99mihomo` и выполняет **самопроверку установки** (`[ok]/[WARN]/[FAIL]` — см. 3.4).

### 3.3 Безопасно ли запускать повторно?

Установщик написан идемпотентным: каждый изменяющий шаг сначала проверяет, существует ли объект (пакеты, политика, проектный ProxyN, запись в crontab). Повторный запуск ничего не задублирует.

Нюанс: mihomo `.ipk` скачивается при каждом запуске — `opkg` просто пропустит установку, если та же версия уже стоит.

Ещё нюансы о существующих настройках:

- **Чужой Proxy0 не трогается.** Если существующий `Proxy0` не совпадает с проектными признаками (description `mihomo t2sN` + upstream `127.0.0.1:7890`), установщик оставляет его как есть и создаёт первый свободный `ProxyN`. Повторный запуск при уже созданном проектном ProxyN переиспользует его, не создавая новый.
- **Пользовательский `config.yaml` никогда не перезаписывается:** bootstrap создаётся только при отсутствии конфига или на месте нетронутого placeholder пакета.
- Ручные permits в политике `bypass_wa` (например, привязка к своему VPN) сохраняются — добавляется только отсутствующий permit на проектный Proxy.

То же относится к перехвату транзитного DNS: установщик сначала проверяет текущее состояние и включает его (с сохранением конфига) только если он не был включён. Если вы на конкретном роутере сознательно держите транзит DNS открытым — уберите этот блок из установщика перед повторным запуском: ре-запрос включит его снова.

### 3.4 Ожидаемый результат

```text
[setup] ...
[OK] Done
```

Самопроверка печатает три вида строк: `[ok]` — пункт выполнен; `[WARN]` — некритично, установка завершена (`[OK] Done (N warning(s))`); `[FAIL]` — установка **не завершена**, скрипт завершается с ошибкой, текст проверки назовёт упавший пункт.

Предупреждение `[WARN] Port 7890 not listening …` почти всегда означает, что Mihomo не запустился или в `config.yaml` нет `mixed-port: 7890` — переходите к разделу 5: bootstrap поднимает только контрактный порт, рабочий конфиг ставите вы.

## 4. RAM и disk режим

`install.sh [ram|disk]`, по умолчанию `ram`.

| | `ram` (по умолчанию) | `disk` |
| --- | --- | --- |
| Логи, tmp, pid-файлы | tmpfs (RAM) через `S00ubifs` | остаются на накопителе |
| Износ флешки | минимальный | обычный для Entware |
| Данные после reboot | логи пропадают (так задумано) | сохраняются |
| Кому подходит | внутренний флеш, долгая работа 24/7 | устройства с малой RAM, когда нужны постоянные логи |

`S00ubifs` подбирает размеры tmpfs по доступной RAM (профили <40 МБ, <80 МБ, ≥80 МБ свободной памяти). Подробности: [docs/06-s00ubifs.md](06-s00ubifs.md).

Ошиблись режимом: повторный запуск установщика с другим режимом безопасен (уже сделанные шаги пропускаются), но «хвосты» старого режима уберите руками — например `/opt/etc/init.d/S00ubifs` при переходе на `disk`.

## 5. Конфигурация Mihomo

Без валидного конфига ничего не работает. **После установки этот шаг обязателен.**

```bash
nano /opt/etc/mihomo/config.yaml
```

Минимальный рабочий пример:

```yaml
mixed-port: 7890
allow-lan: true
mode: rule
log-level: info

proxies:
  - name: "server"
    type: vless
    server: "YOUR_SERVER"
    port: 443
    uuid: "YOUR_UUID"
    tls: true

proxy-groups:
  - name: "Proxy"
    type: select
    proxies:
      - "server"

rules:
  - GEOIP,private,DIRECT
  - MATCH,Proxy
```

Примечания:

- `allow-lan: true` нужен **клиентам LAN, а не роутеру**: сам Keenetic достучается до Mihomo по `127.0.0.1` независимо от этой настройки. Что она меняет — порт `7890` становится доступен из вашей LAN, и именно это нужно для сценариев `браузер/FoxyProxy → роутер:7890`, других LAN/Wi-Fi-клиентов или удалённой домашней/рабочей сети. Граница безопасности — на вас: это не повод открывать `7890` в WAN — firewall на этот порт должен оставаться закрытым, а к controller API/дашборду Mihomo относитесь ещё строже.
- DoH: «быстрые» резолверы часто оказываются нестабильными. Держитесь проверенных — `https://cloudflare-dns.com/dns-query`, `https://dns.google/dns-query`, `https://dns.quad9.net/dns-query`. Это **собственный DNS Mihomo внутри туннеля** — другой уровень относительно upstream-резолверов Keenetic; про сторону Keenetic и сети с белыми списками см. раздел 6.2.
- Привязка исходящих интерфейсов: запустите прилагаемый хелпер — он выдаёт готовые строки `interface-name:` для ваших WAN-интерфейсов:

```bash
sh mihomo-interface-check.sh    # или скачайте его из репо прямо на роутер
```

Применить и проверить:

```bash
/opt/etc/init.d/S99mihomo restart
/opt/etc/init.d/S99mihomo status      # ожидаем: alive
curl -x socks5://127.0.0.1:7890 https://ipinfo.io   # ожидаем IP выходного сервера
```

Конфиг можно проверить на синтаксис без перезапуска:

```bash
mihomo -d /opt/etc/mihomo -t
```

Чтобы не писать YAML руками, а собрать конфиг из своих ссылок/подписок: [saymer-alt/link-generators](https://github.com/saymer-alt/link-generators) (работает полностью в браузере, ничего никуда не отправляется).

### 5.1 Браузерный прокси (FoxyProxy) и WebRTC

Браузерный сценарий из use cases в README: включите `allow-lan: true`, направьте браузерное расширение вроде FoxyProxy на `<ip-роутера>:7890` (SOCKS5) и добавьте шаблоны для нужных сайтов. Это покрывает обычный веб-трафик браузера.

**WebRTC — отдельный механизм, и рассматривать его нужно отдельно.** WebRTC устанавливает собственные медиа-пути (ICE/STUN) во многом независимо от прокси-настроек браузера; браузеры, как правило, не отправляют WebRTC через SOCKS5-прокси. Поэтому в прокси-сценарии сайт, выполняющий WebRTC/STUN-проверки, может увидеть сетевую информацию, отличающуюся от выхода прокси — например, публичный адрес, который наблюдает STUN-сервер. Что именно раскрывается — зависит от браузера, его версии и вашей сети: современные браузеры по умолчанию скрывают локальные адреса LAN за mDNS-именами, но поведение с рефлексивными (публичными) кандидатами различается, и единого утверждения «для всех браузеров» не существует. Это не гарантированная утечка — и не гарантированная защита: проверяйте на своей конфигурации.

Что делать, по браузерам (механизмы разные — универсальной настройки нет):

- **Chromium-семейство (Chrome, Edge, …):** встроенной пользовательской настройки нет; используйте расширение, управляющее обработкой IP в WebRTC (у uBlock Origin есть настройка защиты WebRTC; расширения типа «WebRTC Network Limiter» выставляют тот же браузерный policy).
- **Firefox:** `about:config` — `media.peerconnection.ice.default_address_only` и `media.peerconnection.ice.no_host` (ограничивают ICE-кандидатов), либо полностью отключите WebRTC — `media.peerconnection.enabled = false`, если браузерные звонки вам не нужны.
- **Safari:** сопоставимой встроенной настройки нет — возможности ограничены; если изоляция WebRTC важна, относитесь к Safari отдельно.

После настройки проверьте себя на тестовой странице WebRTC (например, browserleaks.com/webrtc) с включённым прокси: адреса, которые она показывает, не должны противоречить вашим ожиданиям от сценария.

Про scope: это предупреждение относится **только к браузерному прокси-сценарию**. При маршрутизации всей сети через Keenetic (настройка по умолчанию) UDP — включая WebRTC — идёт по policy-роутингу роутера, как и любой другой трафик, и браузерное ужесточение WebRTC этим проектом не требуется.

## 6. MagiTrickle

Ставится только `install.sh` (в 7621-установщике его нет). Что такое Groups, Rules и Interfaces — см. *MagiTrickle 101* в разделе о модели маршрутизации в начале руководства; этот раздел — про эксплуатацию.

MagiTrickle — уровень принятия решений: он смотрит на DNS-запросы и по каждому домену/подсети выбирает маршрут — напрямую или через туннель/политику вроде Proxy0. Сам трафик он не передаёт — это делает policy-роутинг Keenetic по его указаниям.

Практическая картина после установки:

- Домены, отправленные вами в прокси, идут `LAN → Proxy0 → Mihomo → ваши серверы → Интернет`. В MagiTrickle/Keenetic прокси-интерфейс отображается в нумерации `t2s` — установщик подписывает Proxy0 как **`mihomo t2s0`**, чтобы соответствие было видно с одного взгляда.
- Всё, что не совпало с правилами, идёт напрямую.
- VoIP-UDP (1400/3478/3482) до Mihomo всё равно не доходит — netfilter-хук `bypass_wa` помечает его в политику `bypass_wa` сразу на VPN-интерфейс.

За веб-интерфейс и управление правилами самого MagiTrickle отвечает его upstream-проект (`bin.magitrickle.dev`) — это за пределами данного репозитория.

### 6.1 Перехват транзитного DNS (управляется установщиком)

MagiTrickle может решать только для тех доменов, которые видит. Задуманная цепочка:

```
Клиент → DNS Keenetic → MagiTrickle → решение о маршруте
```

Если устройство отправляет запросы напрямую внешнему резолверу (прописанный руками `8.8.8.8`, приложение со своим DNS), этот трафик полностью минует уровень принятия решений, и маршрутизация такого устройства тихо выпадает из ваших правил. В KeeneticOS есть ровно под это средство: **перехват транзитных DNS-запросов** (в web UI настройка иногда подписана как разрешение транзитных запросов; CLI `dns-proxy intercept enable`, по умолчанию выключен). Включённый, он перенаправляет классические port-53 запросы, адресованные внешним серверам, в DNS-прокси роутера, где их видит MagiTrickle.

Установщик делает это автоматически — это **часть установки, а не ручной post-install шаг**. Он сначала проверяет текущее состояние (наличие `intercept enable` в running-config), применяет команду только при необходимости и сохраняет постоянный конфиг только при реальном изменении. Команда существует с KeeneticOS 3.06 (кратко отсутствовала в 3.08); при сбое установщик пишет предупреждение и продолжает.

Границы, чтобы никто не ждал лишнего:

- Это **только классический DNS** — это **не** защита от DoH/DoT. Браузер с включённым «безопасным DNS» (DoH) туннелирует запросы поверх HTTPS и проходит мимо порта 53 в любом случае; это клиентская настройка.
- Устройства с прописанными вручную внешними резолверами продолжают работать — их запросы отвечает DNS-прокси роутера через свои настроенные upstream'ы. Редкое исключение: то, что должно ходить на *конкретный* внешний DNS-сервер напрямую по порту 53 (нестандартный split-DNS/AD или DNSSEC-инструменты). Если такое есть — откат на конкретном роутере:

```
(config)> dns-proxy
(config-dnspx)> no intercept enable
(config-dnspx)> exit
(config)> system configuration save
```

… и уберите блок перехвата из установщика для этого роутера — иначе повторный запуск включит его снова. Всё остальное в вашей DNS-конфигурации (DoH/DoT-upstream'ы в конфиге Mihomo, собственные резолверы роутера, DNS из DHCP) остаётся нетронутым.

Проверка на роутере:

```bash
ndmc -c "show running-config" | grep "intercept enable"   # ожидаем одну строку в блоке dns-proxy
```

Функциональная проверка с клиента: запрос с явно указанным внешним резолвером (`nslookup example.com 8.8.8.8`) должен по-прежнему проходить — ответ приходит через роутер.

### 6.2 Выбор upstream DNS (и сети с белыми списками)

Раздел 6.1 управлял тем, *куда клиенты отправляют свой DNS*. Этот раздел — следующий уровень: *куда за резолвингом обращается сам Keenetic* — upstream-резолверы DNS-прокси роутера, от которых фактически зависит классификация MagiTrickle.

```
1. Контролируем DNS-путь клиента    → раздел 6.1 (перехват транзита)
2. Выбираем подходящий upstream DNS → этот раздел
3. Для белых списков проверяем доступность выбранного DNS
4. Проверяем результат через диагностику → разделы 6.1, 11, 12
```

**Почему DNS — часть маршрутизации.** MagiTrickle решает по доменам, а видит только те, что до него доходят. Если upstream-резолвер недоступен, медлен, фильтруется или отдаёт неожиданные ответы, классификация ломается — хотя MagiTrickle, Mihomo и туннель полностью здоровы. В сети с белым списком это самая частая точка отказа, и выглядит она ровно как «сломался роутер».

**Проблема белых списков.** В такой сети нельзя выбирать DNS по принципу «какой лучше». Сервис может поддерживать DoH и DoT, быть описан во всех документациях — и быть недоступен из вашей сети просто потому, что его endpoint'ы не входят в белый список. Кроме того, оператор может вмешиваться в сами DNS-ответы (фильтрация, подмена, специальные адреса для заблокированных доменов). Реальные критерии: доступен ли сервис из этой сети и можно ли доверять ответам — а «лучший» уже потом.

**Что поддерживает Keenetic** (официальная [документация DoH/DoT](https://support.netcraze.ru/air/nc-1613/en/31543-dot-and-doh-proxy-servers-for-dns-requests-encryption.html)):

- Нативные upstream'ы DoT и DoH начиная с OS 3.0; требуются системные компоненты *DNS-over-TLS proxy* / *DNS-over-HTTPS proxy*.
- Web UI: *Интернет-безопасность → Конфигурация DNS* — сервер добавляется по IP или FQDN плюс TLS-домен (указание TLS-домена защищает от перехвата запроса); можно привязать интерфейс подключения. До 8 серверов DoT/DoH; при нескольких система расставляет приоритет по измеренному времени отклика. Когда DoT/DoH настроен, DNS провайдера и вручную прописанные обычные серверы не используются.
- CLI-эквиваленты: `dns-proxy tls upstream <адрес> <tls-домен>` (например, `dns-proxy tls upstream 1.1.1.1 cloudflare-dns.com`) и `dns-proxy https upstream <url>` (например, `dns-proxy https upstream https://dns.comss.one/dns-query`).
- Альтернатива: в OS 3.8+ есть встроенные профили публичных DNS-фильтров (AdGuard, Cloudflare, OpenDNS, Quad9, Yandex.DNS и другие), включающие шифрованный DNS без ручной настройки, — учтите, это именно *фильтрующие* профили, проверьте уровень фильтрации.

**Резолверы, которые имеет смысл знать** — все нативно настраиваются в Keenetic:

| DNS | DoH | DoT | Keenetic | Белый список / ограничения | Комментарий |
| --- | --- | --- | --- | --- | --- |
| DNS провайдера | — | — | присутствует всегда (ISP/DHCP) | **Максимальная совместимость** с ограниченными сетями (практическое наблюдение) | Может фильтроваться и подменяться оператором; в обычной сети не обязательно предпочтителен |
| Yandex DNS `77.88.8.8` | `https://common.dot.dns.yandex.net/dns-query` | `common.dot.dns.yandex.net` | нативный DoT/DoH; плюс встроенный профиль *Yandex.DNS* (OS 3.8+) | RU-хостинг — реалистичный кандидат для ограниченных сетей; доступность зависит от конкретной сети/оператора | Официальная страница [dns.yandex.com](https://dns.yandex.com/); уровни Basic / Safe / Family (`safe.` / `family.dot.dns.yandex.net`) |
| Cloudflare `1.1.1.1` | `https://cloudflare-dns.com/dns-query` | `cloudflare-dns.com` | нативно (в примерах самой Keenetic) | Зарубежный резолвер — доступность endpoint'ов в РФ-сетях с ограничениями часто деградирована (широко задокументировано) | Также рекомендация по DoH для *собственного* DNS Mihomo (другой уровень, раздел 5) |
| Google `8.8.8.8` | `https://dns.google/dns-query` | `dns.google` | нативно (в примерах самой Keenetic) | Аналогично Cloudflare | — |
| Quad9 `9.9.9.9` | `https://dns.quad9.net/dns-query` | `dns.quad9.net` | нативно (в примерах самой Keenetic) | Аналогично Cloudflare | По умолчанию фильтрует вредоносные домены |
| AdGuard `94.140.14.14` | `https://dns.adguard-dns.com/dns-query` | `dns.adguard-dns.com` | нативно (в примерах самой Keenetic + профиль фильтра) | Зарубежный; те же оговорки; фильтрация рекламы/трекеров включена по умолчанию — `unfiltered.adguard-dns.com` без неё | — |
| Comss.one | `https://dns.comss.one/dns-query` | `dns.comss.one` (также `dns.east.comss.one`) | нативно — фигурирует в примерах самой Keenetic | RU-ориентированный сервис; практичный вариант по опыту сообщества, доступность — по сети | Сторонний RU-сервис — доверять ли ему, решает пользователь |

Доступность зарубежных резолверов в российских сетях с ограничениями: широко задокументирована, зависит от сети и меняется со временем (блокировки шифрованного DNS у крупных провайдеров публично фиксировались — см. отчёт Human Rights Watch *Disrupted, Throttled, and Blocked*, июль 2025; измерения OONI). Каждую строку таблицы воспринимайте как «проверить в своей сети», а не как гарантию для какого-либо оператора.

**Предупреждение о подмене.** Даже собственный DoH/DoT-upstream не означает автоматически, что ответы не тронуты. Оператор может влиять на доступность на других уровнях — маршрутизация/IP-blackholing, DPI, — а в ограниченных сетях DNS-ответы для отдельных доменов могут отличаться от ожидаемых (специальные адреса, NXDOMAIN, таймауты) независимо от того, какой резолвер вы настроили. Это практическое ограничение любой однороутерной схемы, а не дефект проекта; настройки DNS, которая чинит блокировку на уровне IP, не существует.

**Практические дефолты:**

- Обычная сеть без ограничений: набор из 2–4 серверов DoT/DoH разных провайдеров (Keenetic расставит приоритет по времени отклика), например Cloudflare + Google + Quad9. DNS провайдера тоже работает, но оставляет вас под его фильтрацией.
- Сеть с белым списком: начинайте с DNS провайдера или Yandex DNS (наиболее вероятно доступных), добавляйте зарубежный DoT/DoH только после проверки доступности и перепроверяйте после каждого изменения сети/оператора.

Доступность проверяйте *из этой* сети, а не «из интернета»:

```bash
ndmc -c "show dns-proxy"          # статистика по каждому upstream: R.Sent / A.Rcvd
nslookup ya.ru 77.88.8.8          # доступность кандидата по обычному DNS
```

Upstream, у которого `R.Sent` растёт, а `A.Rcvd` стоит на нуле, из этой сети недоступен — меняйте. Пошаговый сценарий отказа — в [Типовых проблемах](#12-типовые-проблемы).

## 7. Watchdog в эксплуатации

### 7.1 Что и в каком порядке проверяется

Каждые 5 минут (cron) со случайной задержкой 0–24 с (busybox-совместимой: `date +%s % 25` — без `$RANDOM`):

1. **WAN — напрямую, без Mihomo.** Основные цели: `cp.cloudflare.com`, `www.google.com`. Если недоступны *все* — включается whitelist-fallback: `gosuslugi.ru`, `ya.ru`, `mail.ru`, `vk.ru`, `vk.com`. Ответил хотя бы один = WAN есть. Не ответил никто → watchdog выходит, **ничего не перезапуская** — отсутствие WAN не означает, что сломан Mihomo.
2. **Порт прокси** — `127.0.0.1:7890` должен принимать TCP-соединения. Порт закрыт → Mihomo, вероятно, упал → рестарт.
3. **Сквозной туннель** — реальный запрос через `socks5h://127.0.0.1:7890` (DNS тоже через туннель) до google должен пройти. Порт открыт, туннель мёртв → рестарт.

Ограничение частоты: минимум 300 с между рестартами, состояние в `/tmp/mihomo_watchdog.restart` с валидацией содержимого. Lock-файл `/tmp/mihomo_watchdog.lock` не даёт двум копиям работать одновременно.

### 7.2 Как читать лог

```bash
cat /opt/var/log/mihomo_watchdog.log
```

Типовые строки и их смысл:

| Строка лога | Что означает |
| --- | --- |
| `[WAN] Connectivity OK via http://...` | WAN подтверждён, проверки продолжаются |
| `[WAN] Primary targets unavailable, checking whitelist targets` | норма в сетях с ограниченным доступом |
| `[WARN] WAN unreachable (primary + whitelist targets failed)` | интернета нет — watchdog правильно ничего не делает |
| `[RESTART] Mihomo port unreachable` | Mihomo упал / не стартовал — перезапущен |
| `[RESTART] Proxy tunnel check failed` | порт открыт, туннель мёртв — часто проблема на VPN-сервере или в конфиге |
| `[RATE-LIMIT] Restart blocked (Ns < 300s)` | работает защита от циклов, это не ошибка |
| `[OK] All good` | всё здорово |

Ротация встроена: больше 500 строк → остаются последние 300. Логи лежат в tmpfs (RAM-режим) и пропадают при reboot — так задумано.

### 7.3 Какая копия реально запускается?

На роутере могут существовать две копии — **перед обновлением проверьте, какую именно запускает ваш crontab**:

```bash
grep mihomo_watchdog /opt/etc/crontab
```

- `install.sh` кладёт её в `/opt/etc/cron.5mins/mihomo_watchdog` (run-parts или прямая строка)
- `update-watchdog.sh` обновляет `/opt/bin/mihomo_watchdog.sh` (другой путь!)

### 7.4 Ручной отладочный запуск

```bash
sh -x /opt/etc/cron.5mins/mihomo_watchdog
```

Показывает jitter, выбор WAN-цели и каждое решение. При standalone-запуске убедитесь, что `/opt/var/log` существует (каталог создаёт установщик). Порядок проверок, lock-логику, jitter и правило «нет WAN → нет рестарта» не редактируйте — см. [docs/04-watchdog.md](04-watchdog.md).

## 8. Обновление Mihomo

```bash
curl -fSsL https://raw.githubusercontent.com/saymer-alt/keenetic-auto-setup/main/update-mihomo.sh | sh
# или локально на роутере:
sh update-mihomo.sh [--force]
```

Что происходит, по шагам:

1. Lock-файл не даёт запустить два обновления параллельно.
2. RAM-гейт: на устройствах с меньше чем 256 МБ обновление прерывается (защита от OOM).
3. Проверка архитектуры: aarch64 → `linux-arm64`, armv7 → `linux-armv7`. **MIPS/mipsel → намеренный отказ** (официальных бинарников Mihomo под неё не существует).
4. Получает последний тег релиза из `MetaCubeX/mihomo` (GitHub API с fallback'ом на web-redirect).
5. Сравнивает с установленной версией; версии совпали → выход (если нет `--force`).
6. Скачивает `.gz`-бинарник в `/tmp` (curl с fallback'ом на wget), распаковывает, запускает `binary -v` (проверка архитектуры), затем **тест конфига против вашего живого `config.yaml`**.
7. Проверка свободного места на целевой файловой системе (запас 4 МБ; старые `.backup/.old/.bak` рядом с бинарником чистятся; если места всё ещё мало — сервис останавливается, чтобы освободить «призрачные» блоки).
8. Делает backup старого бинарника в **`/tmp`** (RAM — не `/opt`), останавливает сервис, заменяет бинарник, проверяет версию и запуск (pidof, до 5 попыток).

**Автоматический откат** срабатывает на любом сбойном шаге: тест бинарника, тест конфига, место, замена, несовпадение версии, старт сервиса. Предыдущий бинарник восстанавливается, сервис снова запускается. Неудачное обновление должно оставить вас ровно там, где вы были.

Примечания:

- Backup в `/tmp` удаляется после успеха — **постоянной копии на `/opt` нет**. Для ручного даунгрейда скачайте нужный релизный бинарник сами (см. раздел 10).
- Updater ищет бинарник через `find /opt -name mihomo | head -1` — если у вас несколько копий, выбор не определён; держите одну.
- Обновляйтесь этим скриптом, а не вручную: ручная процедура существует для особых случаев в [mihomo_manual_update_arm.md](../mihomo_manual_update_arm.md) (RU).

## 9. Обновление watchdog

```bash
curl -fSsL https://raw.githubusercontent.com/saymer-alt/keenetic-auto-setup/main/update-watchdog.sh | sh
```

Updater: скачивает во временный файл → проверяет, что он непустой → проверяет sanity-маркер `MIHOMO WATCHDOG SCRIPT` → проверка синтаксиса `sh -n` → backup текущей копии в `/opt/var/log/mihomo_watchdog.sh.bak.<timestamp>` → атомарный `mv` на место.

**Нюанс с путями (важно):** он обновляет `/opt/bin/mihomo_watchdog.sh`, тогда как `install.sh` разворачивает в `/opt/etc/cron.5mins/mihomo_watchdog`. Перед обновлением проверьте, какая копия реально прописана в crontab (раздел 7.3) — иначе вы обновите файл, который никогда не выполняется.

## 10. Откат

**Автоматический (Mihomo updater).** Встроен в `update-mihomo.sh` на каждом критическом шаге — делать ничего не нужно, предыдущий бинарник возвращается сам.

**Ручной даунгрейд Mihomo (ARM).** Поскольку постоянный backup не хранится:

1. Выберите версию на [github.com/MetaCubeX/mihomo/releases](https://github.com/MetaCubeX/mihomo/releases).
2. На роутере:

```bash
cd /tmp
wget https://github.com/MetaCubeX/mihomo/releases/download/vX.Y.Z/mihomo-linux-arm64-vX.Y.Z.gz
gzip -d mihomo-linux-arm64-vX.Y.Z.gz && chmod +x mihomo-linux-arm64-vX.Y.Z
./mihomo-linux-arm64-vX.Y.Z -v                       # должна напечататься версия
which mihomo                                          # например /opt/bin/mihomo
/opt/etc/init.d/S99mihomo stop
mv /tmp/mihomo-linux-arm64-vX.Y.Z "$(which mihomo)"
/opt/etc/init.d/S99mihomo start
```

3. Проверьте: `mihomo -v`, `ps | grep mihomo`, затем curl-проверку прокси из раздела 5.

**Ручное восстановление watchdog** (если `update-watchdog.sh` пошёл не так): предыдущая копия лежит в `/opt/var/log/mihomo_watchdog.sh.bak.<timestamp>` — скопируйте её `cp` обратно на путь, который прописан в вашем crontab.

## 11. Быстрая диагностика

| Вопрос | Команда | Здоровый ответ |
| --- | --- | --- |
| Mihomo жив? | `/opt/etc/init.d/S99mihomo status` | `alive` |
| RAM Mihomo? | `grep VmRSS /proc/$(pidof mihomo)/status` | замеряйте до/после изменений — фиксированной нормы нет |
| Прокси пропускает трафик? | `curl -x socks5://127.0.0.1:7890 https://ipinfo.io` | IP выходного сервера |
| Watchdog работает? | `cat /opt/var/log/mihomo_watchdog.log` | свежее `[OK] All good` |
| Запись в cron есть? | `grep mihomo_watchdog /opt/etc/crontab` | ровно одна строка |
| Демон cron? | `ps \| grep cron` | процесс cron на месте |
| Хук VoIP применён? | `iptables -t mangle -L \| grep _CUST_BYPASS_WA_` | цепочка есть; счётчики растут во время звонка |
| tmpfs смонтирован? (ram) | `mount \| grep tmpfs` | `/opt/tmp`, `/opt/var/log`, `/opt/var/run` |
| Какие WAN-интерфейсы доступны Mihomo? | `sh mihomo-interface-check.sh` | готовый блок `interface-name:` |
| Перехват транзитного DNS включён? | `ndmc -c "show running-config" \| grep intercept` | `intercept enable` в блоке `dns-proxy` |
| Место / RAM | `df -h /opt`, `free` | — |
| Время верное? | `date` | сбитое время → SSL-ошибки везде |

### Быстрый MT smoke test

После установки или изменения маршрутизации минутная проверка полезнее глубокой диагностики. Создайте в MagiTrickle группу `MT TEST` с несколькими тестовыми сайтами — обычно `2ip.ru`, `2ip.io`, `speedtest.net` — и направьте её через проверяемый выход (например, mitun0). Открытие этих страниц за один заход проверяет сразу несколько уровней: правило срабатывает (клиент действительно попадает под группу), перехват/маршрутизация работают, трафик реально уходит через ожидаемый выход, видимый публичный IP — ожидаемый, а speedtest подтверждает реальную передачу данных. Это smoke test, а не исчерпывающая диагностика всего стека — он просто быстро падает и показывает, куда копать дальше.

### Универсальный пошаговый алгоритм

Когда что-то не работает, идите по пути по порядку — каждый шаг сужает поиск:

1. Интернет работает на самом Keenetic? (состояние WAN — его показывает лог watchdog, раздел 7)
2. DNS клиента приходит туда, куда ожидается? (перехват транзита включён — раздел 6.1)
3. MagiTrickle видит запрос? (сегмент клиента покрыт его списком интерфейсов — MagiTrickle 101)
4. Срабатывает нужное правило? (совпадение группы/правила в UI MagiTrickle)
5. Трафик попадает в ожидаемый выход — ProxyN или mitun0?
6. Mihomo принимает соединение? (порт `7890`/TUN жив — таблица выше)
7. Выбирается правильный outbound? (правила/дашборд Mihomo)
8. Исходящее соединение Mihomo использует ожидаемый Linux-интерфейс? (`interface-name` — помните: это не переключатель WAN)
9. Какой фактический публичный IP? (2ip/ipinfo через проверяемый путь)
10. IP правильный, но сервис всё равно работает плохо? → DNS, MTU, IPv6 (только если сами включали), TLS или сам сервис.

Это модель с контрольными точками, а не мануал по каждому компоненту — где какой компонент живёт, описано в MagiTrickle 101 / Mihomo basics (начало руководства) и разделах 5–7.

## 12. Типовые проблемы

Симптом → причина → решение.

**`opkg update` падает / `curl: (6) Could not resolve host`**
Сломан DNS в Entware. `echo "nameserver 1.1.1.1" > /opt/etc/resolv.conf` (и `8.8.8.8` второй строкой), повторить.

**SSL-ошибки при скачивании (`curl: (60)`, ошибки сертификатов opkg)**
Сбитые часы. `ntpd -q -p pool.ntp.org`, проверить `date`, повторить. Классика на только что загруженном роутере.

**Интернет есть, прокси не работает (особенно `proxy fail [502/...]`)**
Нестабильные/битые DoH-серверы в `config.yaml`. Перейдите на cloudflare-dns / dns.google / quad9. Заодно проверьте сам сервер: `curl -x socks5://127.0.0.1:7890 https://ipinfo.io`.

**`proxy fail [000/000]` / Mihomo не стартует**
Почти всегда `config.yaml` — отсутствует или неверен. `mihomo -d /opt/etc/mihomo -t` напечатает настоящую ошибку; запуск `mihomo -d /opt/etc/mihomo` в foreground покажет логи старта.

**«Всё установилось, но ничего не открывается»**
Нет `config.yaml` (раздел 5) или DNS на клиентах. Также проверьте, что собственный DNS роутера жив — никогда не «тестируйте» изменением default route/DNS как попало.

**Лог watchdog пустой**
Cron не запущен, либо строка в crontab указывает на другую копию скрипта (раздел 7.3). Проверьте `ps | grep cron` и `grep mihomo_watchdog /opt/etc/crontab`.

**Watchdog выполняется дважды (дубли строк в логе)**
Дубли строк в `/opt/etc/crontab` — легко нарожать ручной правкой. Удалите все строки с `mihomo_watchdog`, добавьте одну, перезапустите cron (`/opt/etc/init.d/S10cron restart`).

**`[RATE-LIMIT] Restart blocked` в логе**
Не ошибка — работает 300-секундная защита от циклов.

**Медленно открываются сайты / часть сервисов не работает, остальное в порядке**
Классический симптом MTU на туннелях. Поставьте MTU туннеля 1200–1300 (1500 ломается на DPI/PPPoE многих провайдеров). Это проблема MTU, а не маршрутизации.

**VoIP всё равно не работает**
Проверьте хук: `iptables -t mangle -L _CUST_BYPASS_WA_ -v -n` — счётчики должны расти во время звонка, а политика `bypass_wa` должна указывать на рабочий VPN-интерфейс. Пересоберите firewall или перезагрузитесь, чтобы хук применился заново. На MT7621 не покрывается вовсе (раздел 13).

**Роутер стал нестабильным после установки**
Почти всегда устройство на 128 МБ. Тулкит там не поддерживается; tmpfs доводит такие системы до предела. Максимум — режим `disk`, а лучше — железо помощнее.

**Логи пропали после reboot**
Так задумано в режиме `ram` (tmpfs). При необходимости сохраняйте их сами или используйте `disk`.

**Странности с IPv6 (только если вы включали IPv6 сами)**
Базовая конфигурация держит IPv6 **выключенным намеренно** — MagiTrickle поставляется с отключённым IPv6, а конфиги от link-generators используют `ipv6: false` — чтобы базовая схема оставалась предсказуемой. Если вы включили IPv6, перепроверьте маршрутизацию, DNS и то, что ничего не обходит задуманный IPv4-путь; дальше — обычная IPv6-диагностика.

**Устройство с прописанным вручную внешним DNS ведёт себя иначе / не может достучаться до конкретного внешнего DNS-сервера**
Перехват транзитного DNS (раздел 6.1) перенаправляет классические port-53 запросы в DNS-прокси роутера. Это задуманное поведение; если конкретному устройству действительно нужен прямой доступ к своему DNS-серверу — откатите перехват для всего роутера командами из раздела 6.1.

**Сеть с белым списком: маршрутизация работает, но часть доменов определяется неправильно или перестаёт открываться**
Классическая ловушка — не начинайте с Mihomo. В сети с белым списком такая картина обычно DNS-уровневая, выше MT/Mihomo. Порядок диагностики:

1. **Какой DNS реально используется.** Upstream'ы роутера: `ndmc -c "show ip name-server"` плюс DoT/DoH-записи в running-config (`grep "tls upstream\|https upstream"`). Сторона клиента: включён ли перехват транзита? (раздел 6.1) — если нет, часть устройств может обходить ваш DNS целиком.
2. **Доступен ли выбранный DNS из этой сети?** Сети с белым списком могут делать недоступными даже сервисы с DoH/DoT. Опросите кандидата напрямую (`nslookup ya.ru 77.88.8.8`), затем посмотрите статистику по upstream'ам в `show dns-proxy`: сервер с растущим `R.Sent` и нулевым `A.Rcvd` из этой сети мёртв — меняйте (раздел 6.2).
3. **Что возвращает DNS?** Разрешите проблемный домен через несколько резолверов и сравните ответы. Одинаковые неверные/заблокированные ответы у всех резолверов указывают на фильтрацию на уровне сети, а не на выбор резолвера.
4. **Не используется ли DNS провайдера?** Если DoT/DoH не настроен, Keenetic ходит на серверы ISP — фильтрация/подмена оператора действует на всё, что выше них.
5. **Состояние DoH/DoT:** установлены ли компоненты *DNS-over-TLS/HTTPS proxy* и настроены ли серверы (*Интернет-безопасность → Конфигурация DNS*)? Указаны ли TLS-домены (без домена запрос можно перехватить)?
6. **Проходит ли сам DNS-endpoint через белый список?** Попробуйте из этой сети разрешить имя и достучаться до хоста DoH/DoT-сервера; если не выходит — переключите upstream на DNS провайдера или Yandex DNS и повторите проверку.
7. **Только теперь** смотрите MT/Mihomo: лог watchdog (раздел 7), правила MagiTrickle, проверку туннеля (`curl -x socks5://127.0.0.1:7890 https://ipinfo.io`).

## 13. Особенности MT7621 / mipsel

Универсальный `install.sh` объявляет поддержку mipsel/mips, но этот путь на MT7621 давно не проходил повторное тестирование. Для совместимых MT7621-устройств есть отдельный `install_7621.sh`: он появился из-за наблюдавшихся на этих устройствах TLS-сбоев при скачивании («`curl: (60)`» и друзья; подтверждены ли они свойством платформы — нет). Он обходит это через `--insecure` и HTTP-зеркало, **меняя проверку сертификатов на совместимость** — MITM теоретически возможен; скачивание идёт только с фиксированных известных источников, а fallback-пакет запинован по версии, что снижает практический риск, но трейдофф понимайте.

Отличия от `install.sh`:

| | install.sh | install_7621.sh |
| --- | --- | --- |
| Архитектура | авто (aarch64/armv7/mipsel/mips) | mipsel (совместимые MT7621) |
| TLS | проверяется | `--insecure` + HTTP-зеркало |
| MagiTrickle | ✅ | ❌ не ставится |
| bypass_wa (VoIP) | ✅ | ❌ не ставится |
| Источник Mihomo | релизы `saymer-alt/entware-go` (latest) | HTTP-зеркало, fallback на запинованный `mihomo_1.19.23-1` ipk из тега `mihomo` этого репо |
| Watchdog / Proxy0 / S00ubifs | ✅ | ✅ |

Mihomo на MIPS: **официальных бинарников под mipsel нет** — `update-mihomo.sh` там намеренно отказывается работать. Не «чините» это подстановкой чужих сборок; используйте opkg-пакет или собирайте сами ([docs/09](09-limitations.md)).

Без MagiTrickle маршрутизация на MT7621 — «всё или ничего» (политики по интерфейсам настраиваются в KeeneticOS вручную); без `bypass_wa` VoIP-звонки идут через прокси и будут настолько хороши (или плохи), насколько ваш прокси умеет UDP.

## 14. Известные ограничения

- **128 МБ RAM: не поддерживается.** Не рекомендация — проверенный в продакшене сценарий отказа.
- **Watchdog чинит только Mihomo.** Он не починит мёртвый VPN-сервер, аварию у провайдера, DNS или ошибки в конфиге.
- **У Mihomo есть пределы в работе с UDP** — именно поэтому VoIP идёт мимо него.
- **Entware — не полноценный Linux.** Причуды BusyBox (`$RANDOM`, `pidof`, `ss`, `run-parts`), урезанные пакеты — держите это в голове, прежде чем «модернизировать» скрипты.
- **Логи в RAM пропадают при reboot** — плата за защиту флешки.
- **IPv6 выключен намеренно** в базовой конфигурации — ради предсказуемости, а не по недосмотру. Включение — продвинутое изменение со своей проверкой (см. Типовые проблемы).
- **Docker в этом стеке не используется.** Mihomo на Keenetic управляется init-скриптом (`/opt/etc/init.d/S99mihomo`) — watchdog и updater используют тот же механизм. Команды вида `docker restart mihomo` относятся к другим средам.
- Коммит в `main` этого репо меняет то, что выполнит следующий `curl | sh` — стейджинга и CI нет. Относитесь к обновлениям соответственно.

Больше границ и рассуждения за ними: [docs/09-limitations.md](09-limitations.md).
