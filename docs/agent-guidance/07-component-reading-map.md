## Reading decision: start narrow, escalate when needed

1. Identify requested user outcome, affected subsystem and exact Git ref/SHA. Use scoped symbol search (`git grep -n 'symbol' -- path` / `rg -n`), not recursive file dumps. Search hits are **locations**, not proof of complete behavior.
2. **Low-risk, local-only change** (e.g. text, formatting, non-semantic UI, a read-only helper with no changed safety verdict): read the actual function/block **plus imports, callers, state it touches, adjacent branches and focused tests**. Expand to consumers and negative cases. If you cannot prove the boundary, treat it as high-risk.
3. **High-risk change:** before editing, read the **complete affected safety-critical script(s)** at the verified SHA *once*, then inspect shared contracts and interacting scripts as needed. This includes install/bootstrap, update, migration/import, watchdog restart, locking, process identity, rollback, zRAM/SWAP, storage, service state, and persistent router/ProxyN/DNS/firewall/routing mutations. Changes to Doctor status/FAIL decisions or safety parsers are also high-risk. Do not use an excerpt as the sole safety review.
4. **Escalate immediately** if a supposedly small change touches global initialization, shared helpers, cross-file state, exit codes, error/rollback paths, install/update ordering, or permissions. Reading only a function never justifies skipping a lifecycle invariant or its regression. Never use archived device history as current runtime evidence.
5. After edits, review the entire **diff**, affected callers and tests. Cheap focused tests first; required project CI/QEMU/release gates at the appropriate final SHA. A previous full-file read is reusable only for the *same content/SHA*, not indefinitely. If code changed concurrently, refresh the impacted scope.

## Example: why the decision matters

- A typo in a Doctor **informational string**, with no changed classification or parser behavior: inspect the relevant case/function, output consumer, translations if any, and its focused regression. If it alters `OK/WARN/FAIL`, error handling or prerequisite detection, escalate to the complete Doctor and coupled contracts.
- A change to the Mihomo update/rollback path: read the full affected updater at exact SHA, then the migration or lifecycle consumers it affects; verify stop/commit/restore sequence and relevant negative regressions before changing code.
- For an uncertain bug, perform read-only TRIAGE and save a compact `issue/PR | SHA | symptom | evidence | likely function | next probe` handoff. Don't pre-read four 40–170 KiB files just because all are in KAS.
