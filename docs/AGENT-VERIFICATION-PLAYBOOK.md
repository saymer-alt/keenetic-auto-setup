# Agent verification playbook — KAS / KAS Web

**Статус: инструкция для агентов и план проверок, не отчёт о выполненных испытаниях.** Разработано 30.10.2026 на основе полезных принципов [Pstack](https://github.com/cursor/plugins/tree/main/pstack) и действующих контрактов KAS.

Общие правила: [Proof Before Build](https://github.com/saymer-alt/saymer-alt/blob/main/PROOF-BEFORE-BUILD.md), [общий инженерный стандарт (PR #11)](https://github.com/saymer-alt/saymer-alt/pull/11), [локальная конституция](CONSTITUTION.md), [тестовая стратегия](TESTING_STRATEGY.md). **KAS-SAFETY-001 и остальные safety-гейты имеют приоритет; менять их этим документом запрещено.**

## Доказательством является сценарий пользователя

Для каждого изменения заранее определить наблюдаемое действие, ожидаемое состояние и артефакт проверки. Агент не должен считать `exit 0`, зелёный CI, успешную сборку, существование файла или вывод самого агента достаточным подтверждением функции.

| Пользовательский сценарий | Наблюдаемое состояние/проверка | Опасный край |
| --- | --- | --- |
| Установка с Entware | Версии/архитектура, mount `/opt`, допустимость resource-profile, состояние служб и действующий маршрут | Прерывание загрузки, недоступный источник (`curl 35`), повторный запуск |
| Импорт YAML | После применения действующий `config.yaml`, подтверждённый `mihomo -t` и рабочий процесс | Невалидный YAML и откат на прежнюю конфигурацию без второго Mihomo |
| KAS Web: фильтр подписки | Полученный через Mihomo список; сохранённый exclude-filter; проверенный результат после импорта/перезапуска | Пустой список, устаревшие данные, недоступный Controller API, отмена/снятие фильтра |
| KAS Web: настройки доступа | Доступ только согласно **явно выбранному** режиму, без предположения о сети `Home`/подсети пользователя | Доступ по SSTP/L2TP/из другой подсети; занятый порт; отсутствие секретов в логах |
| Netfilter / bypass | Состояние цепочек и правил до/после изменения и после реальной перезагрузки; наблюдаемое прохождение нужного трафика | Перестройка таблицы, отсутствие цепочки, ложноположительный Doctor |
| Watchdog | Правильная реакция на доступный WAN, недоступный туннель и отсутствие WAN | Отсутствие restart storm; сохранение блокировок и cooldown |
| Обновление / удаление | Состояние до/после, ownership, отсутствие влияния на чужие ресурсы | Повторный uninstall, частично выполненное обновление, rollback |
| Doctor | Read-only, точное разделение INFO/WARN/FAIL и причины | Нельзя исправлять `FAIL` снижением уровня или изменением диагностики ради теста |

Таблица задаёт **будущие и текущие контрольные сценарии**, но **не утверждает, что они уже автоматизированы или успешно пройдены**. Каждый прогон привязывать к точному commit, модели, версии KeeneticOS, профилю памяти и окружению.

## Минимальный цикл агента

1. **Baseline.** Прочитать `AGENTS.md`, конституцию, затронутый код и связанные Issues. Записать симптом, версии и существующее поведение.
2. **Risk / blast radius.** Найти внешние зависимости, побочные эффекты, reboot/retry, доступ к сети и rollback. Для изменения в netfilter/config import отдельно проверить инварианты безопасности.
3. **Smallest fix.** Устранить причину без лишнего нового слоя. При двух неудачных попытках, основанных на одной гипотезе, проверить гипотезу и зафиксировать блокер.
4. **Reproduce → fix → prove.** По возможности иметь минимальный воспроизводящий тест, который падает до изменения и проходит после. В иных случаях явно объяснить недоступность теста и провести ближайшую достоверную проверку.
5. **Evidence tiers.** `CI PASS` / `EMULATOR PASS` / `HARDWARE OBSERVED` / `NOT VERIFIED` не подменяют друг друга. Указывать фактически запущенные команды и доказательства, не расширять область вывода.
6. **Hand-off.** Для серьёзных PR указать diff, проверенные сценарии, непройденные гейты, риски, способ отката и решение, которое ещё требует владельца.

## Как развивать автоматизацию

- Сначала повторно использовать существующие тесты, Doctor и эмулятор; отдельный новый framework оправдать по Proof Before Build.
- Для KAS Web допустима **в перспективе** проектная `verify`-инструкция с картой основных UI-функций и реальным control harness, но это отдельное внедрение, а не предположение о наличии Playwright/CDP.
- Использовать реальные пользовательские входы и проверять изменение persistent state. Моки допустимы для изоляции внешнего сервиса, но не считаются доказательством реального маршрута.
- Не создавать долговечных процессов, не менять активный роутер и не приводить устройство в другое состояние для тестирования без owner GO.
- Если нужна независимая проверка PR, рецензент должен привести конкретный контрпример (команду, лог, тест, реальные состояния), не просто согласиться с автором.
- Не строить десятки одинаковых E2E и не заменять живые испытания зелёными отчётами. У каждого нового прогона должна быть проверяемая новая гипотеза, риск либо изменение.
