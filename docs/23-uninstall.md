# KAS — безопасное удаление: проверка состояния

**Доступны только режимы чтения `--check` и `--plan`. Автоматическое удаление пока НЕ реализовано.**
[Задача #179](https://github.com/saymer-alt/keenetic-auto-setup/issues/179).

## Почему недостаточно opkg remove

KAS может настраивать ProxyN, policy `bypass_wa`, правила Netfilter,
`dns-proxy intercept`, cron/watchdog, а также устанавливать Mihomo и MagiTrickle.
Старые версии не сохраняли полноценные данные о том, какие объекты созданные KAS,
а какие использовались раньше. Удаление по имени вроде `Proxy0` опасно.

Нельзя считать `opkg remove mihomo magitrickle` безопасным полным удалением.
Не удаляйте целиком `/opt/etc/mihomo`, чужие политики, Entware, swap/zRAM,
глобальный DNS или общий MagiTrickle.

## Журнал для новых установок

Текущий опубликованный `install.sh` создаёт приватный журнал
`/opt/etc/keenetic-auto-setup/ownership.v1` (**KAS_OWNERSHIP_V1**).
Запись выполняется атомарно с правами `0600`, после успешного создания/включения объекта.
На повторном запуске журнал не объявляет уже существовавшие объекты собственностью KAS.

В журнал могут попадать только подтверждённые новые объекты: конкретный `ProxyN`,
новая политика `bypass_wa`, включение ранее выключенного DNS-перехвата,
ранее отсутствовавшие пакеты `mihomo`/`magitrickle`,
`magitrickle.conf`, Netfilter-хук, watchdog и `S00ubifs`.
Чужие/переиспользованные элементы туда не записываются.

**Журнал — необходимое, но недостаточное условие удаления:** ресурс мог стать общим
уже после установки. Перед фактическим удалением нужно проверить актуальную
конфигурацию и зависимости. Запись о включении DNS-перехвата, например,
сама по себе **не разрешает его выключить**.

На старых установках без журнала `--remove` и `--purge` запрещены; наличие журнала само по себе пока не включает их.
Универсального `--force` не будет: так можно удалить чужой ProxyN или политику.

### Особенность MagiTrickle

У MagiTrickle существует штатная процедура удаления: остановить
`S99magitrickle`, выполнить `opkg remove magitrickle`, при желании очистить
`/opt/var/lib/magitrickle` и удалить репозиторий Entware.
В KAS это **разные решения**:

- остановка сервиса и удаление пакета — только при подтверждённом создании
  пакета этим KAS и отсутствии признаков совместного использования;
- содержимое `/opt/var/lib/magitrickle` — пользовательские настройки,
  по умолчанию **сохраняется**; очистка допускается лишь по отдельному
  подтверждению в будущем `--purge` и после резервной копии;
- `/opt/etc/opkg/magitrickle.conf` удаляется только если он создан KAS
  и после проверки, что репозиторий больше никому не требуется;
- `curl`, `jq`, `nano`, `cron`, базовый Entware и компоненты KeeneticOS
  деинсталлятор не удаляет.

## Проверка на тестовом KN-1010

После публикации в `main` скачать диагностический скрипт в отдельный временный файл и запустить **только** `--check`:

```sh
curl -fSsL -o /tmp/kas-uninstall.sh https://raw.githubusercontent.com/saymer-alt/keenetic-auto-setup/main/uninstall.sh && sh -n /tmp/kas-uninstall.sh && sh /tmp/kas-uninstall.sh --check
```

Пришли вывод для проверки признаков `SHARED_OR_FOREIGN` и `UNKNOWN`. **Пока не выполнять** `opkg remove`, `rm -rf`, `--remove` и `--purge` и не стирать Entware: иначе нельзя будет проверить настоящий деинсталлятор. Даже при чистом Entware у KeeneticOS могут сохраниться старые ProxyN, а их состав может измениться между двумя проверками.

## План удаления с учётом зависимостей

`uninstall.sh --plan` выполняет **только чтение** и использует валидированный
`ownership.v1` и отдельные блоки каждого интерфейса ProxyN из
`show running-config`. План фиксирует действующие/выключенные
интерфейсы, указывающие на `127.0.0.1:7890`, как препятствие удалению
Mihomo. Владелец `ProxyN` не определяется по подписи — нужна запись в журнале.

```sh
curl -fSsL -o /tmp/kas-uninstall.sh https://raw.githubusercontent.com/saymer-alt/keenetic-auto-setup/main/uninstall.sh &&
sh -n /tmp/kas-uninstall.sh &&
sh /tmp/kas-uninstall.sh --plan
```

`BLOCKED` — автоматическое удаление пока запрещено, `REVIEW` — объект
требует отдельной проверки и правильного порядка действий,
`PRESERVE` — объект сохраняется. Даже состояние `Proxy1 down`
само по себе не означает право удалить этот чужой интерфейс.
**Реальных операций удаления `--remove` / `--purge` в этой версии нет.**

### Проверка девяти записей перед настоящим удалением

Аппаратное испытание KN-1010 от 22.10.2026 подтвердило: после ручного
`opkg remove mihomo` и `opkg remove magitrickle` конфигурации
`/opt/etc/mihomo/config.yaml` и
`/opt/var/lib/magitrickle/config.yaml` **исчезли из исходных каталогов**.
Обязательны приватная резервная копия обеих YAML, проверка идентичности
копий и восстановление после удаления пакетов; сам факт `opkg remove`
не обещает сохранности конфигурации.

В `--plan` теперь **различаются**:

- Если найден хоть один ProxyN, указывающий на `127.0.0.1:7890`, **без
  записи `owned|proxy|ProxyN`**, Mihomo отмечается `BLOCKED`: чужой интерфейс
  оставляем нетронутым и не ломаем его зависимость.
- Если **все** обнаруженные ProxyN на порту 7890 записаны как созданные KAS
  и пакет Mihomo также записан как собственный, выводится `REVIEW`: перед
  удалением необходимо проверить маршрутизацию/политики, затем отсоединить
  собственные интерфейсы и заново проверить отсутствие зависимостей.
  `REVIEW` **не означает разрешение на удаление**.
- При записи `owned|policy|bypass_wa` политика отмечается `REVIEW`:
  другие правила, привязки и маршруты могли появиться позднее. При
  отсутствии такой записи политика остаётся `PRESERVE`.
- При записи `enabled|dns|intercept` DNS-перехват также `REVIEW`.
  Одной записи недостаточно для отключения: MagiTrickle или другие
  сервисы могли начать его использовать. Если KAS его не включал,
  режим `PRESERVE` обязателен.
- Для обоих YAML выводится `BACKUP_REQUIRED` — **до** остановки
  сервисов и удаления OPKG-пакетов.

Эти изменения касаются только **плана чтения**. Режимы `--remove` и
`--purge` по-прежнему возвращают код 3 без изменения роутера.
Отдельный следующий этап: lifecycle lock, снимок состояния, откат,
точечный Netfilter teardown, OPKG stop/remove с восстановлением конфигов
и полевой тест на KN-1010.

## Приватный снимок перед удалением (только данные, без остановки служб)

Новый отдельный `uninstall-snapshot.sh` собирает резервную копию **перед**
будущим `--remove`. Он не удаляет пакеты, не переключает ProxyN и не меняет
настройки KeeneticOS. `--check` не создаёт файлов; `--create` пишет
доказательства и копии в уникальный каталог под
`/opt/kas-uninstall-backups/` с правами `0700`, файлы `0600`.

Сохраняются журнал владения, оба YAML, общий crontab, KAS hook/watchdog,
MagiTrickle feed, скрипты инициализации пакетов, текущие конфигурация
KeeneticOS, таблица политик, `iptables -t mangle -S` и список OPKG-пакетов.
Каждая скопированная конфигурация проверяется командой `cmp`, а маркер
`READY` создаётся **только после успешного снимка**. При ошибке каталог
неполного снимка остаётся для диагностики, но не признаётся готовым.

Снимок блокируется при отсутствующем, некорректном или символьном
`ownership.v1`, повторяющихся записях, отсутствующих YAML для
journal-owned пакетов, недоступной конфигурации роутера или активном
lifecycle/maintenance-маркере. Проверка маркера — ещё **не** полноценная
транзакционная блокировка; её нужно реализовать для настоящего удаления.

**Важно:** YAML и `running-config` могут содержать пароли, токены и другие
секреты. Каталог снапшота хранится в файловой системе Entware — его
нельзя публиковать и копировать в issue. В выводе указывается только путь.

После публикации новой версии в `main` запуск будет:

~~~sh
curl -fSsL -o /tmp/kas-uninstall-snapshot.sh https://raw.githubusercontent.com/saymer-alt/keenetic-auto-setup/main/uninstall-snapshot.sh &&
sh -n /tmp/kas-uninstall-snapshot.sh &&
sh /tmp/kas-uninstall-snapshot.sh --check
~~~

Только после успешного `--check` можно добровольно запустить
`sh /tmp/kas-uninstall-snapshot.sh --create`.
После создания снимка следует независимо проверить его целостность и
актуальность **второй** read-only командой:

~~~sh
curl -fSsL -o /tmp/kas-uninstall-snapshot-verify.sh https://raw.githubusercontent.com/saymer-alt/keenetic-auto-setup/main/uninstall-snapshot-verify.sh &&
sh -n /tmp/kas-uninstall-snapshot-verify.sh &&
sh /tmp/kas-uninstall-snapshot-verify.sh 20261022-182643-5879
~~~

Аргумент — **только имя каталога**, не абсолютный путь; скрипт проверяет
фиксированный каталог `/opt/kas-uninstall-backups/`. Он отказывается работать
с символьными ссылками, ослабленными правами, изменёнными YAML, файлами,
`running-config`, политиками, `iptables`, списком пакетов или с повреждённым
манифестом. Никакие секреты из копий не выводятся. При изменениях нужно создать
**новый** снимок, а не использовать устаревший.

Верификация не заменяет атомарный lifecycle lock. Будущий `--remove`
должен заново выполнить контроль после получения эксклюзивной блокировки.

Это **не деинсталлятор**: `uninstall.sh --remove` и `--purge` остаются
заблокированы.

### Имена интерфейсов в `bypass_wa`

На KN-1010 KeeneticOS 5.1.8 `ndmc -c 'show running-config'` может
вывести `no permit global ISP` вместо
`no permit global GigabitEthernet1`. `ISP` — псевдоним (`rename ISP`)
WAN `GigabitEthernet1`, а не отдельный интерфейс.

В `uninstall-transaction-gate.sh` оба варианта допускаются, **но** алиас
`ISP` принимается только при одном проверенном соответствии
`interface GigabitEthernet1` → `rename ISP` в том же текущем выводе
конфигурации. Пропавший, дублированный либо назначенный другому интерфейсу
псевдоним блокирует проверку. Дополнительные разрешения, повторяющиеся
директивы или новые правила политики также блокируют её.

Исправление относится только к режиму проверки `--check`. Оно не меняет
WAN, не удаляет интерфейсы и не разрешает `uninstall.sh --remove`.

## Транзакционный gate перед удалением (READ ONLY)

После того как резервная копия проверена, `uninstall-transaction-gate.sh`
дополнительно проверяет, что текущая система соответствует **узкому,
аппаратно проверенному профилю KN-1010**: ровно девять записей владения,
один канонический `Proxy0` на `127.0.0.1:7890`, простая политика
`bypass_wa`, включённый самим KAS DNS intercept и живая цепочка mangle.

Проверка **блокируется**, если обнаружены чужие ProxyN на 7890, новые
директивы Proxy0, изменённые правила/привязки политики, отсутствие DNS
intercept, изменённые данные снимка или активный maintenance-маркер.
Она вызывает самостоятельный верификатор снимка перед проверкой.

Команда (только после публикации PR в main):

~~~sh
curl -fSsL -o /tmp/uninstall-snapshot-verify.sh https://raw.githubusercontent.com/saymer-alt/keenetic-auto-setup/main/uninstall-snapshot-verify.sh
curl -fSsL -o /tmp/uninstall-transaction-gate.sh https://raw.githubusercontent.com/saymer-alt/keenetic-auto-setup/main/uninstall-transaction-gate.sh
sh -n /tmp/uninstall-transaction-gate.sh
sh /tmp/uninstall-transaction-gate.sh --check 20261022-182643-5879
~~~

Скрипт принимает только `--check` и **не выполняет ни одной операции
удаления**. Успех подтверждает только структурную готовность; внешние
потребители Mihomo/MagiTrickle и будущие зависимости DNS могут быть
недоступны для достоверной инвентаризации. Перед реальным `--remove`
нужны отдельное согласие оператора, общий lifecycle lock, backup с
транзакционным журналом, безопасный Netfilter teardown, восстановление YAML,
проверка восстановления и испытание отказов.

## Только просмотр

Скачанный отдельно `uninstall.sh` можно запустить в режиме:

~~~sh
sh uninstall.sh --check
~~~

Аудитор читает файлы Entware, `opkg list-installed` и только информационные
`ndmc -c 'show running-config'`, `ndmc -c 'show ip policy'` и
`iptables -t mangle -S _CUST_BYPASS_WA_`. Он не останавливает службы,
не сохраняет настройки и не удаляет файлы.

- `ABSENT`: объект не обнаружен по доступным данным.
- `SHARED_OR_FOREIGN`: пользовательский/общий объект — сохранить.
- `UNKNOWN`: принадлежность не доказана или чтение не удалось — не удалять.

Даже узнаваемое имя, запись в журнале или содержимое не доказывают эксклюзивное владение KAS.
При успешной проверке журнала `--check` показывает записи `RECORDED`, но ничего не удаляет.
Аудитор не выводит содержимое пользовательского YAML и его секреты.

## Режимы удаления

~~~sh
sh uninstall.sh --check
sh uninstall.sh --plan
sh uninstall.sh --remove [SNAPSHOT]
sh uninstall.sh --purge
~~~

`--remove` — транзакционное удаление через `uninstall-transaction.sh`
(см. следующий раздел). `--purge` остаётся **NOT_IMPLEMENTED** (код 3) и
намеренно отделён от `--remove`. Для старых установок без валидного
ownership-журнала `--remove` отказывает без изменений — защиты для
legacy-инсталляций без provenance сохранены.

### Транзакция `--remove`

Предусловия (отказ ДО любых изменений):

1. verified-снимок (`uninstall-snapshot.sh --create` + verify);
2. строгий nine-claim gate (`uninstall-transaction-gate.sh --check`);
3. маркер `--prepare` (lifecycle lock, повторная сверка состояния);
4. **rollback cache**: `.ipk` установленных версий `mihomo`/`magitrickle`
   + sha256 MANIFEST внутри снимка. Если точные версии недоступны —
   `--remove` отказывает до мутации (восстановимость важнее удаления).

Журнал `transaction/journal.v1` пишет intent перед каждым шагом. Шаги
(идемпотентные, state-aware): cron-расписание → watchdog-файлы → netfilter
jump+chain (точный `-D` из live-сериализации, без flush) → хук → стоп
сервисов → `no ip policy bypass_wa` → `no interface Proxy0` +
`system configuration save` → `opkg remove` двух owned-пакетов → feed →
ledger. Прерванная транзакция возобновляется аудитом фактического
состояния (prefix-консистентность) или завершается fail-closed. Повторный
`--remove` после завершённого удаления — идемпотентный no-op (PASS).

**Сохраняется всегда:** чужие ProxyN/политики/цепочки/правила, чужие
cron-строки (включая любые упоминания `mihomo_watchdog` — они блокируют
удаление), пользовательские YAML (копии в снимке), общий MagiTrickle при
shared-use, Entware и системные пакеты, **DNS intercept** (умолчание:
не отключается без доказанной эксклюзивности).

## Очистка Netfilter без перезагрузки

Хук `/opt/etc/ndm/netfilter.d/020-bypass_wa.sh` выполняется KeeneticOS
**при пересоздании таблицы Netfilter**, а не непосредственно при любом
`up/down` интерфейса. Поэтому переключение интерфейса *может* инициировать
пересоздание `mangle`, но не гарантирует его и не доказывает исчезновение
пользовательской цепочки `_CUST_BYPASS_WA_`.

Последовательность для будущего `--remove` на выделенном стенде:

1. Зафиксировать правила `iptables -t mangle -S PREROUTING` и
   `iptables -t mangle -S _CUST_BYPASS_WA_` и актуальную mark политики;
   подтвердить единственную проектную ссылку и точный набор трёх правил
   (MARK/CONNMARK/RETURN) на порты 1400,3478,3482.
2. Под lifecycle lock убрать **только журналируемый и проверенный**
   `020-bypass_wa.sh`, предварительно сохранив его для восстановления.
3. При необходимости использовать контролируемое изменение **безопасного**
   интерфейса для перестройки таблицы. Нельзя безусловно переключать
   WAN или активный `Proxy0`: на KN-1010 он служит политике маршрутизации.
4. Повторно прочитать обе таблицы `iptables -S`: отсутствие хука
   не означает автоматически, что исчезли live jump/chain.
5. Если записи сохранились, допускается отдельная **точечная** очистка
   лишь после проверки сигнатур, всех входящих ссылок и возможности rollback.
   Никаких `iptables -F` для всей таблицы mangle, никаких удалений общих
   политик или чужих цепочек.

Нельзя считать успешным uninstall, если в `PREROUTING` остался jump на
`_CUST_BYPASS_WA_` или в системе сохранилась неожиданная цепочка.
После изменения состояния интерфейса нужна повторная проверка, а не
предположение, что KeeneticOS всё удалил.

Источник принципа hook: [официальное описание OPKG/netfilter.d Keenetic](https://support.keenetic.com/hero/kn-1011/en/42407-opkg-component-description.html).

**Полевое наблюдение KN-1010 (22.10.2026):** изначально одновременно
существовали Proxy0→1081 и Proxy1→7890; в более позднем снимке MCP
Proxy1 и Policy0 уже отсутствуют, а Proxy0 остаётся активным.
Поэтому preflight выполняется непосредственно перед любой операцией;
старый снимок не заменяет актуальное состояние.

## Транзакционная подготовка под lifecycle lock

`uninstall-transaction.sh --prepare SNAPSHOT_NAME` — промежуточный
этап разработки из #179. Скрипт повторно запускает строгий gate и
независимую верификацию резервной копии, затем получает **общую** с
установщиком/обновлятором Mihomo lifecycle-блокировку. Уже под ней
вторично сверяет YAML, ownership, crontab, hook/watchdog, текущее
`running-config`, политики, полный список OPKG и состояние
`iptables -t mangle -S` с проверенным снимком.

Netfilter-проверка требует ровно одну цепочку
`_CUST_BYPASS_WA_`, один переход из `PREROUTING` и три ожидаемых
правила MARK/CONNMARK/RETURN для портов 1400,3478,3482. Неизвестные
правила внутри цепочки или дополнительные ссылки приводят к
`BLOCKED`. Это защита от удаления чужих правил и последующей потери
сетевого доступа.

Только после успешных проверок в закрытый каталог снимка добавляется
`transaction/prepare.v1` со статусом
`PREPARED_NO_DEVICE_MUTATIONS`. Marker фиксирует готовность
**без полномочия** на удаление. Команды `--remove` и `--purge`
по-прежнему возвращают код 3.

Чтобы запустить только этап подготовки после публикации в `main`,
нужно загрузить три скрипта в один каталог: `uninstall-snapshot-verify.sh`,
`uninstall-transaction-gate.sh` и `uninstall-transaction.sh`.
Проверка требует актуального снимка и не останавливает сервисы.

Дополнительно добавлен **только для изолированных CI-фикстур**
режим `--rehearse`. Он под lifecycle lock временно удаляет файлы,
которые журнал признаёт созданными KAS (watchdog binary/wrapper и
Netfilter hook), точно исключает проектную строку из общего cron (или
сохраняет общий `run-parts`) и восстанавливает файлы из приватного
снимка. В тестах внедряются отказы после удаления wrapper, binary,
hook и cron; после каждого отказа нужно восстановить все исходные файлы
побайтово. **На настоящем роутере этот режим заблокирован**; это
испытание восстановления файлов, а не тест маршрутизации или OPKG.

**Оставшаяся часть работы:** испытания отказов при остановке
служб, точечном Netfilter teardown, удалении Proxy0/policy, пакетном
OPKG uninstall с сохранением/восстановлением двух YAML и сценариях
отката. Только после этого вводить реальный `--remove`.

## Состояние реализации (23.10.2026)

`--remove` реализован (PR #215): журнал, rollback cache, точечное снятие,
идемпотентность и resume покрыты фикстур-тестами в
`tests/uninstall-remove-regression.py` (dash + BusyBox ash).

Gate-контракт Proxy0: принимается **любой единственный отрендеренный
положительный** `ip global <N>`. Установщик ставит `ip global auto`;
номер выделяет аллокатор NDMS (350 на KN-1010-стенде, 32767 на Ported
5.1.8) и не является сигналом владения — владение доказывается ledger
claim + канонической сигнатурой + single-consumer scan + байтовым
сравнением со снимком. Дубль/отсутствие/не-число — BLOCKED.

До аппаратной приёмки на запасном KN-1010 merge в main не выполняется.
`--check` остаётся read-only и не является удалением. `--purge` требует
отдельного подтверждения и резервной копии. Тесты на стенде, а не на
основном роутере.

### Восстановление после удаления (rollback)

Снимок содержит всё необходимое: `packages/*.ipk` точных версий (с
MANIFEST), `files/` с копиями обоих пользовательских YAML и конфигураций,
`running-config`/`ip-policy`/`iptables-mangle`/`opkg-packages` на момент
снимка. Ручное восстановление:

~~~sh
opkg install /opt/kas-uninstall-backups/SNAP/packages/*.ipk
cp -p /opt/kas-uninstall-backups/SNAP/files/opt/etc/mihomo/config.yaml /opt/etc/mihomo/
cp -p /opt/kas-uninstall-backups/SNAP/files/opt/var/lib/magitrickle/config.yaml /opt/var/lib/magitrickle/
~~~

Либо повторная установка `install.sh disk` и возврат YAML из снимка.
Частично завершённая транзакция: повторный `--remove` запустит аудит
состояния и продолжит/остановится fail-closed; снимок не удаляется
транзакцией и остаётся источником восстановления.

## Аппаратная приёмка на запасном KN-1010 (read-only preflight)

Стенд: Keenetic Giga KN-1010, KeeneticOS 3.05/5.x (проверить фактическую
`show version`), Entware на EXT4, ~248 MB RAM, внешний SWAP ~468 MB.
Перед испытанием состояние устройства перечитывается заново. Домашний
NC-4210 и рабочие роутеры НЕ используются. Физический `--remove` — только
после отдельного Owner GO.

Последовательность (все шаги до `--prepare` не меняют систему):

~~~sh
sh uninstall.sh --check                 # инвентарь: ledger/packages/Keenetic state
sh uninstall.sh --plan                  # блокеры и REVIEW-заметки
sh uninstall-snapshot.sh --create       # приватный снимок (+ verify)
sh uninstall-snapshot-verify.sh SNAPSHOT_NAME
sh uninstall-transaction-gate.sh --check SNAPSHOT_NAME
sh uninstall-transaction.sh --prepare SNAPSHOT_NAME
# rollback cache: убедиться в [PASS] Rollback cache verified и сохранить
# путь к снимку; opkg download требует доступности фидов с точными версиями
ls -l /opt/kas-uninstall-backups/SNAPSHOT_NAME/packages/
~~~

Ожидаемые результаты: `[LEDGER] ownership.v1` валиден (nine-claim),
gate — `[PASS] Nine-claim KAS transaction preflight`, prepare —
`[PASS] KAS uninstall transaction prepared` + `[PASS] Rollback cache
verified`. Любой BLOCKED на этом пути означает: аппаратная приёмка
откладывается до устранения причины.

После виртуальной приёмки (QEMU) владелец даёт отдельный GO на реальный
`sh uninstall.sh --remove SNAPSHOT_NAME`. Контроль после аппаратного
удаления: сохранность чужих ресурсов, работа KeeneticOS/Entware, отсутствие
KAS-owned остатков, возможность повторной установки, Doctor без FAIL.
