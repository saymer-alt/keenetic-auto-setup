# S00ubifs — защита флешки и RAM-режим

Почему используется tmpfs и где это НЕ нужно включать.

---

## Задача

Снизить износ флешки (/opt) за счёт переноса временных данных в RAM.

---

## Проблема

Entware активно пишет:
- логи (mihomo, watchdog)
- PID-файлы
- временные файлы
- кэши

При постоянной работе:

👉 флешка умирает через 6–12 месяцев  
👉 особенно на 20+ роутерах  

---

## Решение

Перенести volatile-данные в RAM:

```

/opt/tmp
/opt/var/log
/opt/var/run

```

через tmpfs

---

## Как это работает

Сервис:

```

/opt/etc/init.d/S00ubifs

````

Запускается раньше всех (`S00`).

---

### При старте

Размеры подбираются автоматически по свободной RAM (профили):

| Профиль | Свободная RAM | /opt/tmp | /opt/var/log | /opt/var/run |
| ------- | ------------- | -------- | ------------ | ------------ |
| low     | < 40 МБ       | 5M       | 2M           | 512k         |
| medium  | < 80 МБ       | 10M      | 5M           | 1M           |
| high    | ≥ 80 МБ       | 20M      | 10M          | 1M           |

```bash
mount -t tmpfs -o size=$SIZE,mode=$MODE,noatime,nosuid,nodev tmpfs "$d"
````

---

### Что остаётся на диске

* /opt/bin (пакеты)
* /opt/etc (конфиги)
* config.yaml
* crontab

---

### Что уходит в RAM

* логи
* временные файлы
* сокеты
* PID

---

## Почему это важно

Без этого:

* постоянная запись на флешку
* деградация скорости
* eventual failure (смерть накопителя)

---

## Главный момент: ОГРАНИЧЕНИЕ ПО RAM

👉 **Memory-profile проекта:** 256 МБ поддерживается только с активным штатным zRAM независимо от места /opt. На 512 МБ+ установка не блокируется, но должен быть хотя бы один активный memory-pressure fallback (zRAM или подходящий swap); если его нет, проект выдаёт явный WARN и не даёт гарантий устойчивости при memory pressure.

128 МБ-класс допускается **только как best-effort/experimental и только при внешнем /opt + активном storage-backed swap на внешнем носителе >= 384 МБ** (512 МБ предпочтительно). Без этого установщик останавливается на раннем preflight, до скачиваний и изменений; неопределимое состояние носителя — консервативный отказ с указанием, что именно не верифицировано. Сам проект swap и носители никогда не создаёт и не меняет.

---

## ⚠️ 128 МБ: BEST-EFFORT (реальный опыт)

### 128 МБ устройства

Примеры:

* Keenetic Extra (MT7628)
* Keenetic Viva старый (MT7621, 128MB)

---

### Что происходит

* RAM занята почти полностью (~120/128)
* не стартуют штатные сервисы Keenetic
* нестабильная работа
* random падения

👉 система начинает "сыпаться"

---

### Вывод

Установка на 128MB **разрешена только при внешнем /opt и активном storage-backed swap на внешнем носителе от 384 МБ** (512 МБ предпочтительно), и стабильность не гарантируется даже со swap. Реальный опыт показал, что сочетание малого запаса RAM и tmpfs способно дестабилизировать Keenetic. Поэтому сначала предпочтителен `disk`; `ram` — только осознанный эксперимент с наблюдением за памятью.

---

## zRAM и дисковый swap — разные вещи

KeeneticOS имеет встроенный zRAM («Сжатый RAM-диск для системного swap»): swap в сжатой RAM, без записи классического swap-файла во внутреннюю NAND. Включается в системных настройках производительности (точный путь/формулировки зависят от прошивки и языка). После установки проверьте фактически активный объём и бэкенды через `mihomo-doctor.sh`. Не предполагаем размер zRAM по объёму физической RAM — оценивается только реальное активное состояние.

Состав бэкендов активного swap различается, и для 128 МБ-класса это критично:

* **zRAM** — сжатый swap в RAM; байт в NAND не пишет. На 128 МБ-классе он может быть дополнительным backend'ом, но независимо от его фактического размера **не считается** в обязательный минимум >=384 МБ внешнего storage-backed swap.
* **Дисковый swap** (раздел или swap-файл на внешнем носителе) — классический бэкенд; во внутреннюю NAND
  swap-файл не кладём.

128 МБ: требование — **внешний /opt + >= 384 МБ storage-backed swap на внешнем носителе** (512 предпочтительно); zRAM в этот минимум не входит; даже с ними — best-effort.
256 МБ: активный zRAM обязателен независимо от того, внутренний или внешний /opt.
512 МБ+: внутренний/внешний /opt разрешены; нужен хотя бы один активный zRAM/swap как рекомендуемый memory-pressure fallback, иначе явный WARN; внешний /opt + дисковый swap — проверенный,
но не обязательный паттерн.

Проект сам никогда не создаёт, не включает и не меняет размер swap — только оценивает и сообщает.

---

## ✔️ Рекомендуется

| RAM     | Статус                  |
| ------- | ----------------------- |
| 128 MB  | ⚠️ best-effort / experimental: внешний /opt + внешний storage-backed swap >= 384 МБ (512 предпочтительно; zRAM не считается) |
| 256 MB  | ✅ поддерживается только с активным штатным zRAM независимо от места /opt |
| 512 MB+ | ✅ нормально; без любого активного zRAM/swap — явный WARN и без гарантии устойчивости при memory pressure |
| 1024 MB | ✅ идеально              |

## Почему именно такие размеры tmpfs

Значения ниже — профиль high (≥ 80 МБ свободной RAM); при меньшем объёме скрипт уменьшает размеры сам (см. выше).

| Директория   | Размер | Почему          |
| ------------ | ------ | --------------- |
| /opt/tmp     | 20M    | временные файлы |
| /opt/var/log | 10M    | логи            |
| /opt/var/run | 1M     | PID и сокеты    |

## Что теряется при reboot

Это важно понимать:

* логи watchdog
* логи mihomo
* временные файлы

👉 это НОРМАЛЬНО

---

## Когда использовать disk режим

Если:

* мало RAM
* нужен persistent лог
* нестабильность системы

👉 отключить tmpfs

---

## Почему не весь /opt в RAM

Потому что:

* пакеты должны сохраняться
* конфиги должны сохраняться
* иначе после reboot всё исчезнет

---

## Почему именно init.d (S00)

* запускается раньше всех сервисов
* гарантирует, что:

  * cron
  * mihomo
  * watchdog

уже работают с tmpfs

---

## Частые проблемы

### Не смонтировалось

Причины:

* мало RAM
* ошибка mount

Проверка:

```bash
dmesg | grep tmpfs
```

---

### Система стала нестабильной

👉 почти всегда нехватка RAM

Решение:

* отключить S00ubifs
* или перейти на роутер с 256+ МБ
