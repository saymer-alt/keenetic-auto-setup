# S00ubifs — защита флешки и RAM-режим

Почему используется tmpfs и где это НЕ нужно включать.

---

## Задача

Снизить износ флешки (/opt) за счёт переноса временных данных в RAM.

---

## Проблема

Entware активно пишет:
- логи (mihomo, watchdog)
- PID-файлы
- временные файлы
- кэши

При постоянной работе:

👉 флешка умирает через 6–12 месяцев  
👉 особенно на 20+ роутерах  

---

## Решение

Перенести volatile-данные в RAM:

```

/opt/tmp
/opt/var/log
/opt/var/run

```

через tmpfs

---

## Как это работает

Сервис:

```

/opt/etc/init.d/S00ubifs

````

Запускается раньше всех (`S00`).

---

### При старте

Размеры подбираются автоматически по свободной RAM (профили):

| Профиль | Свободная RAM | /opt/tmp | /opt/var/log | /opt/var/run |
| ------- | ------------- | -------- | ------------ | ------------ |
| low     | < 40 МБ       | 5M       | 2M           | 512k         |
| medium  | < 80 МБ       | 10M      | 5M           | 1M           |
| high    | ≥ 80 МБ       | 20M      | 10M          | 1M           |

```bash
mount -t tmpfs -o size=$SIZE,mode=$MODE,noatime,nosuid,nodev tmpfs "$d"
````

---

### Что остаётся на диске

* /opt/bin (пакеты)
* /opt/etc (конфиги)
* config.yaml
* crontab

---

### Что уходит в RAM

* логи
* временные файлы
* сокеты
* PID

---

## Почему это важно

Без этого:

* постоянная запись на флешку
* деградация скорости
* eventual failure (смерть накопителя)

## Главный момент: ОГРАНИЧЕНИЕ ПО RAM

👉 **Memory-profile проекта:** на 256 МБ-классе проект ожидает **один** активный backend: штатный zRAM **или** внешний storage-backed swap; отсутствие обоих — WARN, установка продолжается. На **512 МБ-классе один из этих backend обязателен для поддерживаемой новой установки**: отсутствие и zRAM, и проверенного внешнего storage-backed swap — ERROR installer / FAIL Doctor. Для внешнего swap на 256/512 МБ-классе проект использует две границы: **1× обнаруженной RAM** как warning floor и **3× RAM** как предпочтительный target (не более **2 ГиБ**). Ниже 1× — WARN; от 1× до 3× — только INFO; выше 2 ГиБ — ERROR новой установки / FAIL Doctor. На устройствах выше 512 МБ-класса swap/zRAM опциональны. Если одновременно активны zRAM и внешний дисковый/file swap, проект выдаёт WARN: документация производителя рекомендует при использовании классического swap отключать zRAM.

128 МБ-класс допускается **только как best-effort/experimental и только при внешнем EXT4 `/opt` + активном storage-backed swap на внешнем носителе >=384 МБ**. Порог 384 МБ — наш project-specific experimental floor, а не заявленный производителем минимум. zRAM этот минимум не заменяет. Без условий установщик останавливается на раннем preflight, до скачиваний и изменений; неопределимое состояние носителя — консервативный отказ. Сам проект swap и носители никогда не создаёт и не меняет.

## ⚠️ 128 МБ: BEST-EFFORT (реальный опыт)

### 128 МБ устройства

Примеры:

* Keenetic Extra (MT7628)
* Keenetic Viva старый (MT7621, 128MB)

---

### Что происходит

* RAM занята почти полностью (~120/128)
* не стартуют штатные сервисы Keenetic
* нестабильная работа
* random падения

👉 система начинает "сыпаться"

---

### Вывод

Установка на 128MB **разрешена только при внешнем EXT4 `/opt` и активном storage-backed swap на внешнем носителе от 384 МБ** (project-specific experimental floor), и стабильность не гарантируется даже со swap. Реальный опыт показал, что сочетание малого запаса RAM и tmpfs способно дестабилизировать Keenetic. Поэтому сначала предпочтителен `disk`; `ram` — только осознанный эксперимент с наблюдением за памятью.

## zRAM и дисковый swap — разные вещи

KeeneticOS имеет встроенный zRAM («Сжатый RAM-диск для системного swap»): swap в сжатой RAM, без записи классического swap-файла во внутреннюю NAND. Включается в системных настройках производительности (точный путь/формулировки зависят от прошивки и языка). После установки проверьте фактически активный объём и бэкенды через `mihomo-doctor.sh`. Не предполагаем размер zRAM по объёму физической RAM — оценивается только реальное активное состояние.

Состав бэкендов активного swap различается:

* **zRAM** — сжатый swap в RAM; байт в NAND не пишет.
* **Дисковый swap** (раздел или swap-файл на внешнем носителе) — классический backend; во внутреннюю NAND swap-файл не кладём.
* **Не смешиваем их как штатный профиль.** В актуальной документации производителя прямо сказано: при использовании раздела/файла подкачки zRAM следует предварительно отключить. Скрипты это состояние не исправляют сами, а только показывают WARN.

128 МБ: **внешний EXT4 `/opt` + >=384 МБ внешнего storage-backed swap** (наш experimental floor); zRAM минимум не заменяет.
256 МБ: **zRAM ИЛИ внешний storage-backed swap**; отсутствие обоих — WARN. Если выбран внешний swap: <1× RAM → WARN, 1×..3× → INFO, предпочтительный target 3× RAM, максимум 2 ГиБ.
512 МБ-класс: **zRAM ИЛИ проверенный внешний storage-backed swap ОБЯЗАТЕЛЕН для новой установки**; отсутствие обоих — installer ERROR / Doctor FAIL. Исключения по модели или роли точки доступа нет: контракт смотрит на реальный MemTotal и активный backend. Выше 512 МБ-класса swap/zRAM опциональны.

### Основание memory-profile

Контракт `20260927_1` сохраняет прежнюю оценку размера внешнего swap, но повышает отсутствие backend на 512 МБ-классе до hard gate:

* [Виртуальный файл подкачки zRAM](https://support.netcraze.ru/giga/nc-1012/ru/21906-zram-virtual-swap-file-and-hwnat-traffic-accelerator.html): производитель отмечает, что на устройствах с большим объёмом RAM swap в некоторых сценариях может практически не требоваться; при наличии быстрого физического накопителя с классическим swap zRAM имеет смысл отключить. **Проект намеренно строже для своего 512 МБ supported profile**: Mihomo + MagiTrickle + системные сервисы создают иной memory-pressure сценарий, а hard gate нужен как OOM-headroom policy. Это project policy, а не vendor minimum.
* [Подготовка USB-накопителя и активация SWAP-раздела](https://support.netcraze.ru/hopper-4g-plus/nc-2312/ru/20978-preparing-a-usb-drive-as-storage-and-activating-a-swap-partition.html): zRAM и раздел/файл swap не рекомендуется использовать одновременно; при disk swap zRAM следует отключить. В примере около 500 МБ swap достаточно для большинства задач; производитель также пишет, что обычно нет необходимости делать SWAP больше чем примерно 3× RAM, а автоматически монтируемый SWAP-раздел не должен превышать 2 ГБ. Важно: это **не утверждение о минимуме 3× RAM**. Проект использует 1× RAM только как собственный warning floor, а 3× — как предпочтительный sizing target для 256/512 МБ-класса; оба значения не являются vendor minimum.

Полевой MCP-срез 2026-09-27 показал, почему роль устройства нельзя путать с memory-class. Два KN-1012 без swap, работавшие только точками доступа за основным роутером, были низконагруженными выбросами (около 41–49% non-cache RAM used). На основных 512 МБ gateway-роутерах KN-3811/NC-3812 наблюдалось примерно 63–76% non-cache RAM used; три доступных zRAM backend уже реально содержали данные (примерно 7–17 МБ), а другой основной KN-1012 с внешним swap имел около 68% non-cache RAM used и лишь ~26 МБ raw `memfree`. Это не доказывает неизбежный OOM на каждом устройстве, но показывает, что отсутствие memory-pressure backend на рабочем gateway оставляет слишком маленький запас для поддерживаемого профиля.

Проект сам никогда не создаёт, не включает и не меняет размер swap — только оценивает и сообщает. Для 128 МБ порог 384 МБ остаётся именно project-specific best-effort ограничением, а не цитатой из документации производителя.

## Почему именно такие размеры tmpfs

Значения ниже — профиль high (≥ 80 МБ свободной RAM); при меньшем объёме скрипт уменьшает размеры сам (см. выше).

| Директория   | Размер | Почему          |
| ------------ | ------ | --------------- |
| /opt/tmp     | 20M    | временные файлы |
| /opt/var/log | 10M    | логи            |
| /opt/var/run | 1M     | PID и сокеты    |

👉 это НОРМАЛЬНО

---

## Когда использовать disk режим

Если:

* мало RAM
* нужен persistent лог
* нестабильность системы

👉 отключить tmpfs

---

## Почему не весь /opt в RAM

Потому что:

* пакеты должны сохраняться
* конфиги должны сохраняться
* иначе после reboot всё исчезнет

---

## Почему именно init.d (S00)

* запускается раньше всех сервисов
* гарантирует, что:

  * cron
  * mihomo
  * watchdog

уже работают с tmpfs
