# Метрики роутера: read-only сбор состояния (кандидат для Web beta.4)

`kas-sys-metrics.sh` — необязательный одноразовый read-only сборщик штатных показателей ядра Linux/KeeneticOS (issue [#309](https://github.com/saymer-alt/keenetic-auto-setup/issues/309)): температура SoC/CPU из sysfs, load average, uptime, сводка памяти/swap из /proc и — начиная с collector 0.2.0 (issue [#476](https://github.com/saymer-alt/keenetic-auto-setup/issues/476), stage A, только backend) — файловая система накопителя Entware `/opt`. Решение владельца от 31.10.2026: **необязательная полезная функция на будущее** — сначала collector с честными UNKNOWN, затем простые карточки в KAS Web beta.4; это не мониторинг и не блокер beta.4.

## Что собирается

| Показатель | Источник | Правило |
| --- | --- | --- |
| Температура SoC/CPU | `/sys/class/thermal/thermal_zone*/{type,temp}`, затем `/sys/class/hwmon/hwmon*/{name,temp*_input}` | зона выбирается строго по `type`/`name`, содержащим cpu/soc (без учёта регистра); общий `*thermal*` не считается CPU-датчиком; пустое/не-число/отрицательное/вне диапазона −40…+150 °C → **UNKNOWN, без «подгонки»**; выбор и источник печатаются |
| Load average 1/5/15 | `/proc/loadavg` | это **load average, не процент CPU**; проценты не вычисляются |
| Uptime | `/proc/uptime` | время работы Linux с загрузкой; это не uptime WAN/ISP/Mihomo/watchdog |
| RAM / swap | `/proc/meminfo` (MemTotal, MemAvailable, SwapTotal, SwapFree) | сводка; полный анализ RAM/storage остаётся в основном Doctor — вердикты здесь не дублируются |
| Накопитель Entware /opt (0.2.0, #476 stage A) | `df -kP` (fallback `-k`) по `$KAS_OPT_ROOT` (по умолчанию `/opt`) + самая глубокая запись из `/proc/mounts` | классификация зеркалит Doctor: `ubifs`/`squashfs` или источник `ubi*`/`mtd*` → `internal`; `tmpfs`/`ramfs` → `ram` (RAM, не flash); известная ext-класс ФС на `/dev/sd*`/`/dev/nvme*`/`/tmp/mnt/*` → `external`; остальное → `unknown`. Свободно/всего — **килобайты уровня файловой системы df, а не сырой размер flash**; опрашивается только `/opt` — никогда `/tmp` tmpfs и swap/zRAM. Exit-код из-за storage не меняется. |

## Fail-closed правила для /opt (#476 stage A)

- Побеждает самая глубокая запись монтирования, покрывающая `/opt`; **конфликтующие** записи той же глубины — неоднозначность → класс `unknown` (валидные числа df остаются честным `PASS` с `source: df`).
- Нет записи `/opt` и нет каталога → `N/A` (наблюдать нечего); есть покрывающее монтирование, но df нечитаем/битый/вне диапазона → `UNKNOWN` (никогда нули, никогда вердикт).
- Значения df обязаны быть целыми числами с `0 < total <= 9999999999` кБ и `free <= total`; всё прочее (отрицательное, дробное, переполнение, нулевой total) → `UNKNOWN`, числа не отдаются.
- `PASS` всегда несёт `mount_class`, `fstype`, `mount_point`, `source` (`df+proc_mounts` / `df` / `proc_mounts` / `none`) и `observed_utc`; блок без `PASS` чисел не несёт и объясняет причину в `note`.
- Идентификатор устройства-источника (например `/dev/ubi0_0`) **намеренно не** отдаётся; kernel-экранированные точки монтирования декодируются для показа (`\040` → пробел).
- Веб-отрисовка этого блока — **Stage B, сознательно отложена** (последовательно с каноническим Web #491); этот PR не меняет Web UI.

## Чего сборщик не делает

- Ничего не меняет; один запуск = один проход; без демонов, cron, сети и пакетов (Fastfetch/flashfetch **не устанавливаются** и не требуются).
- **Порогов перегрева нет**: вендорские лимиты по моделям неизвестны, поэтому вердиктов «перегрев/OK» не существует — только наблюдение.
- **Вердиктов о здоровье накопителя нет**: заявлений «flash умирает/здорова» не существует; свободно/всего — наблюдения, `0 кБ свободно` — честное значение.
- Отсутствующий/неопределённый датчик → `UNKNOWN`/`N/A`, никогда не фиктивное значение и не FAIL.
- Секретов и серийников в выводе нет.

## Запуск

```sh
sh kas-sys-metrics.sh
sh kas-sys-metrics.sh --json /opt/tmp/metrics.json
```

Коды возврата: `0` — хотя бы одна метрика наблюдена; `1` — ничего не удалось наблюдать (всё UNKNOWN); `2` — ошибка использования. Exit-код отражает **только четыре основные метрики**; наблюдение `/opt` — аддитивное и его не меняет. Для тестов предусмотрены корни-инъекции `KAS_SYSFS_ROOT`/`KAS_PROC_ROOT`, а для storage — `KAS_OPT_ROOT`/`KAS_MOUNTS_SRC`/`KAS_DF_BIN` (в нормальной работе не задаются).

## JSON-контракт `router-metrics/v1`

`--json FILE` пишет версию схемы, имя/версию инструмента, UTC-время, exit-код и блоки `temperature` (статус, °C, зона, type, source, note «no thresholds asserted»), `load` (статус, 1/5/15 мин, note «load average, not CPU percentage»), `uptime` (статус, секунды, note), `memory`, `swap` и — с 0.2.0 — опциональный аддитивный блок `storage` (`status`, `path`, `mount_class`, `fstype`, `mount_point`, `free_kb`, `total_kb`, `source`, `observed_utc`, `note`). Все статусы — `PASS / UNKNOWN / N/A / INFO`; формат готов для будущих карточек Web beta.4.

**Совместимость версий (обоснованный versioned-contract выбор):** схема остаётся `router-metrics/v1`, потому что поле опционально и аддитивно — старые потребители игнорируют неизвестные ключи, старые сохранённые ответы v1 остаются валидными. `tool_version` движется `0.1.0` → `0.2.0`: Go-адаптер принимает обе версии, отвергает ответ `0.1.0` с блоком storage (такой collector его не выпускал) и строго валидирует блок при наличии (словарь статусов, наборы class/source, числовые границы, `free <= total`, отсутствие чисел при не-PASS, отсутствие control-байтов). Collector и валидатор всегда поставляются вместе внутри одного Web-бинарника, поэтому производственного рассогласования не бывает; JSON `0.2.0`, скормленный старой сборке beta.8, отвергается её version pin — это fail-closed по дизайну.

## Тестирование и границы

- `tests/sys-metrics-regression.py` — офлайн-регрессия на fixture-деревьях sysfs/procfs (корни-инъекции): нормальная зона `soc_thermal`, вариант только через hwmon, несколько зон (первая CPU-зона выбирается, все печатаются), завышенное значение → UNKNOWN без «подгонки», отрицательное и текстовое значение → UNKNOWN, нечитаемый файл → UNKNOWN, отсутствие датчиков при рабочих /proc → 3 из 4, полное отсутствие всего → exit 1 «всё UNKNOWN», битый loadavg/uptime, отсутствие swap → N/A, валидность JSON и отсутствие «FAIL/WARN»-вердиктов в отчёте.
- `tests/sys-metrics-storage-regression.py` (#476 stage A) — офлайн-регрессия storage на инъекциях `/opt` + таблицы монтирований + df: внутренняя UBIFS через корневое монтирование (полевой профиль KN-3811), внешняя EXT4 с bind-стилем `/opt` и экранированной родительской точкой, `/opt` на tmpfs → `ram`, отсутствие `/opt` → N/A, каталог без покрывающего монтирования, битый/нечисловой/вне-диапазона df, ноль свободно → честный PASS, завышенный total, отсутствие бинарника df, fallback `-kP` → `-k`, неоднозначность → класс unknown, нечитаемые mounts при рабочем/битом df, декодирование `\040`, различение /opt и /tmp tmpfs, неизменность exit-кода.
- Go-контракт: `web/control-center/router_metrics_test.go` — таблица версионированных ответов (старый v1, новый v1 с/без валидного и битого storage) и end-to-end прогоны collector'а через встроенный скрипт (`KAS_OPT_ROOT`/`KAS_MOUNTS_SRC`/`KAS_DF_BIN` — только тестовые инъекции; в проде не передаются).
- Прогон выполнен на host sh и BusyBox ash 1.37: **MOCK PASS на обоих диалектах** для обоих regression-наборов.
- **QEMU (отдельный read-only прогон): PASS для запуска сборщика** в disposable KeeneticOS Ported 5.1.8 / Entware (DRIVER_OK, 254 с): `kas-sys-metrics.sh` завершился с exit 0, JSON `router-metrics/v1` валиден; прочитаны гостевые `/proc/loadavg`, `/proc/uptime`, `/proc/meminfo`. Этот QEMU-прогон **предшествует** блоку storage 0.2.0; у самой storage-секции **нет QEMU- и физических доказательств**. Fixture-проверки — отдельный **MOCK PASS**, а CI `native-kas / ported-lab` — отдельная проверка общего жизненного цикла KAS. **PHYSICAL: NOT TESTED** — KN-3811/KN-1010/KN-1012/NC-1812 и другие физические роутеры требуют отдельного GO; полевой пробел KN-3811 остаётся открытым до тех пор.
