# KeeneticOS: `ip global` — приоритет интерфейса, а не идентификатор

> Правило для KAS, разработчиков и AI-агентов: не объявлять `ip global 350`, `700`, `32767` или любое другое число неизменной константой, признаком владения KAS или обязательным значением для конкретной модели.

## Что означает параметр

По официальному справочнику CLI Keenetic, свойство `ip global` помечает IP-интерфейс как ведущий к глобальной сети. Оно участвует в выборе маршрута по умолчанию, работе NAT/DynDNS и приоритетах резервирования интернет-подключений. **Чем больше числовой приоритет, тем предпочтительнее интерфейс для установки default route** среди применимых подключений. Это не уникальный ID интерфейса, не показатель его скорости и не стандартная Linux `ip route` metric.

Синтаксис CLI:

```text
(config-if)> ip global <priority>
(config-if)> ip global order <order>
(config-if)> ip global auto
(config-if)> no ip global
```

- `priority` — целое число **1…65534**; значение имеет смысл как приоритет в соответствующей конфигурации подключений/политике.
- `order` — способ задать относительное положение интерфейса.
- `auto` — **автоматический расчёт** приоритета KeeneticOS. Установщик KAS создаёт ProxyN через `ip global auto`; `show running-config` может позже вывести вычисленное числовое значение.
- В режиме балансировки (`multipath`) значения `ip global` могут дополнительно влиять на **соотношение нагрузки**; это отдельный специальный случай, не повод считать числа универсальными весами всех маршрутов.

## Примеры и границы интерпретации

На проверяемом KN-1010 (KeeneticOS 5.1.8) наблюдались `ip global 700` в одном блоке конфигурации и `ip global 350` внутри `interface Proxy0`. В Ported/QEMU встречался `ip global 32767`. **Все три значения могут быть нормальными в своём контексте**. Отдельное `700` не конфликтует с `350` в Proxy0; простое обнаружение иного числа вне собственного блока не является ошибкой KAS.

Сравнение `700 > 350` указывает на больший глобальный приоритет, **но само по себе не доказывает фактически выбранный маршрут для конкретного клиента**: важны доступность интерфейсов, действующая политика и её привязки. Не изменять эти приоритеты автоматически в ходе установки, диагностики или удаления KAS.

## Обязательные правила для KAS и тестов

1. **Разбирать `show running-config` по блокам интерфейсов**, а не делать общий `grep 'ip global'` по всему конфигу и не связывать чужой WAN с ProxyN.
2. Для принадлежащего KAS ProxyN проверять корректный синтаксис и одну допустимую числовую директиву `ip global N` (или документированное представление `auto` на соответствующем этапе), **но не фиксированное значение N**.
3. **Не выводить принадлежность из N.** Владение подтверждают ownership ledger, канонические параметры именно этого ProxyN, проверка чужих потребителей и сравнение с проверенным snapshot.
4. **Не нормализовать и не переписывать N**, чтобы «подогнать» стенд под `350`. Если число поменялось после snapshot, применять обычную защиту от drift и пересоздать snapshot по безопасной процедуре; не игнорировать изменение только потому, что N динамический.
5. В регрессионных тестах принимать корректные разные числа (в частности, `350` и `32767`), проверять отсутствие/дублирование/некорректный формат, и отдельно проверять посторонний интерфейс с `ip global 700`. Эти тесты не должны ослаблять проверки чужих ProxyN или policy.
6. **Не путать приоритет интерфейса `ip global` с метрикой отдельного статического маршрута или идентификатором policy.** Любые выводы о фактической маршрутизации требуют контекста политики/маршрутной таблицы.

В KAS #215/#227 gate уже не привязан к `350`: проверяется единственное положительное целое внутри собственного ProxyN при сохранении остальных ownership/snapshot-контрактов. Эта заметка закрепляет обоснование, **не изменяет runtime** и не означает аппаратный PASS для uninstall.
