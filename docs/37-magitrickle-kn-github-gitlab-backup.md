# MagiTrickle резерв GitHub/GitLab для Keenetic — только `_kn`

**Статус:** кандидат Draft PR / не развёрнут на роутерах. В этой работе нет изменения `stable`, обновления OPKG, переключения feeds и публикации KAS Core. Ветка исправления fresh-Entware архитектуры: `agent2/mt-kn-fresh-fix` (от `4c5ad19`, локальная, без push).

## Проверенный upstream (12.11.2026, Agent D)

- Официальный GitLab [`0.8.2`](https://gitlab.com/magitrickle/magitrickle/-/releases/0.8.2) и [Package Registry](https://gitlab.com/magitrickle/magitrickle/-/packages/64455047): именно пакетные файлы `0.8.2-1` с `_kn.ipk`. **12.11.2026 все 3 IPK скачаны и верифицированы независимо.** Версии `-1` и `-2` не побайтно идентичны: отличается `Version` и payload `opt/bin/magitrickled` (per-ABI SHA); control (`Depends: libc, iptables, socat`), `postinst`, `conffiles` и состав data — идентичны.
- **12.11.2026 подтверждено:** официальный feed `bin.magitrickle.dev/packages/entware/<arch>/` отдаёт `0.8.2-1`, и его байты **побайтово идентичны** GitLab `0.8.2-1` для всех трёх `_kn` ABI (см. mirrors/magitrickle и docs/36). Это снимает вопрос «fallback GitLab ставит чужой пакет»: GitLab-кандидат — ровно тот же пакет, что поставил бы официальный feed.
- Разработчик сообщил 02.08.2026, что ревизия `-2` исправляла права APK для OpenWrt, а не Entware. Это не повод приравнивать хеши двух IPK и не делает `0.8.2-1` более новой. Порядок fallback (GitHub `0.8.2-2` → GitLab `0.8.2-1`) — от более новой официальной ревизии к feed-идентичной; ни один шаг не понижает уже установленный пакет.
- Поддерживаемые резервные Keenetic ABI: `aarch64-3.10_kn`, `mips-3.4_kn`, `mipsel-3.4_kn`. Обычные `aarch64-3.10`, `mips-3.4`, `mipsel-3.4` и `armv7-3.2` **не допускаются** в резервной ветке: для armv7 upstream не публикует `_kn` IPK.
- Официальный helper KAS по-прежнему получает с `bin.magitrickle.dev` и выполняет только после `sh -n`. Сам официальный helper читает `opkg print-architecture`.

## Что делает кандидат `install.sh`

1. **KN ARCH PREP v1 (исправление fresh Entware, follow-up #505).** `mt_prepare_kn_arch` классифицирует устройство **до** всей MT-секции и никогда не прерывает весь установщик:
   - Уже установлен с `_kn` ABI (`opkg status`) → обычный verify-never-touch, регистрация не требуется.
   - Уже установлен с **generic**/чужой архитектурой (`mipsel-3.4`, `armv7-3.2`, …) → `warn` + **пропуск всей MT-секции**: KAS не заменяет работающую установку и не мигрирует generic-сборки автоматически. Остальной установщик (mihomo и далее) продолжается.
   - Не установлен, `_kn` уже зарегистрирован (`mt_select_kn_arch` успешен) → продолжение без регистраций.
   - Не установлен, fresh Entware (только plain-архитектуры): `_kn` **выводится** из единственной зарегистрированной whitelisted plain-архитектуры (`mipsel-3.4`/`mips-3.4`/`aarch64-3.10` → парный `*_kn`) и регистрируется. Никаких uname/модель-угадываний и никаких «слепых» регистраций: plain-архитектура — платформенная правда самого Entware, имя `_kn` — опубликованный upstream-вариант ровно этого имени, байты пакета всё равно проходят pinned SHA256/size-гейт и post-install re-check.
   - Не установлен и вывести нельзя (armv7-3.2, неизвестная платформа, неоднозначный plain) → `warn` + пропуск MT-секции (upstream не публикует `_kn` для этой платформы; generic запрещён); установка KAS продолжается, пользователь может поставить MagiTrickle вручную по upstream README.
2. Регистрация пишется в **KAS-owned fragment** `/opt/etc/opkg/kas-mt-arch.conf` строкой вида `arch mipsel-3.4_kn 251` (приоритет = plain+1, чтобы `_kn` выигрывал равные версии при последующих ручных `opkg update`; без печатного приоритета — 500). Официальный opkg читает этот файл через свой glob `/opt/etc/opkg/*.conf` в default-режиме — ровно как install.sh вызывает opkg на устройстве (проверено на официальном Entware opkg-бинарнике; нюанс: `--offline-root` glob отключает — это особенность только лабораторных rig). `opkg.conf` Entware и `magitrickle.conf` helper **не изменяются**. Запись идемпотентна (строка не дублируется) и журналируется в ownership ledger (`owned repository kas-mt-arch.conf`, отказ журналирования = `err` по конвенции magitrickle.conf).
3. Уже установленный MagiTrickle не заменяет. Проверяет, что его `opkg status` указывает на тот же `_kn` ABI. Нет скрытого downgrade, принудительной установки или перехода на MT-C.
4. При наличии официального helper и успешного обновления метаданных проверяет `opkg info magitrickle`: только однозначный `_kn` кандидат допускается к установке по имени. При неверной/неоднозначной архитектуре — переход к резерву **до установки пакета**.
5. Если официальный helper недоступен/не прошёл проверку или OPKG не может подтвердить единственный `_kn` кандидат, использует **официальный GitHub Release** (точно pinned `0.8.2-2` IPK); при ошибке загрузки или SHA/size переходит на **официальный GitLab Package Registry** (точно pinned `0.8.2-1` IPK). Пользователь видит источник/ревизию/архитектуру и результат.
6. Для каждого байтового кандидата проверяет заданные SHA256 и size перед `opkg install FILE`; пакет проходит штатную проверку зависимостей OPKG. При сбое **после начала OPKG install** не начинает вторую установку другой ревизии. Контроль init-script/процесса/DNS остаётся за каноническим installer и Doctor.
7. Резерв работает только для **чистой установки компонента**. На существующие конфиги/подписки установка с зеркала не должна выполнять прямых изменений KAS; side effects package postinst остаются частью OPKG и требуют отдельной лабораторной проверки.

## Порядок uninstall (инвариант для uninstall-сервиса)

`opkg remove magitrickle` требует, чтобы зарегистрированная архитектура ещё существовала: после удаления `kas-mt-arch.conf` opkg отвечает «has no valid architecture, ignoring» и **оставляет файлы пакета**. Uninstall должен удалять пакет **до** каскадного удаления journal-файла `kas-mt-arch.conf`.

Реализация (интеграция `agent2/mt-kn-fresh-fix` в Core 1.8.10): `uninstall-packages.sh --cleanup` обрабатывает `kas-mt-arch.conf` только после цикла `opkg remove` и лишь если ни одно удаление пакета не провалилось; запись владения (`owned|repository|kas-mt-arch.conf`) обязательна, symlink сохраняется с предупреждением. `uninstall.sh` валидирует новую запись как легитимную (whitelist леджера) и в `--plan` помечает фрагмент как `REVIEW` с этим инвариантом. Регрессии: `tests/uninstall-packages-regression.py` (cleanup-сценарии) и `tests/uninstall-audit-regression.py` (валидный журнал с записью MT).

## Границы и регрессии

- **Глобальный `opkg update` (исправлено в этом PR):** если глобальный `opkg update` падает, а сконфигурированный MT-фид недоступен целиком (каждый его URL проверен bounded-пробой `Packages.gz`/`Packages`) и MagiTrickle ещё не установлен, установщик продолжает работу с явным предупреждением — MT-секция использует резерв. Любая другая причина сбоя (Entware-фиды, MT установлен) остаётся строгим `err`. Реальный отказ Entware по-прежнему всплывает на строгой установке базовых пакетов сразу после этого шага.
- **Fresh-Entware политика (исправление этого follow-up):** свежее Entware регистрирует только plain-архитектуру, а официальный `add_repo.sh` ничего не регистрирует — прежний безусловный `mt_select_kn_arch || err` прерывал весь установщик на каждом fresh-устройстве. Теперь fresh-устройство с whitelisted plain-архитектурой получает выведенную `_kn` регистрацию; armv7/неизвестные/неоднозначные — чистый skip с предупреждением. Generic-установленный MagiTrickle остаётся как есть (никакой миграции), MT-секция пропускается.
- **De-facto путь первой установки остаётся pinned GitHub `0.8.2-2`:** после регистрации helper пишет обе feed-строки (plain + `_kn`), `opkg info magitrickle` показывает двух кандидатов с равной версией → single-candidate проверка уходит в резерв. Это подтверждено на реальном opkg: `opkg info` ровно 2 станзы (`mipsel-3.4`, `mipsel-3.4_kn`).
- `opkg install` с официального источника может дать частично применённую транзакцию. Кандидат **не** переходит на другую ревизию после этого; нужна диагностика. `postinst` может молча закончиться успешным кодом: см. [#493](https://github.com/saymer-alt/keenetic-auto-setup/issues/493). Идеальный E2E ещё не пройден.
- Хардкодированные digests намеренно **immutable**: новые upstream release версии потребуют отдельного обновления manifest/review, а не слепого `latest`. Не скачивать `_kn` из непроверенного feed без SHA.
- Сюда не входит вариант `KAS-owned mirror` из [Draft PR #507](https://github.com/saymer-alt/keenetic-auto-setup/pull/507): там отдельная публикация тех же официальных GitHub байтов. Установка из GitLab в этом PR возможна напрямую по официальному Package Registry.
- Никаких `--force-architecture`, `--force-downgrade`, `-k`/TLS bypass или автоматических изменений OPKG sources. Регистрация архитектуры — отдельная KAS-owned строка в собственном файле, не правка `opkg.conf`.
