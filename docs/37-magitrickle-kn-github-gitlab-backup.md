# MagiTrickle резерв GitHub/GitLab для Keenetic — только `_kn`

**Статус:** кандидат Draft PR / не развёрнут на роутерах. В этой работе нет изменения `stable`, обновления OPKG, переключения feeds и публикации KAS Core.

## Проверенный upstream (10.11.2026)

- Официальный GitHub [`0.8.2-rev2`](https://github.com/MagiTrickle/MagiTrickle/releases/tag/0.8.2-rev2): именно пакетные файлы `0.8.2-2` с `_kn.ipk`. SHA256 + размер в GitHub Release API.
- Официальный GitLab [`0.8.2`](https://gitlab.com/magitrickle/magitrickle/-/releases/0.8.2) и [Package Registry](https://gitlab.com/magitrickle/magitrickle/-/packages/64455047): именно пакетные файлы `0.8.2-1` с `_kn.ipk`. SHA256 + размер из GitLab Package Files API. Версии `-1` и `-2` не побайтно идентичны, хотя основная версия исходников одинакова.
- Разработчик сообщил 02.08.2026, что ревизия `-2` исправляла права APK для OpenWrt, а не Entware. Это не повод приравнивать хеши двух IPK и не делает `0.8.2-1` более новой.
- Поддерживаемые резервные Keenetic ABI: `aarch64-3.10_kn`, `mips-3.4_kn`, `mipsel-3.4_kn`. Обычные `aarch64-3.10`, `mips-3.4`, `mipsel-3.4` и `armv7-3.2` **не допускаются** в резервной ветке: для armv7 upstream не публикует `_kn` IPK.
- Официальный helper KAS по-прежнему получает с `bin.magitrickle.dev` и выполняет только после `sh -n`. Сам официальный helper читает `opkg print-architecture`.

## Что делает кандидат `install.sh`

1. Считывает `opkg print-architecture`; выбирает единственное присутствующее разрешённое значение `*_kn`, иначе **ERROR**. Не определяет CPU по uname и не угадывает архитектуру по модели.
2. Уже установленный MagiTrickle не заменяет. Проверяет, что его `opkg status` указывает на тот же `_kn` ABI. Нет скрытого downgrade, принудительной установки или перехода на MT-C.
3. При наличии официального helper и успешного обновления метаданных проверяет `opkg info magitrickle`: только однозначный `_kn` кандидат допускается к установке по имени. При неверной/неоднозначной архитектуре — переход к резерву **до установки пакета**.
4. Если официальный helper недоступен/не прошёл проверку или OPKG не может подтвердить единственный `_kn` кандидат, использует **официальный GitHub Release** (точно pinned `0.8.2-2` IPK); при ошибке загрузки или SHA/size переходит на **официальный GitLab Package Registry** (точно pinned `0.8.2-1` IPK). Пользователь видит источник/ревизию/архитектуру и результат.
5. Для каждого байтового кандидата проверяет заданные SHA256 и size перед `opkg install FILE`; пакет проходит штатную проверку зависимостей OPKG. При сбое **после начала OPKG install** не начинает вторую установку другой ревизии. Контроль init-script/процесса/DNS остаётся за каноническим installer и Doctor.
6. Резерв работает только для **чистой установки компонента**. На существующие конфиги/подписки установка с зеркала не должна выполнять прямых изменений KAS; side effects package postinst остаются частью OPKG и требуют отдельной лабораторной проверки.

## Границы и регрессии

- Глобальный первоначальный `opkg update` KAS до базовых пакетов остаётся строгим. Если уже подключённый чужой/официальный MT feed ломает **глобальный** OPKG update, установщик может остановиться ещё до этого fallback. Это отдельный сценарий для последующего узкого PR; не отключать глобальную проверку пакетов неразборчиво.
- `opkg install` с официального источника может дать частично применённую транзакцию. Кандидат **не** переходит на другую ревизию после этого; нужна диагностика. `postinst` может молча закончиться успешным кодом: см. [#493](https://github.com/saymer-alt/keenetic-auto-setup/issues/493). Идеальный E2E ещё не пройден.
- Хардкодированные digests намеренно **immutable**: новые upstream release версии потребуют отдельного обновления manifest/review, а не слепого `latest`. Не скачивать `_kn` из непроверенного feed без SHA.
- Сюда не входит вариант `KAS-owned mirror` из [Draft PR #507](https://github.com/saymer-alt/keenetic-auto-setup/pull/507): там отдельная публикация тех же официальных GitHub байтов. Установка из GitLab в этом PR возможна напрямую по официальному Package Registry.
- Никаких `--force-architecture`, `--force-downgrade`, `-k`/TLS bypass или автоматических изменений OPKG sources.
