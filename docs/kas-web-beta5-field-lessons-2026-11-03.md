# KAS WEB beta.5 — полевые испытания 03.11.2026, ошибки и уроки для beta.6

> **Тип:** протокол фактов и инженерных выводов («как надо / как не надо»). 
> **Статус:** beta.5 уже опубликована; документация не означает исправления кода, нового IPK или продвижения `stable`.

## 2. Рабочий KN-1012 SE — проверенное по реальному SSH

Окружение: KeeneticOS `5.1.8`, Entware `aarch64-3.10`, доступ SSH к `10.0.6.78`; домашний мост роутера — `br0=192.168.88.1/24`. Не путать `10.0.6.78` (реальный интерфейс WAN/рабочей сети) и `198.51.100.11` (встроенный служебный адрес `ezcfg`).

1. Скачан IPK beta.5, проверка SHA256 через `sha256sum -c` — **OK**. `opkg install` обновил `kas-control-center` с `0.1.0~beta.4-1` до `0.1.0.beta.5-1` — **PASS**; сервис требует отдельного старта.
2. `sh /opt/etc/init.d/S98kas-control-center start` → `PORT_BIND_FAILED`; `status` → `NOT_RUNNING`. Файл `/opt/etc/kas-control-center.settings.json` **отсутствовал**, значит для beta.5 подразумевался порт `8081`.
3. `netstat -tlnp`: `198.51.100.11:8081` и `2001:2::c633:640b:8081` заняты `nginx` KeeneticOS (первоначально PID 779, после reboot/перезапуска другой PID). `/proc/779/cmdline` → `nginx: master process /usr/sbin/nginx -e /dev/null`, `/proc/779/exe` → `/usr/sbin/nginx`. **Это не зависшая старая beta.4**.
4. Ошибочное действие в процессе диагностики: был подан `kill -TERM 779`, не зная назначения процесса. Системный nginx автоматически восстановился, продолжил слушать `:8081`, а beta.5 не запустилась. **Не повторять этот шаг**: можно нарушить работу веб-интерфейса и reverse proxy, а первопричину он не устраняет.
5. После перезагрузки конфликт остался: это не временная утечка старого процесса панели. MCP подтвердил, что интерфейс `GigabitEthernet1` имеет `10.0.6.78`, KeenDNS работает в облачном режиме, HTTP reverse proxy `mt` идёт на `127.0.0.1:8080`, `mh` — на `127.0.0.1:9090`. Ни один из этих proxy upstream **не настроен на 8081**.
6. Для обхода был выбран **свободный 18082**, без изменений в системном nginx/KeenDNS. С `umask 077` создан отсутствовавший файл `/opt/etc/kas-control-center.settings.json` c `{"version":1,"port":18082,"auth_mode":"none"}`. Старт службы → `RUNNING`, `PANEL_ADDRESS: 192.168.88.1:18082`, `netstat` → `:::18082 LISTEN kas-control-center`, `curl http://127.0.0.1:18082/` → **HTTP 200**. Пользователь подтвердил открытие UI с ПК по `http://10.0.6.78:18082/` — **LAN/routed browser PASS**.
7. UI подтверждает `KAS Web v0.1.0.beta.5`, установлено/запущено/доступно `v0.1.0.beta.5`; beta-канал обновлений работает, новой версии нет. Раздел состояния видит работающие Mihomo и MagiTrickle; `kas-core` отсутствует, watchdog обнаружен. Это не является E2E-проверкой импорта YAML, загрузки конфигурации, обновления пакетов или автозапуска после reboot.
8. **8082 на рабочем роутере не был подтверждён пользователем как запущенный.** Проверен и работал именно **18082**. Не повышать статус `8082` до PASS, пока не будет испытания.

## 3. Домашний NC-4210 и ранние испытания 8081 — границы доказательств

- На домашнем Netcraze Titan SE **раньше** KAS WEB beta.4 работала на `8081`. По сообщению владельца от 03.11.2026, **на beta.5 дома также воспроизвёлся конфликт занятого 8081**. Конкретные текущие `netstat`, PID, ошибки запуска, параметры settings и наличие нового рабочего порта **не приложены**; нельзя автоматически приписывать дому ту же привязку nginx, что на рабочем роутере, без отдельного read-only снимка.
- В ходе прежних испытаний порт `8081` работал на тестовом KN-1010 и ещё на двух устройствах пользователей. Условия, версии и активный режим bind в этих тестах не сверены с beta.5, поэтому **не считать их четырьмя успешными независимыми тестами beta.5**.
- Общая проблема перехода beta.4 → beta.5 подтверждена **двумя владельческими сообщениями**, но полная причинная диагностика на уровне Linux выполнена **пока только на рабочем KN-1012 SE**.
- Объяснение, почему beta.4 работала: она привязывалась к конкретному IPv4 `br0:8081`, а beta.5 по умолчанию привязывается к **`0.0.0.0:8081`**. IPv4 wildcard пересекается с сокетом nginx на `198.51.100.11:8081`, даже если `br0:8081` свободен.
- Адреса `198.51.100.11` и `2001:2::c633:640b` описаны на форуме Keenetic как служебные адреса `ezcfg`, используемые встроенной веб-инфраструктурой: [обсуждение на форуме](https://forum.keenetic.ru/topic/29429-52-a1-%D0%B0%D0%B4%D1%80%D0%B5%D1%81a-ezcfg/). Конкретное *назначение именно порта 8081* через доступные RCI/документацию не доказано; его **фактический владелец — nginx**. Не называть его «посторонний вирус/Entware-сервис/старый процесс beta.4».

## 4. Второй реальный дефект — версия Mihomo показывается «?»

На рабочем KN-1012 SE UI KAS WEB beta.5:
- «Процесс Mihomo запущен», но «Версия запущенного Mihomo: ?»; `opkg` версия пакета `1.19.28-1`, в entware-go доступен `1.19.33-2`.
- Фактический read-only запрос `curl -sS -i --max-time 3 --noproxy '*' http://127.0.0.1:9090/version` → **HTTP 200**, `{"meta":true,"version":"v1.19.33"}`.
- Исходники `web/control-center/runtime.go` (`readMihomoVersion`) отвергают ответ, если `!componentVersionPattern.MatchString(body.Version)`; паттерн в `components.go`: `^[0-9][A-Za-z0-9.+~-]{0,63}$`. Он исключает **ведущую `v`**, хотя JSON валиден и API доступен. Версия процесса **установлена: `v1.19.33`**; «?» — дефект отображения/парсинга KAS WEB, не неисправность Mihomo.
- Команда `/opt/bin/mihomo -v` на этом роутере дала `not found`. Это **не доказательство отсутствия работающего бинарника**. Проверять фактический путь `/proc/<pid>/exe` или `/opt/sbin/mihomo`: KAS допускает обе позиции. Не чинить «отсутствие Mihomo» установкой/перезаписью наугад.
- Корректная версия процесса, версия opkg-пакета и версия available из GitHub — **три разные сущности**. Не делать `opkg upgrade` всего дерева ради устранения вопросительного знака; возможен откат runtime.
- Минимальный патч beta.6: строго принимать и нормализовать **один опциональный `v`** перед проверкой семантической версии из `/version`; отрицательные тесты на мусорный формат, `meta=false`, 401/404, таймаут, невалидный JSON. Не ослаблять глобальный паттерн компонентов и не выводить секреты Controller.

## 5. Как надо делать / как не надо делать (обязательно для агентов)

| Делать | Не делать |
| --- | --- |
| Перед обновлением/сменой listener проверить `netstat`, `/proc/<pid>/cmdline`, `/proc/<pid>/exe`, фактический `br0` и private settings; отличать `198.51.100.11` ezcfg от WAN. | Не считать любой PID на `:8081` старой KAS WEB и не отправлять `kill` системному nginx. |
| При bind-конфликте оставить чужой сервис нетронутым; в лаборатории или штатной панели выбрать безопасный свободный порт и сохранить его. | Не пробовать `0.0.0.0:8081` вслепую после успешного `opkg install`, не объявлять успех без `RUNNING` и HTTP 200. |
| Доказывать отдельными проверками: IPK installed, daemon running, local HTTP, браузер с нужной сети, KeenDNS, reboot, UI операции. | Не приравнивать CI, пакет, порт LISTEN или один localhost curl к полному аппаратному E2E. |
| Для auto-port fallback проверять **результат реального bind** и только ошибку `EADDRINUSE`; выводить выбранный порт. | Не выбирать порт по предварительному `netstat` без фактического bind и не считать все ошибки старта «порт занят». |
| Сохранять частные настройки и установленный пользователем порт; при auto-fallback устойчиво записывать фактически выбранное значение. | Не менять явно выбранный порт молча и не перезаписывать существующие настройки `auth_mode`/пароль или KeenDNS upstream. |
| Учитывать `auth_mode=none`, wildcard bind и маршруты/ACL/firewall; обращаться через доверенную LAN/VPN. | Не открывать неизвестный новый порт наружу и не утверждать, что `Home-only=false` автоматически безопасно. |
| Для версии Mihomo использовать ответ реально работающего Controller, с поддержкой `v1.19.33` и строго валидируемым JSON. | Не трактовать `?` как упавший Mihomo и не заменять runtime версию данными opkg. |
| Формулировать статус домашнего NC-4210 как «владелец сообщил конфликт», пока нет сырого вывода. | Не переносить `nginx/ezcfg`-диагноз одного устройства на всё семейство без проверки. |

## 6. Требования к beta.6 (готовая постановка для нового чата)

**P1 — Startup/listener:**
1. Сохранить **8081 по умолчанию** (не переучивать все уже работающие установки). Если сохранённого пользовательского порта нет и bind на `0.0.0.0:8081` падает именно с `EADDRINUSE`, последовательно пробовать `8082,8083,…` до разумного фиксированного предела (предложено `8090`).
2. Не делать «silent port hopping» при ошибках других типов (`EACCES`, неправильная конфигурация, повреждённый settings), при явно заданном порте, либо после фактического запуска процесса. Учитывать сложный upgrade-case: если beta.4 сохранила `8081` как auto-default, отличать его от явного пользовательского выбора; без такой информации не переопределять settings.
3. Выполнять резервирование реальным `net.Listen` без TOCTOU, безопасно сохранять новый порт при первом auto-selection (файл 0600, атомарность/ownership/no symlinks), обеспечивать постоянство после reboot, корректную обработку невозможности persist, понятный init/status и фактический URL.
4. Не трогать nginx, системный `ezcfg`, firewall или KeenDNS; явно указать, что для KeenDNS upstream может потребоваться обновление конфигурации **оператором**. Сохранить existing auth/Home-only настройки без деградации безопасности.
5. Негативные тесты: свободный `8081`; чужой listener на отдельном IP `:8081` (точная ошибка wildcard); занят `8082`; сохранённый custom порт; bad settings; другой errno; restart и reboot; два одновременных запуска; внешняя недоступность при закрытом firewall. Включить native emulator + реальные KN-1012 SE/NC-4210 по явному owner GO.

**P1 — runtime version Mihomo:** поддержать формат `v1.19.33` (и `1.19.33`), регрессионные тесты API в том числе с `meta=true`, без ослабления остальных паттернов.

**Важные границы:** разработка через отдельный PR, не трогать опубликованный beta.5 IPK/Pages, не двигать `stable`, не смешивать исправления с installer/watchdog/Core/MT; никакого merge/release без owner GO. До начала работ перечитать `AGENTS.md`, `docs/CONSTITUTION.md`, `docs/AGENT-TASK-CONTRACT.md`, `web/control-center/LAN.md`, `web/control-center/PANEL_SETTINGS.md`, `web/control-center/packaging/S98kas-control-center`, `main.go`, `runtime.go`, `components.go`, и связанные issues #344/#349/#357.

## 7. Результат и что ещё не доказано

**PASS (работа):** IPK SHA verified, opkg install beta.5, init-service на специально выбранном 18082 RUNNING, `localhost:18082/` HTTP 200, открытие UI с рабочего ПК `10.0.6.78:18082`, self-reported panel version beta.5, Mihomo API HTTP 200 с runtime `v1.19.33`, идентификация nginx/ezcfg bind conflict.

**FAIL (производственное ожидание):** beta.5 **не запускается на default 8081** на рабочем KN-1012 SE; владелец сообщил аналогичный конфликт дома NC-4210. Версия Mihomo в UI `?` при рабочем API.

**NOT VERIFIED:** 8082 на рабочем роутере, весь набор функций UI, домашний полный SSH/netstat сценарий, домашняя версия/состояние beta.5 после любых ручных правок, автозапуск и сохранение после перезагрузки на fallback порту, KeenDNS для KAS WEB, безопасность WAN-экспозиции, исправление в коде и CI beta.6.

Это **полевой отчёт**, а не разрешение выпускать beta.6 без повторной приёмки.
