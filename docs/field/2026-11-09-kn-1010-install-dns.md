# FIELD 2026-11-09 — KN-1010: нестабильный DNS при установке Core + Web

**Состояние:** FIELD install/retry PASS на одном физическом KN-1010; первопричина интермиттирующего DNS **НЕ ДОКАЗАНА**; CI по PR #482 не PASS; reboot/маршрутизация/другие архитектуры НЕ ПРОВЕРЕНЫ.

**Область:** исследование/план, без изменений маршрутов, DNS, Entware feeds, конфигов и выполняемых скриптов. Источник фактов — SSH-журналы владельца от 09.11.2026. Внешние подписки, токены, YAML, частные IP, HWID и ключи в отчёте не приводятся.

**GitHub:** [universal install #480](https://github.com/saymer-alt/keenetic-auto-setup/issues/480), [PR #482](https://github.com/saymer-alt/keenetic-auto-setup/pull/482), [MagiTrickle incident #483](https://github.com/saymer-alt/keenetic-auto-setup/issues/483); существующие треки [#169](https://github.com/saymer-alt/keenetic-auto-setup/issues/169) (bounded wget/curl) и [#167](https://github.com/saymer-alt/keenetic-auto-setup/issues/167) (лишние opkg update + слабые устройства). Основные troubleshooting-источники: [22-entware-feed-fallback.md](../22-entware-feed-fallback.md), [27-download-check.md](../27-download-check.md), [29-network-doctor.md](../29-network-doctor.md), [18-output-colors.md](../18-output-colors.md).

## 1. Проверенная конфигурация и исходный код

- Keenetic Giga KN-1010, Entware `mipsel-3.4` + `mipsel-3.4_kn`, BusyBox ash v1.38.0.
- Внешний `/opt` на EXT4, свободно ~13.8 GiB; RAM 248 MiB (показание installer), storage-backed SWAP 468 MiB; zRAM выключен. Предпочтительная цель SWAP ~745 MiB, но минимум профиля выполнен, **эта рекомендация не является причиной текущего отказа**.
- KAS Core строго по опубликованному тегу `v1.8.8`, Web строго `v0.1.0-beta.8`, experiment `kas-universal-install.sh` из ветки PR #482; `main` при постановке отчёта `b41ff34d835c82a5136e06bf10c235d9edac4032`. Это не production-ветка `stable`.
- `/etc/resolv.conf` в момент сбоя содержал `nameserver 127.0.0.1` и `options timeout:1 attempts:1 rotate`; `/opt/etc/resolv.conf` отсутствовал. Запросы поступали в локальный resolver; сама по себе эта запись **не доказывает** его неисправность, работу/неработу DNS-перехвата или причину ошибки curl.

## 2. Хронология наблюдений — подтверждённые факты

1. Первая команда `opkg update && opkg install curl && …` завершилась ещё до запуска KAS: два `Packages.gz` на `bin.entware.net` — `wget: bad address`. При повторной попытке оба feed загрузились, установлены `curl` и зависимости.
2. Системное `ping -c 2 1.1.1.1` — 2/2 успешных ответа (~26 ms). `nslookup bin.entware.net` через `127.0.0.1` в отдельной пробе разрешил имя. `nslookup bin.entware.net 1.1.1.1` завершился `Temporary failure in name resolution`. **ICMP ping на 1.1.1.1 не доказывает доступность UDP/TCP 53 на этом узле.**
3. Universal launcher определил `mipsel-3.4`, штатный Core 1.8.8 прошёл resource/компонентный preflight, установил Mihomo `1.19.33-2_mipsel-3.4` из `saymer-alt/entware-go`; без подмены 55-МБ несжатым бинарником. Proxy0/Netfilter уже присутствовали. На этапе `Ensuring MagiTrickle package repository` три curl-попытки и wget fallback были исчерпаны; итог `Failed to download MagiTrickle repository helper through curl/wget`. Core оборвался и **Web не запускалась**.
4. Отдельно `nslookup bin.magitrickle.dev` через локальный DNS успешно разрешил адрес. Запрос `curl -4 -v` к `https://bin.magitrickle.dev/packages/add_repo.sh` — TLS 1.3 и HTTP **200 OK**, `Content-Length: 6522`. Запрос с `-4` по HTTP — также 200 и 6522 B. **Версия о недоступности HTTPS опровергнута. HTTP вместо HTTPS использовать не требуется.**
5. Повторные загрузки **без** `-4` по HTTPS: сначала два `curl: (6) Could not resolve: bin.magitrickle.dev:443`, затем четыре успешные передачи по 6522 B; `sh -n` выполнен без ошибок. Это прямое подтверждение **интермиттирующего отказа разрешения имени при вызове curl**, но не идентификация виновного DNS-компонента или наличия дефекта IPv6.
6. Повторный `sh /tmp/kas-universal-install.sh all` завершился успешно. Штатный Core повторно использовал уже имеющийся Mihomo (без повторной загрузки), сохранил старый YAML и отдельную резервную копию, установил MagiTrickle `0.8.2-1` из репозитория, watchdog + cron. Промежуточный `[WARN] MT_LISTENER_MISSING` затем сменился на подтверждённые `magitrickled RUNNING` и DNS listener `:3553`; Core сообщил `[OK] Done`.
7. Пользователь в интерактивном importer передал новый YAML: штатная проверка синтаксиса Mihomo прошла, конфигурация применена атомарно, старый YAML сохранён в `config.yaml.bak`, процесс и порт `:7890` подтверждены.
8. Universal launcher получил Web IPK `kas-control-center_0.1.0.beta.8-1_mipsel-3.4.ipk` (2,737,920 B), сверил опубликованный SHA256, установил OPKG, запустил `S98kas-control-center`: `RUNNING`, порт `:18080`.

### Что НЕ следует считать доказанным

- **Причина:** тайм-ауты локального резолвера, DNS-policy/DoT/DoH/перехват, потеря UDP 53, маршрутизация через другой gateway или выход, IPv6, блокировка или перегрузка сервера — гипотезы, не диагноз. `timeout:1 attempts:1` повышает чувствительность клиентского резолвера к задержкам, но ещё не доказывает корень сбоя.
- **Скорость/CPU:** MIPS/256 MB могут влиять на длительность установки и задержки, однако наблюдаемые `curl (6)` и `wget bad address` — именно провалы разрешения имён, не свидетельства CPU/flash-full/OOM.
- **Внешняя работоспособность:** status демонов/портов/Netfilter не гарантирует успешный DNS transit для клиентов, рабочий прокси upstream, доступность сайтов, состояние после reboot или правильность Web write-действий.
- **Поддержка других ABI:** KN-1010 является FIELD PASS только для `mipsel-3.4`; остальные три IPK требуют собственной аппаратной проверки.
- **CI:** по PR #482 имеется независимая проблема проверки контрольной суммы внешнего `opkg` (а также beta ladder); зелёного общего CI на тот же SHA пока нет. Нельзя ослаблять hash gate или считать FIELD заменой CI.

## 3. Инженерные выводы

- Сетевой доступ нестабилен избирательно: ICMP работал, DNS-запросы и `curl` иногда не могли разрешить отдельные имена; затем те же адреса были доступны без модификации конфигурации.
- Штатный Core **fail-closed**: не объявил успешную установку после исчерпания загрузчиков MagiTrickle; universal launcher не установил Web на незавершённом Core. Это поведение нужно сохранить.
- Повторный запуск уже частично установленного KAS в этом FIELD-кейсе прошёл без повторной установки Mihomo, защитил пользовательский YAML и довёл установку до Web. Это аргумент за idempotent recovery, но не универсальное доказательство для любых точек сбоя.
- Не нужны как «быстрые исправления»: переустановка Entware, глобальная смена DNS/`resolv.conf`, изменение `opkg.conf`/feed, HTTP fallback для исполняемых скриптов, отключение TLS/CA, `--insecure`, скачивание несжатого Mihomo вместо проверенного IPK.

## 4. План работ — последовательность и критерии

### P1-A. Диагностика первопричины DNS (read-only; #483)

- На KN-1010 сделать ограниченные серии **отдельных** проверок (`nslookup` через штатный `127.0.0.1`, `curl` default и `curl -4`) для `bin.entware.net`, `bin.magitrickle.dev`, `raw.githubusercontent.com` с датой, кодом возврата, фазой (DNS/TCP/TLS/HTTP), без сохранения содержимого настроек и подписок.
- По возможности собрать read-only состояние локального DNS/KeeneticOS и действующих DNS-policy/перехвата; сравнить поведение **до и после** старта Mihomo/MagiTrickle, а также с/без фактического VPN-трафика только посредством наблюдения. Не менять DNS/fwd/iptables без отдельного owner GO.
- Раздельно проверять DNS к явно заданному resolver **только при наличии разрешённого пути UDP/TCP 53**; ошибка `nslookup @1.1.1.1` не является доказательством неисправности штатного DNS.
- Не делать вывод о блокировке провайдером или ошибке KeeneticOS без воспроизводимой корреляции, packet trace/журналов либо свидетельств upstream.
- **Acceptance:** диагностические пробы дают раздельные коды и измерения для локального резолвера и запросов transport; причина обозначена как `CONFIRMED` только при доказательствах, иначе `UNKNOWN`.

### P1-B. Устойчивость Core downloader для MagiTrickle и других небольших скриптов (#483, #169)

- Аудировать текущие downloader функции `install.sh`/`setup.sh` на **точном SHA**; учесть имеющиеся три curl-попытки и wget fallback, не дублировать уже реализованную архитектуру.
- Смоделировать `curl exit 6` первые 2–3 раза с последующим успехом, зависший резолвер, `wget` ошибку имени, reset/TLS error, ошибочный HTTP, пустой/частичный файл, небезопасную подмену полезной нагрузки.
- Рассмотреть небольшой **bounded backoff**/повтор после `exit 6` только при доказанной пользе; не ставить бесконечные циклы. Для больших IPK сохранить отдельный тайм-аут, **не** ограничивать их бюджетом 20–25 сек для shell scripts.
- После исчерпания транспорта печатать понятный конечный статус (`DNS_RESOLUTION_FAILED`, `TCP_UNREACHABLE`, `TLS_FAILED`, `HTTP_ERROR`, `PAYLOAD_INVALID` или `UNKNOWN`) с безопасными итоговыми кодами, **не** по одной строке на каждый internal retry. Принцип вывода #169 / [18-output-colors.md](../18-output-colors.md) обязателен: quiet per attempt, один WARN на исчерпанный транспорт и итоговый ERROR; никаких секретов, raw output от доменных subscriptions, паролей и ключей.
- Скрипты из удалённого источника запускать только после проверки ожидаемого payload и синтаксиса; TLS верификацию не отключать. Следовать существующему safety contract и ownership.
- **Acceptance:** в mock успех после временных `curl 6` не приводит к лишним install/restart, постоянный отказ безопасно завершает установку, при повторе состояние уже установленных компонентов и конфиги сохранены; отсутствие ложного `[OK] Done`.

### P2-A. Ненавязчивый read-only network preflight / диагностика (#483, #167)

- Проверить существующие [kas-download-check](../27-download-check.md), [kas-network-doctor](../29-network-doctor.md) и [Entware preflight](../31-entware-busybox-preflight.md) на повторное использование — **не плодить новый дублирующий диагностический движок**.
- Перед изменением поведения оценить, стоит ли показывать opt-in/read-only проверки трёх источников до установки. **Не** вводить постоянный hard gate по внешнему DNS как способ обойти уже работающие runtime/offline сценарии или installation resource safety preflight.
- Предупреждать пользователя, если источник временами не разрешается, но не автоматически переопределять DNS на `1.1.1.1` и не переписывать `/etc/resolv.conf`.

### P2-B. Повторный OPKG update и UX слабых платформ (#167)

- Измерить реально необходимые `opkg update`: в start user command, штатном Core и после добавления MagiTrickle feed; **последнее** обновление нужно для появления новых индексов, без обоснования не удалять.
- Разделить UX для ожидания OPKG и управления KAS-download: показать текущую стадию, итоги/причину ошибки и следующий безопасный шаг, но не заливать терминал повторами или фиктивными процентами. Если есть реальный `Content-Length`, отображать прогресс только при подтверждённой поддержке и без выдуманных процентов.
- Сохранить fallback на **сжатый проверенный Mihomo IPK**, не скачивать ~55-MB raw binary по умолчанию; архитектуру определять по `opkg print-architecture`, включая `*_kn`.
- **Acceptance:** измерено снижение или осознанно сохранено число metadata requests без сломанной первичной установки; поведение на mipsel и aarch64 проверено отдельно.

### P1-C / acceptance matrix после реализации

- Mock: DNS 2× FAIL → success, DNS 3× FAIL → STOP, HTTPS 200-but-invalid payload, wrong SHA256, OPKG partial install, MT `start` сообщает `done`, но process/listener отсутствует, delayed bind 3553, безопасная повторная попытка.
- Shell/BusyBox ash lint; exact SHA CI + unit/contract smoke; доступность third-party контрольных сумм анализировать отдельно, но **не** подменять зафиксированный SHA догадкой.
- FIELD KN-1010: fresh-ish повторный запуск, после reboot подтверждены Mihomo/MT, DNS listener :3553, ProxyN/iptables, Watchdog/cron, Web :18080, реальный прокси и DNS-запросы. Секреты и приватные subscription URLs в лог не включать.
- FIELD другие ABI: aarch64-3.10 (NC-4210/KN-381x где ABI реально совпадает), armv7-3.2, mips-3.4 — только при наличии устройств/эмуляторов и отдельном owner GO.
- Выполнение отдельных acceptance шагов отмечать `IMPLEMENTED / CI PASS / FIELD PASS / MERGED / PUBLISHED` строго раздельно. **Merge в main / stable, release, изменение обновлений или роутера — отдельное решение владельца.**

## 5. Принятое сейчас решение

**DOCUMENT + INVESTIGATE**, без самовольной сетевой конфигурации. FIELD сценарий `all` на KN-1010 успешен **после повторного запуска**, но первопричина DNS остаётся открытой. Технические изменения должны идти через связанные Issue/PR, с тестами отрицательных сценариев и отдельным GO на merge/release.
